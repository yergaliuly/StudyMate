# Миграции PostgreSQL

SQL лежит в [`../src/main/resources/db/migration/`](../src/main/resources/db/migration/)
и попадает в JAR. Здесь только пояснения; вторую копию SQL не создавать.

Flyway выполняет миграции при запуске. История — `public.flyway_schema_history`;
данные приложения — в схеме `studymate`. V1 создаёт схему, V2 — таблицу `users`:
серверный UUID, нормализованный email, имя, хеш пароля и серверное время создания.
`users_normalized_email_key` обеспечивает конкурентную уникальность email.
Нормализация выполняется приложением (JS trim + lowercase Locale.ROOT); БД сравнивает
готовые ключи с collation C, без неявной зависимости от locale сервера.
V3 добавляет `studymate.spring_session` и `studymate.spring_session_attributes` по схеме
Spring Session JDBC 4.1.1 для PostgreSQL: уникальный session id, индексы срока/владельца,
атрибуты BYTEA и каскадное удаление атрибутов. В principal хранится UUID пользователя.
Автоинициализация Spring Session отключена: `spring.session.jdbc.initialize-schema=never`.
Просроченные по бездействию строки очищаются каждую минуту; доступ прекращается сразу
по истечении срока, независимо от момента очистки. V1 и V2 не переписываются.
V4 добавляет `studymate.subjects`: UUID/владелец, оформление, UTC-время создания,
уникальное нормализованное название внутри аккаунта и индекс owner/created_at/id.
Ключи названия и описания рассчитываются Java lowercase(Locale.ROOT); поиск не зависит
от locale PostgreSQL. Счётчики и прогресс не сохраняются в таблице предметов.
`studymate.subject_creation_requests` хранит успешные ответы POST /subjects на 24 часа:
ключ пользователя, SHA-256 нормализованных полей, исходные JSON и Location.
Ссылки на предмет здесь нет: удаление в будущем не должно менять исходный ответ повтора.
Предмет и ответ записываются в одной транзакции. Просроченные ответы очищаются каждые
15 минут партиями до 1000 строк; проверка срока действует независимо от очистки.
V5 добавляет `subjects.version BIGINT NOT NULL DEFAULT 1` с проверкой положительности.
Существующим предметам назначается 1; исходные данные и сохранённые JSON-ответы POST
не меняются. PATCH увеличивает версию в транзакции, после проверки ожидаемой версии.
V6 добавляет `studymate.jobs`: владелец, тип/ключ операции, внутренний JSONB payload,
политика повтора, состояние, попытки, время следующей попытки, токен/срок аренды,
предельное время выполнения, идентификатор результата и безопасный код ошибки.
Уникальность owner/kind/operation_key действует на весь срок хранения задания.
Лимиты повторов/времени фиксируются при enqueue; настройки нового запуска их не меняют.
Индексы обслуживают очередь готовых заданий, просроченные аренды и владельца.
CHECK-ограничения согласуют состояние, аренду, finished_at и результат; FK не удаляет
задания каскадно при удалении пользователя. Политика удаления аккаунтов — будущий этап.
V7 создаёт material_objects (долговечный журнал ключей/квоты/загрузок) и materials
(метаданные и версия). Уникальны owner/request_key и object_key; CHECK согласуют
uploading/stored/deleting/deleted с reserved/used/released. Квота резервируется под
блокировкой users строки, чтобы конкурирующие запросы считали общий used+reserved.
Composite FK (subject_id, owner_id) → subjects(id, owner_id) — non-deferrable ON DELETE RESTRICT;
индекс subject_id обязателен. SubjectService переводит SQLSTATE 23503 в SUBJECT_NOT_EMPTY.
Метаданные и FK предмета удаляются только после R2 DELETE в fenced callback задания.
Журнал material_objects остаётся для идемпотентности и повторной очистки поздних PUT;
cached response удаляется, quota освобождается. Технические ключи пока без срока истечения.
Будущие учебные данные и история попыток должны иметь ON DELETE CASCADE к materials;
каскад дополнительно проверяется тестовой таблицей stage8_history_test.
V8 создаёт material_pages: физический page_number 1–200 и text_content, FK materials
ON DELETE CASCADE. materials получает processing_job_id, page_count и text_characters.
Ошибки jobs расширены стабильными PDF-кодами. Старые материалы получают NULL-ссылку
на job, не ставятся в очередь миграцией; сохранённые ответы POST остаются исходными.
Все страницы и статистика сохраняются только в транзакции завершения с действующей арендой.
V9 добавляет summary_job_id, material_summaries и summary_versions с CASCADE.
V10 добавляет quiz_job_id, quizzes, quiz_questions, quiz_options. Версия уникальна внутри
материала; composite FK фиксирует владельца и принадлежность правильного варианта вопросу.
Ответ проверяется отложенным FK в конце транзакции; версия, вопросы и варианты сохраняются
атомарно. Каскад удаляет все версии с материалом. jobs получает QUIZ_INSUFFICIENT_CONTENT.
V11 добавляет attempts/attempt_answers: неизменяемая привязка к quizId и владельцу,
идемпотентный ключ начала, состояние/DB-время/серверный балл и выбранные варианты.
Composite FK запрещает смешение тестов, вопросов и вариантов; пропуски представлены NULL.
CHECK согласует completed, время и формулу балла; вся сдача сохраняется одной транзакцией.
При удалении материала все попытки/ответы удаляются через quizzes ON DELETE CASCADE.
Индексы обслуживают историю владельца и каскады. Существующие данные V10 не меняются;
попытки автоматически не создаются. Применённые V1–V10 не меняются.
Следующая миграция — `V12__description.sql`.
Тестовая таблица `stage6_material_references_test` создаётся/удаляется только интеграционным
тестом в отдельной тестовой БД и не входит в миграции приложения.
В SQL указывать схему явно, например `studymate.users`, чтобы не зависеть от search_path.

Включены проверка имён и контрольных сумм. `baseline-on-migrate` выключен:
непустая чужая база не принимается автоматически как исходная схема.
`clean` запрещён; `schema.sql`, `data.sql`, Hibernate DDL и ручные правки общей схемы
не используются. Не применять `repair` для сокрытия изменения принятой миграции.

Каждое изменение должно воспроизводиться на новой локальной базе второго участника.
В миграции не включать реальные пароли, лекции, email студентов или дампы production.
Не менять уже применённую общую миграцию молча: добавлять новое изменение и проверять его.

Проверка на отдельной PostgreSQL 17: `mvnw -Ppostgres-it verify` из `backend/`.
Переменные и создание тестовой базы описаны в [README](../README.md).
