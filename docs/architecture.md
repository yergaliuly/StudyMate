## Продукт и ответственность

StudyMate — личный учебный кабинет студента. Первый законченный сценарий:
регистрация и вход → свой предмет → PDF с текстовым слоем → извлечение текста →
сохранённый конспект → тест → серверная проверка → сохранённый результат.

Пользователь отвечает за backend, его друг — за frontend. Работа над backend ведётся
последовательно в одном потоке, по одному согласованному этапу; параллельные агенты,
worktree для нескольких задач и прежний план T00–T15 не запускаются.
Распределение работ: [team-tasks.md](team-tasks.md).

Frontend: React + Vite + JavaScript и собственный CSS. Сохраняется выбранный светлый
дизайн с сине-фиолетовыми акцентами, боковым меню, поиском и карточками;
[дизайн](design.md) не переопределяется backend-работами.

## Принятый стек и границы системы

- Java 21, Spring Boot, Maven Wrapper; один модульный монолит.
- Spring MVC для API, серверная валидация входных данных.
- Spring JDBC для данных и Flyway для последовательных миграций.
- PostgreSQL для данных приложения, серверных сессий и сохраняемых фоновых заданий.
- Spring Security и Spring Session JDBC; cookie-аутентификация с CSRF-защитой.
- Приватный Cloudflare R2 для оригиналов PDF.
- Отдельные адаптеры для R2, обработки PDF и ИИ.
- JSON и параметры API — camelCase; поля SQL — snake_case.
- Префикс `/api/v1`, оболочки `data`, `meta`, `error`.
- UUID объектов создаёт сервер; время API — ISO 8601 UTC.

На этапе 2 закреплены Java 21, Spring Boot 4.1.1, Maven 3.9.16 и Wrapper 3.3.4.
Flyway 12.4.0, PostgreSQL JDBC 42.7.13 и Spring Security 7.1.1 управляются BOM Spring Boot.
Локальное окружение: JDK 21.0.6 и PostgreSQL 17.2; Docker не требуется.
Источник версий, настройки и команды: [backend/README.md](../backend/README.md).
V1 создаёт пустую схему `studymate`; история Flyway лежит в `public`.
V2 добавляет `studymate.users`: UUID, normalized_email, display_name, password_hash,
created_at. Уникальный ключ normalized_email защищает от гонок; операция создания —
один INSERT с ON CONFLICT по именованному ограничению, без предварительного SELECT.
Аккаунт возвращается отдельным DTO без хеша и служебных полей.
На этапе 4 добавлен Spring Session JDBC 4.1.1 из BOM Boot: схему создаёт Flyway V3,
автоинициализация выключена. На этапе 5 V4 создаёт subjects и subject_creation_requests.
Работают health, auth API и GET/POST subjects; остальные маршруты закрыты.
Стандартного пользователя Spring нет.

Браузер обращается к backend через API. Backend работает с PostgreSQL, R2 и выбранным
позже ИИ-провайдером. Frontend не обращается к базе и не получает секретов сервисов.
Микросервисы, Kafka, Redis, векторная база и отдельный постоянно работающий worker-сервис
в первую версию не добавляются. Supabase не является обязательным компонентом.

## Модули монолита

| Модуль | Ответственность |
| --- | --- |
| identity | Аккаунты, хеши паролей, вход, выход, сессии и текущий пользователь |
| subjects | Предметы, оформление, поиск, уникальность названий внутри аккаунта |
| materials | Метаданные, квоты, R2, обработка PDF, страницы текста, скачивание и удаление |
| summaries | Сохранённые конспекты, редактирование и версии |
| quizzes | Неизменяемые версии тестов, вопросы, попытки и серверная проверка |
| jobs | Состояния операций, аренда выполнения, ограниченные повторы и восстановление |
| ai | Адаптер провайдера, проверка результата и учёт использования |
| dashboard | Чтение реальных агрегатов после определения метрик и появления событий |

Модули добавляются по мере соответствующих этапов. HTTP DTO отделяются от хранения:
ключи ответов теста и служебные данные нельзя случайно сериализовать вместе с объектом БД.
Владельца определяет аутентификация, а не входной `userId`.
Операции проверяют доступ ко всем объектам, включая задания, файлы и попытки.
Чужой и отсутствующий приватный объект возвращают одинаковый `404`.

## Аутентификация и взаимодействие с браузером

Сессии хранятся в PostgreSQL через Spring Session JDBC. Их схему ведёт Flyway.
После входа меняются session id и CSRF, при выходе удаляются сессия, её атрибуты и cookie.
Бездействие — максимум 30 минут, абсолютный срок — 12 часов после успешного входа;
анонимная сессия ограничена 12 часами от создания. Обычный запрос не продлевает абсолютный
срок. В principal хранится UUID без пароля/хеша/профиля; me читает актуальные данные из БД.
Перезапуск JAR не сбрасывает действующие сессии. Истечение проверяется до Security/CSRF.

Целевое развёртывание — frontend и API под одним origin; локально Vite proxy к API.
Cookie `STUDYMATE_SESSION`: HttpOnly, Secure по умолчанию, SameSite=Lax, Path=/, без Domain.
Исключение Secure — только явный HTTP-профиль `local`. CORS сейчас не включён;
Vite proxy должен добавить frontend-разработчик по примеру в backend/README.md.
Если понадобятся разные origins, разрешается конкретный origin frontend, credentials
и необходимые методы/заголовки; preflight проходит до проверки сессии.
CORS не заменяет CSRF и проверку владельца.

Frontend получает CSRF-токен через `GET /api/v1/auth/csrf` и передаёт его заголовком
в изменяющих запросах, включая регистрацию, вход, выход и загрузку файла.
После входа и выхода нужен новый токен. Точный протокол и ошибки описаны в [API](api.md).
На этапе 3 выбран Argon2id: 19 МиБ, t=2, p=1, соль 16 байт, хеш 32 байта;
используются Spring Security и Bouncy Castle 1.86. Основания и источники — в
[backend/README.md](../backend/README.md). Пароли не обрезаются и не нормализуются.
Пароли, session cookie, токены и ключи не выводятся в логи.

Регистрация закрыта по умолчанию, включая локальный запуск. Для разработки её можно
явно включить через `STUDYMATE_REGISTRATION_ENABLED=true`; CSRF при этом остаётся обязательным.
Создание аккаунта не выполняет вход. Получение CSRF и аутентификация реализованы на этапе 4.
Частотные лимиты и механизм допуска пилота должны быть готовы до открытия регистрации группе.

## Предметы и достоверность данных

Сохраняются `title`, `description`, `icon`, `tone`; допустимые коды оформления
берутся из актуальной формы и перечислены в API. Название нормализуется.
Уникальность обеспечивает БД по паре владелец–нормализованное название:
одинаковые названия у разных студентов разрешены, параллельные запросы одного
пользователя не создают дубликаты.

Этап 5: title нормализуется как JS trim + схлопывание пробелов; ключ названия и ключ
описания для поиска — Java lowercase(Locale.ROOT), с collation C в БД. Пользователь
берётся из сессии через модуль identity; SQL всегда ограничивает owner_id. Поиск использует
буквальную подстроку (%, _ и обратный слеш не становятся SQL-шаблонами).
Список и total читаются одним SQL-снимком; сортировка created_at DESC, id DESC.

Идемпотентность POST /subjects: SHA-256 нормализованных полей, область пользователь/операция/UUID.
Транзакционная pg_try_advisory_xact_lock не ждёт чужую операцию и даёт REQUEST_IN_PROGRESS
с Retry-After: 1; блокировка освобождается при commit/rollback, включая остановку процесса.
Создание и исходные 201/JSON/Location сохраняются одной транзакцией; повторы действуют 24 часа.
Результат хранится отдельно от предмета: изменение/удаление не меняет прежний ответ
и повтор не восстанавливает старое состояние. Ответы этапа 5 остаются без version;
GET возвращает актуальный предмет с версией после миграции V5.
Просроченные ответы удаляются каждые 15 минут партиями до 1000; предметы очистка не затрагивает.
Это очистка кэша, не реализация сохраняемых заданий этапа 7. Гонки, откат после сбоя записи
результата и сохранность ответа после перезапуска JAR проверены на настоящем PostgreSQL.

Этап 6: V5 добавляет положительную BIGINT version (изначально 1) без переписывания V1–V4.
GET/PATCH/DELETE фильтруют owner_id в SQL; чужой и отсутствующий UUID дают одинаковый 404.
PATCH принимает version и хотя бы одно изменяемое поле, пропущенные поля сохраняет,
явный null отклоняет. В транзакции SELECT FOR UPDATE блокирует строку, затем проверяется
версия и выполняется UPDATE с version + 1. Даже сохранение совпадающих значений увеличивает
версию. Старая версия — 409 SUBJECT_VERSION_CONFLICT, дубликат названия — 409 SUBJECT_TITLE_EXISTS.
Ошибка откатывает поля и версию. Frontend сохраняет черновик, загружает актуальные данные
по решению пользователя и не повторяет PATCH автоматически с новой версией.

DELETE удаляет только строку своего предмета, 204 без тела; повтор даёт 404. Версия для
удаления не нужна. Нарушение внешнего ключа при DELETE переводится в 409 SUBJECT_NOT_EMPTY.
Этап 6 проверил защиту на тестовой FK-таблице и гонках. Этап 8 добавляет реальную
materials с composite non-deferrable FK (subject_id, owner_id) ON DELETE RESTRICT и
индексом subject_id, сохраняя ссылку до конца очистки. CASCADE здесь запрещён. Наличие
обрабатываемого/удаляемого материала блокирует DELETE независимо от отображаемого lectureCount.

`lectureCount` вычисляет сервер по материалам с сохранённым оригиналом, исключая
удаляемые. Ошибка извлечения текста не означает отсутствия уже загруженного материала.
Клиент не задаёт владельца, id, даты и счётчики.

Этап 8 вычисляет lectureCount из stored-материалов в запросах списка/GET/PATCH предметов;
отдельного сохранённого счётчика нет. Кэш старого POST остаётся исходным ответом.

`progressPercent` пока всегда `null`: метрика ещё не определена.
Демонстрационные 65%, число изученных лекций, тестов и повторений не импортируются
из frontend в аккаунт. Новому аккаунту возвращается пустой список предметов.
Завершённая попытка, созданный тест и повторение карточки — разные события.

## PDF, R2 и удаление

Первая версия принимает PDF с извлекаемым текстом. OCR, сканы без текстового слоя
и аудио не входят в обязательный объём. Загружаемый файл недоверенный:
проверяются формат, фактический размер, принадлежность предмета и квота.
Дополнительно ограничиваются число страниц, объём извлечённого текста, память,
время обработки и конкурентность. Для этапа 9 пользователь утвердил 200 страниц,
1 000 000 UTF-16 символов суммарно и 100 000 на страницу, 60 секунд и heap 256 МиБ.

Начальная загрузка идёт через backend. Сначала проверяются аутентификация и CSRF
в заголовке (без чтения multipart); после разбора ограниченных частей — доступ к предмету.
Файл принимается с ограничением размера и проверяется;
затем транзакционно резервируется квота и сохраняется запись с ключом R2.
Подтверждение оригинала даёт 201/stored; этап 9 создаёт material.extract_text в той же
транзакции, processingStatus=queued. Старые материалы остаются not_started до явного process.
Текст сохраняется в PostgreSQL с реальными номерами страниц. PDFBox 3.0.8 работает
в короткоживущей дочерней Java 21 JVM с ограничениями, описанными ниже.

R2 и PostgreSQL не образуют общую транзакцию. Сохраняются сведения, достаточные
для сверки неоднозначного результата загрузки и повторной очистки.
Квота учитывает занятые и зарезервированные байты, включая параллельные загрузки.
Освобождение квоты выполняется однократно после подтверждённой очистки.
Временный диск не является постоянным хранилищем лекций.

Доступ к оригиналу выдаётся после проверки владельца через краткоживущую подписанную
ссылку. Она доступна её обладателю до истечения срока, не является доказательством
личности и не хранится как постоянный URL материала.

Принятая политика удаления (предметы — этап 6; материалы — этап 8):

- Непустой предмет удалить нельзя: `409 SUBJECT_NOT_EMPTY`. Проверка выполняется
  сервером и учитывает материалы в обработке/очистке, а не только отображаемый счётчик.
- Удаление материала удаляет оригинал и связанные учебные данные, включая попытки
  тестов. Frontend до отправки запроса явно предупреждает об этом.
- Материал помечается удаляемым; новые операции запрещаются. Сохраняемое задание
  удаляет объект R2, затем завершает очистку PostgreSQL.
- При сбое сохраняются ключ объекта, состояние и возможность повторной очистки.
  Повтор не создаёт вторую независимую операцию и не освобождает квоту дважды.
- Завершение старой генерации не должно возвращать данные удаляемому материалу.

## Реализация хранения этапа 8

Подтверждены лимиты: PDF 25 МиБ = 26 214 400 байт; аккаунт 500 МиБ = 524 288 000 байт.
title необязателен, по умолчанию берётся из имени файла; точная нормализация и все DTO — в api.md.
V7 создаёт materials и отдельный технический журнал material_objects. Сначала под блокировкой
users строки считаются used+reserved и резервируется квота; запись журнала с уникальным
owner/request_key и ключом объекта фиксируется до PUT. Внешние вызовы выполняются вне
транзакции. Временные multipart-файлы ограничены размером и удаляются после запроса;
постоянного хранения оригиналов на диске нет. Две загрузки на процесс, отказ 429 при перегрузке.
До PDF-процессора проверяются расширение/MIME, фактический размер, заголовок/окончание и SHA-256.
Текстовый слой, шифрование и структуру затем проверяет обработчик этапа 9.

ObjectStorage реализован AWS SDK Java 2.55.7: R2 S3 API, region auto, path style,
chunked encoding выключен, совместимый Content-MD5, ключи и подписи не логируются.
PUT без скрытых повторов, connect 5 с, socket 20 с, попытка 30 с, вызов 60 с.
Для подписи и отправки SDK может читать файл несколько раз даже при одной HTTP-попытке.
Адаптер переоткрывает поток и закрывает предыдущий; mark/reset и копия всего PDF в heap не нужны.
GET URL подписывается локально на 60 с, attachment application/pdf; бакет должен быть приватным.
R2 выключен по умолчанию. Без конфигурации нет имитации облака: загрузка/скачивание/удаление
и явный process возвращают 503, обработчики очистки/извлечения не регистрируются;
остальные функции, включая чтение сохранённых страниц, работают.

Результат PUT публикуется только если состояние ещё uploading и DB-дедлайн 5 минут не истёк.
Одинаковый Idempotency-Key/fingerprint не выполняет второй PUT. После неоднозначного сбоя
запись переводится в deleting; если БД в этот момент недоступна, maintenance найдёт просроченную
reservation после перезапуска (первый проход через 10 с, далее каждую минуту, до 20 записей).
Для неподтверждённой загрузки DELETE ждёт исходный дедлайн, для подтверждённой запускается сразу.
Удаление атомарно ставит deleting и enqueue material.delete (SAFE); новые операции запрещены.
После R2 DELETE короткий callback с проверкой аренды/актуального job удаляет materials
и освобождает квоту. Порядок блокировок: job → users → material_objects → materials.
FK предмета остаётся до callback. При исчерпании повторов quota/key сохраняются;
явный повтор DELETE создаёт новый job, одновременные повторы получают один jobId.

R2 и PostgreSQL не могут дать атомарное «ровно один раз». Даже после таймаута удалённый PUT
может завершиться поздно: журнал ключей не удаляется и после успешной очистки. Maintenance
проверяет не более одного просроченного tombstone за проход, повторяет DELETE не чаще раза
в сутки на ключ; при сбое ключ остаётся для следующего прохода. Это eventual cleanup,
не гарантия отсутствия кратковременного удалённого объекта в любой момент. Ключи никогда
не используются для новой загрузки; deleted не может стать stored. Имена/кэш ответа при
удалении очищаются, технические ID/ключ/hash/размер сохраняются; срок журнала пока не ограничен.

Пользователь повторно подтвердил удаление истории попыток. Таблицы будущих страниц,
конспектов, тестов и попыток должны иметь ON DELETE CASCADE к materials; сейчас такие данные
не создаются. Ошибка любой зависимой очистки откатывает DB-завершение и освобождение квоты.
Download подписывается под короткой блокировкой object без внешних вызовов, согласованной
с началом DELETE. Выданная ранее ссылка может оставаться действительной до удаления/TTL.

## Фоновые задания и ИИ

Обработчик работает внутри монолита, источник состояния — PostgreSQL.
Задания имеют состояния очереди, выполнения и завершения, ограниченное число попыток,
время следующего запуска, аренду выполнения и безопасную ошибку.
Выбор задания и фиксация результата — короткие транзакции; внешние вызовы выполняются
вне них. Просроченные аренды разбираются при старте и во время работы.
Результат устаревшего выполнения не перезаписывает новое состояние.

Этап 7 реализует эту основу в `com.studymate.jobs`, миграция V6. JobQueue.enqueue —
внутренний API модулей: UUID владельца из проверенного контекста, тип, ключ операции,
JSON-объект со ссылками на данные (до 16 КиБ), обязательная политика SAFE/MANUAL.
Лекции, пароли, ключи и большие результаты в payload не помещаются. Вставка присоединяется
к транзакции доменного изменения. UNIQUE(owner_id, kind, operation_key) и сравнение JSONB
возвращают тот же id при повторе; иной payload/политика дают IDEMPOTENCY_KEY_REUSED.
Завершение/отмена не освобождает ключ. Очистка jobs и срок хранения пока не определены.

Каждый процесс держит один активный handler. Claim — один короткий SQL со SKIP LOCKED,
увеличением attempt_count и новым UUID-токеном аренды. Поддерживаемые типы задаются
зарегистрированными JobHandler; неизвестные типы остаются queued без расхода попыток.
Стандартные настройки: опрос 1 с, аренда 30 с, heartbeat 5 с, предел выполнения 120 с,
3 попытки, backoff 2 × 2^(attempt−1) с максимумом 60 с. Параметры ограничены и валидируются.
Настройки попыток/аренды/времени сохраняются в задании; heartbeat адаптируется к более
короткой старой аренде после смены конфигурации. Все решения о сроках принимает БД.

JobHandler.execute вызывается вне транзакции на отдельном потоке. Продление аренды
работает независимо от обработчика и очистки сессий/кэша. Результат возвращается как
JobOutcome; короткий callback Succeeded сохраняет доменные изменения и завершение задания
в одной транзакции после блокировки задания и проверки owner/id/token/сроков.
Повторная проверка после callback откатывает и результат, и статус, если аренда истекла.
Callback не делает внешних вызовов. Доменный адаптер обязан повторно проверять владельца,
актуальную версию и состояние удаления своего ресурса. При отмене/удалении нужен единый
порядок блокировок: сначала задания, затем доменный ресурс, чтобы не создавать дедлоки.

При старте и каждом цикле worker восстанавливает до 100 просроченных аренд со SKIP LOCKED.
SAFE получает отложенную попытку в пределах лимита; исчерпание — JOB_ATTEMPTS_EXHAUSTED.
MANUAL имеет одну попытку: потеря аренды/неизвестный результат → failed/JOB_OUTCOME_UNKNOWN.
Handler явно отличает известный временный сбой (Retry) от окончательного (Failed);
неожиданное исключение не повторяется вслепую. В БД/API только коды из разрешённого списка,
в логах фаза и класс ошибки, без payload, SQL и сообщения исключения.

Потеря аренды/таймаут/отмена посылают прерывание потоку; оно кооперативное, не гарантирует
остановку зависшей библиотеки или внешнего запроса. Слот остаётся занятым до фактического
выхода handler, чтобы не накапливать потоки/задачи. При выключении процесса работа остаётся
под арендой до восстановления. Внешние адаптеры должны иметь собственные таймауты;
этап 9 завершает дочерний PDF-процесс при прерывании и проверяет его ограничения отдельно.

Для SAFE семантика выполнения — как минимум один раз; после утраты аренды старый
внешний вызов ещё может идти одновременно с новой попыткой. Токен защищает публикацию
результата в БД, но не делает сторонний сервис транзакционным. Для внешних эффектов
нужны идемпотентность провайдера/операции либо MANUAL с разбором неопределённого исхода.
Правило будущих платных вызовов ниже остаётся обязательным.

Внутренняя отмена owner/id переводит queued/running в cancelled и лишает старую попытку
права сохранять результат. Прямой HTTP-записи jobs нет; GET /jobs/{id} показывает состояние
владельцу, без payload и аренды. Этап 8 создаёт/повторяет material.delete через DELETE материала.
Тестовые операции и JobProcessMain/MaterialProcessMain находятся исключительно в src/test.

Если хостинг останавливает приложение, задания ждут в базе и продолжаются после
пробуждения. Постоянная работа обработчика во время сна не обещается.
Один `@Async` без сохраняемого состояния не обеспечивает это поведение.

Повтор HTTP-запроса связывается с прежней операцией. Повторы внешних вызовов имеют
таймауты, лимит попыток и задержку. При неопределённом результате платного вызова
и отсутствии надёжной дедупликации у провайдера автоматический повтор запрещён:
сохраняется ошибка `AI_OUTCOME_UNKNOWN` для явного разбора.

Для конспекта выбран OpenAI `gpt-6-luna` через Responses API. `disabled` — умолчание;
`fake` разрешён только в локальном профиле и явно помечается. В опубликованном режиме
без настроенного реального провайдера POST возвращает `AI_UNAVAILABLE`.
Ключ живёт только в окружении backend, `store=false` задаётся для каждого запроса.
Генерация запускается лишь явным POST после предупреждения о передаче текста и стоимости.
Этап 10 не требует настоящего платного вызова в автоматических тестах.

Текст лекции — данные, а не команды приложению. Адаптер не даёт ему инструментов,
SQL, секретов или доступа к другим материалам. Ответ проверяется по структуре,
размеру и связности; ссылки на страницы сверяются с источником.
Корректный JSON не гарантирует правильности содержания.
О передаче текста внешнему ИИ и ограничениях точности сообщается до обработки.
Большие документы не обрезаются молча; поддерживаемый объём и обработка частями
согласованы для этапа 10: до 1 000 000 символов/200 страниц, последовательные части
до 100 000 символов и не более 15 вызовов на материал, без сложного RAG.
Структурированный ответ каждого вызова проверяется по форме и физическим страницам.
Части соединяются детерминированно; ошибки предыдущей генерации не удаляют прежний конспект.
Оплачиваемые вызовы идут с MANUAL job и не повторяются после неопределённого исхода.
Лимит расходов проекта OpenAI управляется отдельно в панели; приложение не оценивает
стоимость в долларах до вызова и не заменяет внешний hard limit.

V9 добавляет ссылку материала на текущий summary job, запись текущей версии и историю
`summary_versions` с каскадным удалением. POST повторным ключом возвращает прежнее задание;
новый ключ после завершения создаёт следующую версию. GET читает сохранённую версию,
не запуская ИИ. PATCH проверяет `version`, конфликт отдаёт 409. Ручная правка очищает
машинные sourcePages; текст предыдущей версии остаётся в истории БД. DELETE материала
отменяет текущее summary job перед очисткой и удаляет все версии вместе с материалом.

## Извлечение текста (этап 9)

V8 добавляет material_pages с FK ON DELETE CASCADE, ссылку materials.processing_job_id,
page_count/text_characters и разрешённые ошибки jobs. Статус обработки выводится из текущего
job: not_started / queued / running / ready / failed / cancelled. Нет отдельного флага,
который мог бы зависнуть при аварии. Старые записи и кэши ответов загрузки не переписываются.

Обработчик скачивает оригинал вне транзакции в приватный временный каталог, ограничивает
фактический объём и сверяет SHA-256. Парсер получает только этот файл, минимальный worker JAR
и PDFBox/fontbox/pdfbox-io/commons-logging. Spring, JDBC, R2 и секреты не передаются;
окружение очищается, stdout — ограниченный бинарный протокол, stderr отбрасывается.
Java 21 SecurityManager с отдельной policy запрещает сеть, процессы, запись и чтение
посторонних файлов. Разрешено чтение исходного PDF, runtime парсера и JDK. На другом major
Java или без SecurityManager worker отказывает в работе. Эта API устарела: переход на
другую Java потребует замены и повторной проверки изоляции, а не отключения политики.

Heap ограничен 256 МиБ, metaspace 64 МиБ, direct memory 16 МиБ, code cache 32 МиБ.
Это не предел RSS процесса и не OS sandbox: native-уязвимости JVM требуют защиты средствами
хостинга. Для пилота нужны лимиты памяти/диска/CPU на уровне ОС и обновляемый JDK 21.
Одна активная обработка на процесс backend, таймаут дочерней JVM 60 секунд; при timeout,
отмене или потере аренды родитель завершает ребёнка. Внутренний watchdog ограничивает
время оставшегося ребёнка при аварии родителя. Временные файлы удаляются в finally;
после аварии родителя остатки требуют штатной очистки приватного temp на хостинге.

PDF без текста/зашифрованный/повреждённый/слишком большой завершается стабильной ошибкой;
частичные страницы не публикуются, оригинал и usedBytes остаются. OCR не выполняется.
Текст недоверенный, его нельзя исполнять или воспринимать как инструкции. Пустые страницы
сохраняются; UTF-16 лимиты включают пробелы/переводы строк, NUL/непарные суррогаты заменяются.

Парсинг выполняется вне БД-транзакции. Fenced callback задания атомарно сохраняет все
страницы и счётчики; перед сохранением проверяет владельца, stored и processing_job_id.
Порядок блокировок: processing job → users → material_objects → materials. DELETE сначала
блокирует/отменяет текущий processing job, затем создаёт очистку. Если job сменился между
предварительным чтением и блокировкой объекта, DELETE возвращает повторяемый 409.
Просроченный/отменённый результат не записывается; callback и статус succeeded коммитятся вместе.
Рестарт восстанавливает SAFE-задание, GET pages читает сохранённый результат без R2/парсинга.
Повтор process после ошибки — явное действие с новым Idempotency-Key, готовый текст повторно
не извлекается. Новый API и обязанности frontend описаны в api.md/team-tasks.md.

## Генерация тестов — этап 11

`quizzes` сохраняет неизменяемые версии с отдельными UUID; `quiz_questions` и `quiz_options`
содержат вопросы, варианты и закрытый ключ. Composite FK требует, чтобы correct_option_id
ссылался на вариант того же вопроса. `(material_id, owner_id)` связан с владельцем материала.
Новая успешная генерация добавляет версию; будущие attempts будут ссылаться на её UUID.
API проецирует только публичные поля вопросов/вариантов, без ключа, объяснения и источников.

Явный POST `/materials/{id}/quizzes` создаёт material.quiz/MANUAL с пределом 1200 секунд;
GET списка возвращает сохранённые версии и состояние последнего задания, GET `/quizzes/{id}`
читает конкретную версию. По умолчанию 10 вопросов × 4 варианта × 1 правильный ответ.
SourceText делит весь PDF на фрагменты до 100 000 символов, учитывая метки страниц и суррогаты.
Короткий материал идёт прямо в генератор; длинный — через внутренние тезисы каждого фрагмента
и один финальный запрос. До 16 вызовов, общие token counters, без автоматического повтора.
Сохранённый пользовательский конспект не используется как исходник теста.

Structured Outputs и собственная валидация проверяют форму, количества, дубли, ссылки и размеры.
Семантическая точность вопросов остаётся ограничением модели. Недостаточно материала —
QUIZ_INSUFFICIENT_CONTENT, никакой частичной версии. При сбое предыдущие версии остаются.
Callback задания атомарно записывает версию/10 вопросов/40 вариантов вместе с succeeded,
после проверки аренды, владельца, stored и актуального quiz_job_id. DELETE блокирует текущие
processing/summary/quiz jobs в сортированном порядке до users/object/material, проверяет их
неизменность и отменяет генерации. Все версии удаляются CASCADE с материалом.
Прохождение, серверный балл и история — этап 12.

## Начальная модель данных

| Сущности | Назначение |
| --- | --- |
| users, таблицы Spring Session | Аккаунты и серверные сессии |
| subjects | Владелец, нормализованное название, описание, оформление, версия редактирования |
| materials, material_pages | Оригинал, состояние, текст по страницам |
| storage_usage | Занятые и зарезервированные байты |
| jobs, idempotency_requests | Долгие операции и повторные запросы |
| material_summaries, summary_versions | Текущая версия, история конспекта и страницы-источники |
| quizzes, quiz_questions, quiz_options | Неизменяемые версии тестов и закрытые ключи ответов — этап 11 |
| attempts, attempt_answers | Попытка, выбранные ответы, итог и время |
| Учёт использования ИИ | Резервы и фактическое использование, связанные с заданием |

Это ориентир для поэтапных миграций, не созданная SQL-схема. Связи и ограничения
должны предотвращать смешение владельцев и привязку ответа к чужому вопросу.
В первой версии у вопроса один правильный вариант. Backend проверяет сохранённый
ключ, ИИ не участвует в подсчёте. Завершённая попытка не меняется при новой генерации.
Повтор отправки попытки не создаёт второй результат.

## Проверки и отложенные вопросы

Тесты добавляются вместе с функциями: чужие данные, ограничения БД, CSRF,
параллельные запросы, квоты, PDF, ошибки R2/ИИ, перезапуски и сохранность результатов.
Для интеграционных проверок нужен настоящий PostgreSQL; Testcontainers предпочтителен
при доступном Docker. Подмены внешних сервисов контролируемы и явно обозначены.
CI добавляется с реальными командами проверок, без фиктивного успешного workflow.
Отсутствие Docker, сети или credentials отражается в отчёте о невыполненных проверках.

До выбора хостинга проверяем память JVM и обработки PDF, холодный запуск,
приостановку приложения, фоновые операции, лимиты HTTP и соединений,
постоянное хранение PostgreSQL, резервные копии и восстановление.
Бесплатный/пробный тариф не означает бесплатность и безлимитность всей системы.

Остаются отложенными: версии ещё не подключённых библиотек; хостинг;
оценка стоимости хеширования на хостинге;
частотные лимиты, механизм допуска пилота и подтверждение email; OS-изоляция PDF на выбранном хостинге;
метрики прогресса и дневная временная зона; детали следующих API и сроки хранения.
Прежние ориентиры 10/50 МиБ заменены утверждёнными 25 МиБ/PDF и 500 МиБ/аккаунт.
title, DTO и состояния материалов закреплены в api.md; frontend нужно подключить новый контракт.
