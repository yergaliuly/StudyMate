## Продукт и ответственность

StudyMate — личный учебный кабинет студента. Первый законченный сценарий:
регистрация и вход → свой предмет → PDF с текстовым слоем → извлечение текста →
сохранённый конспект → тест → серверная проверка → сохранённый результат.

Пользователь отвечает за backend, его друг — за frontend. Работа над backend ведётся
последовательно в одном потоке, по одному согласованному этапу; параллельные агенты,
worktree для нескольких задач и прежний план T00–T15 не запускаются.
Распределение работ: [team-tasks.md](team-tasks.md).

Frontend: React + Vite + JavaScript и собственный CSS. Сохраняется выбранный светлый
дизайн с сине-фиолетовыми акцентами, боковым меню, поиском и карточками;
[дизайн](design.md) не переопределяется backend-работами.

## Принятый стек и границы системы

- Java 21, Spring Boot, Maven Wrapper; один модульный монолит.
- Spring MVC для API, серверная валидация входных данных.
- Spring JDBC для данных и Flyway для последовательных миграций.
- PostgreSQL для данных приложения, серверных сессий и сохраняемых фоновых заданий.
- Spring Security и Spring Session JDBC; cookie-аутентификация с CSRF-защитой.
- Приватный Cloudflare R2 для оригиналов PDF.
- Отдельные адаптеры для R2, обработки PDF и ИИ.
- JSON и параметры API — camelCase; поля SQL — snake_case.
- Префикс `/api/v1`, оболочки `data`, `meta`, `error`.
- UUID объектов создаёт сервер; время API — ISO 8601 UTC.

На этапе 2 закреплены Java 21, Spring Boot 4.1.1, Maven 3.9.16 и Wrapper 3.3.4.
Flyway 12.4.0, PostgreSQL JDBC 42.7.13 и Spring Security 7.1.1 управляются BOM Spring Boot.
Локальное окружение: JDK 21.0.6 и PostgreSQL 17.2; Docker не требуется.
Источник версий, настройки и команды: [backend/README.md](../backend/README.md).
V1 создаёт пустую схему `studymate`; история Flyway лежит в `public`.
V2 добавляет `studymate.users`: UUID, normalized_email, display_name, password_hash,
created_at. Уникальный ключ normalized_email защищает от гонок; операция создания —
один INSERT с ON CONFLICT по именованному ограничению, без предварительного SELECT.
Аккаунт возвращается отдельным DTO без хеша и служебных полей.
На этапе 4 добавлен Spring Session JDBC 4.1.1 из BOM Boot: схему создаёт Flyway V3,
автоинициализация выключена. На этапе 5 V4 создаёт subjects и subject_creation_requests.
Работают health, auth API и GET/POST subjects; остальные маршруты закрыты.
Стандартного пользователя Spring нет.

Браузер обращается к backend через API. Backend работает с PostgreSQL, R2 и выбранным
позже ИИ-провайдером. Frontend не обращается к базе и не получает секретов сервисов.
Микросервисы, Kafka, Redis, векторная база и отдельный постоянно работающий worker-сервис
в первую версию не добавляются. Supabase не является обязательным компонентом.

## Модули монолита

| Модуль | Ответственность |
| --- | --- |
| identity | Аккаунты, хеши паролей, вход, выход, сессии и текущий пользователь |
| subjects | Предметы, оформление, поиск, уникальность названий внутри аккаунта |
| materials | Метаданные, квоты, R2, обработка PDF, страницы текста, скачивание и удаление |
| summaries | Сохранённые конспекты, редактирование и версии |
| quizzes | Неизменяемые версии тестов, вопросы, попытки и серверная проверка |
| jobs | Состояния операций, аренда выполнения, ограниченные повторы и восстановление |
| ai | Адаптер провайдера, проверка результата и учёт использования |
| dashboard | Чтение реальных агрегатов после определения метрик и появления событий |

Модули добавляются по мере соответствующих этапов. HTTP DTO отделяются от хранения:
ключи ответов теста и служебные данные нельзя случайно сериализовать вместе с объектом БД.
Владельца определяет аутентификация, а не входной `userId`.
Операции проверяют доступ ко всем объектам, включая задания, файлы и попытки.
Чужой и отсутствующий приватный объект возвращают одинаковый `404`.

## Аутентификация и взаимодействие с браузером

Сессии хранятся в PostgreSQL через Spring Session JDBC. Их схему ведёт Flyway.
После входа меняются session id и CSRF, при выходе удаляются сессия, её атрибуты и cookie.
Бездействие — максимум 30 минут, абсолютный срок — 12 часов после успешного входа;
анонимная сессия ограничена 12 часами от создания. Обычный запрос не продлевает абсолютный
срок. В principal хранится UUID без пароля/хеша/профиля; me читает актуальные данные из БД.
Перезапуск JAR не сбрасывает действующие сессии. Истечение проверяется до Security/CSRF.

Целевое развёртывание — frontend и API под одним origin; локально Vite proxy к API.
Cookie `STUDYMATE_SESSION`: HttpOnly, Secure по умолчанию, SameSite=Lax, Path=/, без Domain.
Исключение Secure — только явный HTTP-профиль `local`. CORS сейчас не включён;
Vite proxy должен добавить frontend-разработчик по примеру в backend/README.md.
Если понадобятся разные origins, разрешается конкретный origin frontend, credentials
и необходимые методы/заголовки; preflight проходит до проверки сессии.
CORS не заменяет CSRF и проверку владельца.

Frontend получает CSRF-токен через `GET /api/v1/auth/csrf` и передаёт его заголовком
в изменяющих запросах, включая регистрацию, вход, выход и загрузку файла.
После входа и выхода нужен новый токен. Точный протокол и ошибки описаны в [API](api.md).
На этапе 3 выбран Argon2id: 19 МиБ, t=2, p=1, соль 16 байт, хеш 32 байта;
используются Spring Security и Bouncy Castle 1.86. Основания и источники — в
[backend/README.md](../backend/README.md). Пароли не обрезаются и не нормализуются.
Пароли, session cookie, токены и ключи не выводятся в логи.

Регистрация закрыта по умолчанию, включая локальный запуск. Для разработки её можно
явно включить через `STUDYMATE_REGISTRATION_ENABLED=true`; CSRF при этом остаётся обязательным.
Создание аккаунта не выполняет вход. Получение CSRF и аутентификация реализованы на этапе 4.
Частотные лимиты и механизм допуска пилота должны быть готовы до открытия регистрации группе.

## Предметы и достоверность данных

Сохраняются `title`, `description`, `icon`, `tone`; допустимые коды оформления
берутся из актуальной формы и перечислены в API. Название нормализуется.
Уникальность обеспечивает БД по паре владелец–нормализованное название:
одинаковые названия у разных студентов разрешены, параллельные запросы одного
пользователя не создают дубликаты.

Этап 5: title нормализуется как JS trim + схлопывание пробелов; ключ названия и ключ
описания для поиска — Java lowercase(Locale.ROOT), с collation C в БД. Пользователь
берётся из сессии через модуль identity; SQL всегда ограничивает owner_id. Поиск использует
буквальную подстроку (%, _ и обратный слеш не становятся SQL-шаблонами).
Список и total читаются одним SQL-снимком; сортировка created_at DESC, id DESC.

Идемпотентность POST /subjects: SHA-256 нормализованных полей, область пользователь/операция/UUID.
Транзакционная pg_try_advisory_xact_lock не ждёт чужую операцию и даёт REQUEST_IN_PROGRESS
с Retry-After: 1; блокировка освобождается при commit/rollback, включая остановку процесса.
Создание и исходные 201/JSON/Location сохраняются одной транзакцией; повторы действуют 24 часа.
Результат хранится отдельно от предмета: изменение/удаление не меняет прежний ответ
и повтор не восстанавливает старое состояние. Ответы этапа 5 остаются без version;
GET возвращает актуальный предмет с версией после миграции V5.
Просроченные ответы удаляются каждые 15 минут партиями до 1000; предметы очистка не затрагивает.
Это очистка кэша, не реализация сохраняемых заданий этапа 7. Гонки, откат после сбоя записи
результата и сохранность ответа после перезапуска JAR проверены на настоящем PostgreSQL.

Этап 6: V5 добавляет положительную BIGINT version (изначально 1) без переписывания V1–V4.
GET/PATCH/DELETE фильтруют owner_id в SQL; чужой и отсутствующий UUID дают одинаковый 404.
PATCH принимает version и хотя бы одно изменяемое поле, пропущенные поля сохраняет,
явный null отклоняет. В транзакции SELECT FOR UPDATE блокирует строку, затем проверяется
версия и выполняется UPDATE с version + 1. Даже сохранение совпадающих значений увеличивает
версию. Старая версия — 409 SUBJECT_VERSION_CONFLICT, дубликат названия — 409 SUBJECT_TITLE_EXISTS.
Ошибка откатывает поля и версию. Frontend сохраняет черновик, загружает актуальные данные
по решению пользователя и не повторяет PATCH автоматически с новой версией.

DELETE удаляет только строку своего предмета, 204 без тела; повтор даёт 404. Версия для
удаления не нужна. Нарушение внешнего ключа при DELETE переводится в 409 SUBJECT_NOT_EMPTY.
Таблицы материалов пока нет; защита проверена на явно тестовой таблице ссылок PostgreSQL,
в том числе при одновременных вставке связи и удалении предмета. Это не модель/загрузка PDF.
Этап 8 обязан добавить к materials.subject_id non-deferrable FK с ON DELETE RESTRICT и
индексом subject_id, сохраняя ссылку до конца очистки. CASCADE здесь запрещён. Наличие
обрабатываемого/удаляемого материала блокирует DELETE независимо от отображаемого lectureCount.

`lectureCount` вычисляет сервер по материалам с сохранённым оригиналом, исключая
удаляемые. Ошибка извлечения текста не означает отсутствия уже загруженного материала.
Клиент не задаёт владельца, id, даты и счётчики.

До этапа материалов lectureCount=0 для всех предметов; отдельного сохранённого счётчика нет.
Запрос счётчика будет дополнен после появления таблицы материалов.

`progressPercent` пока всегда `null`: метрика ещё не определена.
Демонстрационные 65%, число изученных лекций, тестов и повторений не импортируются
из frontend в аккаунт. Новому аккаунту возвращается пустой список предметов.
Завершённая попытка, созданный тест и повторение карточки — разные события.

## PDF, R2 и удаление

Первая версия принимает PDF с извлекаемым текстом. OCR, сканы без текстового слоя
и аудио не входят в обязательный объём. Загружаемый файл недоверенный:
проверяются формат, фактический размер, принадлежность предмета и квота.
Дополнительно ограничиваются число страниц, объём извлечённого текста, память,
время обработки и конкурентность. Конкретные пределы ещё предстоит закрепить.

Начальная загрузка идёт через backend. Сначала проверяются аутентификация, CSRF
и доступ к предмету. Файл принимается с ограничением размера и проверяется;
затем транзакционно резервируется квота и сохраняется запись с ключом R2.
После подтверждения записи оригинала создаётся задание извлечения текста.
Текст сохраняется в PostgreSQL с реальными номерами страниц.
PDFBox рассматривается как инструмент извлечения; его версию проверим при подключении.
Изоляция PDF в короткоживущем дочернем процессе требует технической проверки на этапе 9;
она сейчас не реализована и не объявлена проверенной.

R2 и PostgreSQL не образуют общую транзакцию. Сохраняются сведения, достаточные
для сверки неоднозначного результата загрузки и повторной очистки.
Квота учитывает занятые и зарезервированные байты, включая параллельные загрузки.
Освобождение квоты выполняется однократно после подтверждённой очистки.
Временный диск не является постоянным хранилищем лекций.

Доступ к оригиналу выдаётся после проверки владельца через краткоживущую подписанную
ссылку. Она доступна её обладателю до истечения срока, не является доказательством
личности и не хранится как постоянный URL материала.

Принятая политика удаления (предметы — этап 6; материалы — этап 8):

- Непустой предмет удалить нельзя: `409 SUBJECT_NOT_EMPTY`. Проверка выполняется
  сервером и учитывает материалы в обработке/очистке, а не только отображаемый счётчик.
- Удаление материала удаляет оригинал и связанные учебные данные, включая попытки
  тестов. Frontend до отправки запроса явно предупреждает об этом.
- Материал помечается удаляемым; новые операции запрещаются. Сохраняемое задание
  удаляет объект R2, затем завершает очистку PostgreSQL.
- При сбое сохраняются ключ объекта, состояние и возможность повторной очистки.
  Повтор не создаёт вторую независимую операцию и не освобождает квоту дважды.
- Завершение старой генерации не должно возвращать данные удаляемому материалу.

## Фоновые задания и ИИ

Обработчик работает внутри монолита, источник состояния — PostgreSQL.
Задания имеют состояния очереди, выполнения и завершения, ограниченное число попыток,
время следующего запуска, аренду выполнения и безопасную ошибку.
Выбор задания и фиксация результата — короткие транзакции; внешние вызовы выполняются
вне них. Просроченные аренды разбираются при старте и во время работы.
Результат устаревшего выполнения не перезаписывает новое состояние.

Если хостинг останавливает приложение, задания ждут в базе и продолжаются после
пробуждения. Постоянная работа обработчика во время сна не обещается.
Один `@Async` без сохраняемого состояния не обеспечивает это поведение.

Повтор HTTP-запроса связывается с прежней операцией. Повторы внешних вызовов имеют
таймауты, лимит попыток и задержку. При неопределённом результате платного вызова
и отсутствии надёжной дедупликации у провайдера автоматический повтор запрещён:
сохраняется ошибка `AI_OUTCOME_UNKNOWN` для явного разбора.

ИИ-провайдер и модель не выбраны. Предусматриваются `disabled` и явно обозначенный
`fake` для разработки и тестов. В опубликованном режиме без реального провайдера
возвращается `AI_UNAVAILABLE`; заглушка не выдаётся за настоящую генерацию.
До разрешения пользователя платные запросы и облачные ресурсы не создаются.

Текст лекции — данные, а не команды приложению. Адаптер не даёт ему инструментов,
SQL, секретов или доступа к другим материалам. Ответ проверяется по структуре,
размеру и связности; ссылки на страницы сверяются с источником.
Корректный JSON не гарантирует правильности содержания.
О передаче текста внешнему ИИ и ограничениях точности сообщается до обработки.
Большие документы не обрезаются молча; поддерживаемый объём и обработка частями
согласуются на этапе генерации, без автоматического добавления сложного RAG.

## Начальная модель данных

| Сущности | Назначение |
| --- | --- |
| users, таблицы Spring Session | Аккаунты и серверные сессии |
| subjects | Владелец, нормализованное название, описание, оформление, версия редактирования |
| materials, material_pages | Оригинал, состояние, текст по страницам |
| storage_usage | Занятые и зарезервированные байты |
| jobs, idempotency_requests | Долгие операции и повторные запросы |
| summaries | Сохранённые версии конспекта и источники |
| quizzes, questions, options | Неизменяемые версии тестов и закрытые ключи ответов |
| attempts, attempt_answers | Попытка, выбранные ответы, итог и время |
| Учёт использования ИИ | Резервы и фактическое использование, связанные с заданием |

Это ориентир для поэтапных миграций, не созданная SQL-схема. Связи и ограничения
должны предотвращать смешение владельцев и привязку ответа к чужому вопросу.
В первой версии у вопроса один правильный вариант. Backend проверяет сохранённый
ключ, ИИ не участвует в подсчёте. Завершённая попытка не меняется при новой генерации.
Повтор отправки попытки не создаёт второй результат.

## Последовательные этапы

После каждого этапа — проверка, отчёт и остановка до следующего указания пользователя.
Этап 1 не включает создание Spring Boot приложения.

| № | Объём | Проверяемый результат |
| --- | --- | --- |
| 1 | Безопасно обновить backend-ветку и зафиксировать решения | Свежая база ветки, согласованные со стороны backend документы для передачи другу |
| 2 | Maven Wrapper, Spring Boot, конфигурация, PostgreSQL, Flyway, ошибки | Проверенные версии; запуск приложения; миграции на пустой БД |
| 3 | Аккаунты и регистрация | Хеш пароля, валидация, конкурентная уникальность email |
| 4 | Сессии, вход, выход, CSRF, текущий пользователь — реализовано | Проверены ротация/инвалидирование, оба срока жизни, cookie/CSRF и перезапуск JAR |
| 5 | Список, поиск и создание предметов — реализовано | Проверены пагинация, оформление, идемпотентность, гонки и изоляция аккаунтов |
| 6 | Получение, изменение и удаление пустого предмета — реализовано | Проверены владелец, версии, гонки и запрет удаления при FK-ссылках; реальные материалы — этап 8 |

| 9 | PDF и страницы текста | Текстовый/повреждённый PDF, скан, пределы ресурсов, проверка изоляции |

| 13 | Полный сценарий и подготовка пилота | Сквозная проверка с UI, удаления, лимитов и восстановления резервной копии |

## Проверки и отложенные вопросы

Тесты добавляются вместе с функциями: чужие данные, ограничения БД, CSRF,
параллельные запросы, квоты, PDF, ошибки R2/ИИ, перезапуски и сохранность результатов.
Для интеграционных проверок нужен настоящий PostgreSQL; Testcontainers предпочтителен
при доступном Docker. Подмены внешних сервисов контролируемы и явно обозначены.
CI добавляется с реальными командами проверок, без фиктивного успешного workflow.
Отсутствие Docker, сети или credentials отражается в отчёте о невыполненных проверках.

До выбора хостинга проверяем память JVM и обработки PDF, холодный запуск,
приостановку приложения, фоновые операции, лимиты HTTP и соединений,
постоянное хранение PostgreSQL, резервные копии и восстановление.
Бесплатный/пробный тариф не означает бесплатность и безлимитность всей системы.

Остаются отложенными: версии ещё не подключённых библиотек; хостинг; ИИ-провайдер и модель;
числовые квоты, таймауты и бюджет; оценка стоимости хеширования на хостинге;
частотные лимиты, механизм допуска пилота и подтверждение email; техническая изоляция PDF;
метрики прогресса и дневная временная зона; детали следующих API и сроки хранения.
Ранее предложенные 10/50 МиБ — исходные ориентиры, не утверждённые квоты.
До этапа загрузки нужно согласовать точный лимит в байтах, поле `title`, полный объект
материала, состояния и ответ загрузки. Контракт PATCH и конфликт версий дополнены на этапе 6;
frontend-разработчику нужно подтвердить интеграцию нового version и ошибок.
Frontend также попросил повторно подтвердить удаление истории попыток вместе с материалом.
Исходное решение пользователя сохранено; новую политику без обсуждения не вводим.

После первого законченного сценария: карточки с событиями повторения, чат с источниками,
расширенный кабинет, изменение/восстановление пароля и удаление аккаунта.
OCR, аудио, платежи, подписки, социальные функции и совместная работа не добавляются
без отдельного обсуждения. Незавершённые части контракта согласуются до их реализации.
