## Общие правила

- Базовый путь `/api/v1`; все пути ниже приводятся относительно него.
- JSON, query и multipart-поля — camelCase; SQL-поля — snake_case.
- Идентификаторы объектов — UUID сервера, передаваемые строками. Demo-id не задают формат.
- Время — ISO 8601 UTC, например `2026-09-27T10:00:00Z`.
- JSON-запросы: `Content-Type: application/json`; загрузка PDF — multipart/form-data.
- Успех: `{ "data": ... }`; список дополнительно содержит `meta`.
  Ответ `204` не имеет тела: HTTP-клиент не вызывает для него JSON-парсер.
- Ошибка: `error.code`, `error.message`, `error.fieldErrors`.
  Код стабилен для обработки программой; fieldErrors — объект строк по именам полей,
  для общей ошибки он пуст. Message предназначен пользователю.
- Неизвестные поля тела, неверные типы и недопустимый null дают `422 VALIDATION_FAILED`.
- Владельца backend определяет из сессии, включая повторы с Idempotency-Key.
  Чужой и отсутствующий приватный объект возвращают одинаковый `404`.
- Приватные ответы, CSRF и подписанные ссылки используют `Cache-Control: no-store`.
- SQL, стек исключения, системные пути, пароли, cookie и секреты сервисов не выдаются.

## Cookie, CSRF и CORS

Сессии PostgreSQL обслуживает Spring Session JDBC. Cookie `STUDYMATE_SESSION`: HttpOnly, Secure по умолчанию,
SameSite=Lax, Path=/, без общего Domain. После входа идентификатор сессии меняется,
после выхода сессия инвалидируется и cookie удаляется. Срок бездействия — 30 минут,
абсолютный срок — 12 часов после успешного входа (для анонимной сессии — от создания).
Повторный успешный вход начинает новый абсолютный срок; обычные запросы его не продлевают.
HTTP без Secure допускается только в явно выбранном профиле `local`.
JWT и session id в localStorage не используются.

Целевой production — единый origin frontend/API; локально нужен Vite proxy для `/api`.
Backend CORS не включает; пример proxy и запуска — [backend/README.md](../backend/README.md).
В исходной версии этапа 7 (PR #18) Vite proxy уже добавлен: frontend и backend используют
127.0.0.1. Исходники frontend backend-этапы не меняют; UI проверяется отдельно.
`VITE_API_BASE_URL=/api/v1` — публичная настройка.
Для разных origins, если они понадобятся, разрешаются конкретный origin frontend,
credentials и необходимые методы/заголовки, включая Content-Type, X-CSRF-TOKEN,
Idempotency-Key. OPTIONS обрабатывается до проверки сессии. Произвольный origin
не допускается; клиент использует `credentials: "include"`.
Если выбранное размещение окажется cross-site, одной настройки CORS недостаточно:
политику cookie и ограничения браузера нужно отдельно проверить до интеграции.
Совместимость такого размещения с выбранным SameSite=Lax сейчас не обещается.

Протокол браузера:

1. Получить `GET /auth/csrf` с cookie; token и headerName хранить в памяти страницы.
2. Получить `GET /auth/me`; при 401 показать вход.
3. В POST/PATCH/DELETE передавать CSRF-заголовок, включая register/login/logout
   и будущий multipart. Не помещать токен в URL.
4. После успешного входа и выхода получить свежий CSRF. После обновления страницы
   заново выполнить инициализацию.
5. При потере сессии POST может получить `403 CSRF_INVALID` раньше 401.
   Проверить /auth/me, сохранить ввод и предложить вход при необходимости.
   Если сессия действует, обновить CSRF. Создание не повторять вслепую с новым ключом.

## Общие ошибки

| HTTP | error.code | Условие |
| --- | --- | --- |
| 400 | INVALID_REQUEST | Общая ошибка HTTP-запроса без более точного кода |
| 400 | MALFORMED_JSON | Невозможно разобрать JSON |
| 400 | INVALID_QUERY | Неверные page/pageSize/q или неизвестный query-параметр |
| 400 | INVALID_ID | Идентификатор пути не является UUID |
| 400 | IDEMPOTENCY_KEY_REQUIRED / INVALID_IDEMPOTENCY_KEY | Нет обязательного ключа либо неверный формат |
| 401 | AUTHENTICATION_REQUIRED | Нет аутентифицированной сессии |
| 401 | INVALID_CREDENTIALS | Неверный email или пароль, без уточнения причины |

| 403 | ACCESS_DENIED | Общий отказ в доступе |
| 403 | REGISTRATION_CLOSED | Регистрация отключена для текущего режима запуска |
| 404 | SUBJECT_NOT_FOUND | Предмет отсутствует либо принадлежит другому пользователю |
| 404 | JOB_NOT_FOUND | Задание отсутствует либо принадлежит другому пользователю |
| 404 | NOT_FOUND | Отсутствующий маршрут или технический ресурс |
| 405 | METHOD_NOT_ALLOWED | Метод не поддерживается; сохраняется заголовок Allow |
| 406 | NOT_ACCEPTABLE | Запрошенный формат ответа не поддерживается |
| 409 | EMAIL_ALREADY_EXISTS | Нормализованный email занят |
| 409 | SUBJECT_TITLE_EXISTS | Название занято внутри текущего аккаунта |
| 409 | SUBJECT_VERSION_CONFLICT | Переданная версия предмета устарела или не совпадает с текущей |
| 409 | IDEMPOTENCY_KEY_REUSED | Завершённый ключ связан с другим запросом |
| 409 | REQUEST_IN_PROGRESS | Операция с этим ключом выполняется; есть Retry-After |
| 409 | SUBJECT_NOT_EMPTY | Связанные материалы препятствуют удалению предмета, включая обработку/очистку |
| 415 | UNSUPPORTED_MEDIA_TYPE | Неверный Content-Type |
| 413 | PAYLOAD_TOO_LARGE | PDF больше 26 214 400 байт или multipart-запрос больше 26 279 936 байт |
| 422 | VALIDATION_FAILED | Неверные значения/типы, отсутствующие или лишние поля |

| 500 | INTERNAL_ERROR | Неожиданная ошибка без раскрытия подробностей |

Retry-After задаётся числом секунд. Отсутствие HTTP-ответа не доказывает,
что операция не выполнена. Ниже перечислены основные исходы endpoints;
общие ошибки формата, CSRF, частоты и доступности также применяются, где нужно.

Пример ошибки формы, HTTP 422:

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Проверь поля формы.",
    "fieldErrors": {
      "title": "Название должно содержать от 2 до 60 символов.",
      "tone": "Выбери цвет из допустимых значений."
    }
  }
}
```

Общая ошибка без поля, HTTP 401:

```json
{
  "error": {
    "code": "AUTHENTICATION_REQUIRED",
    "message": "Войди в аккаунт.",
    "fieldErrors": {}
  }
}
```

## Модели и валидация

### User и формы аккаунта

User содержит только `id`, `email`, `displayName`.
Хеш пароля, служебные флаги и данные сессии не передаются.
Инициалы Header вычисляются frontend.

| Поле | Регистрация | Вход |
| --- | --- | --- |
| email | Обязательная строка; trim; синтаксически валидный адрес, максимум 254 символа | Те же правила формата |
| password | Обязательная строка, 12–128 единиц UTF-16; без trim/нормализации | Непустая строка, максимум 128 единиц UTF-16; без нормализации |
| displayName | Обязательная строка; trim; 1–60 единиц UTF-16 | Не принимается |

Нормализация email: trim по правилам JavaScript, затем lowercase(Locale.ROOT) в Java.
Она не зависит от locale машины и не удаляет точки и части после плюса.
В User возвращается этот нормализованный email. Конкурентную уникальность обеспечивает БД.
Имя также использует JS trim; внутренние пробелы сохраняются. Некорректные пары
UTF-16 отклоняются с 422 вместо молчаливой замены символов; NUL в имени недопустим.
Синтаксическая проверка не подтверждает владение ящиком. Подтверждение email и механизм
доступа к закрытому пилоту ещё не определены; документ не открывает публичную регистрацию.

### Subject и форма предмета

Допустимые коды проверены по актуальным
[SubjectFormModal.jsx](../frontend/src/components/subjects/SubjectFormModal.jsx)
и [subjectStorage.js](../frontend/src/services/subjectStorage.js)
в исходной версии этапа 7 `e12a63e0b27586675340e789a0dc6a33d3c8c737`.

| Поле создания | Правило |
| --- | --- |
| title | Обязательная строка; trim и схлопывание пробелов; длина после нормализации 2–60 |
| description | Необязательная строка; при отсутствии ""; trim; максимум 160 |
| icon | Обязательная строка: book, database, languages, code |
| tone | Обязательная строка: blue, purple, indigo, green |

Длины title/description измеряются в единицах UTF-16, как текущие JS length/maxLength.
Сохраняется семантика `trim().replace(/\s+/g, ' ')`; совместимость Java/JS проверена
на обычных и Unicode-пробелах. Ключ сравнения — Java lowercase(Locale.ROOT),
без зависимости от locale машины/БД. NUL и непарные UTF-16-суррогаты в title/description
недопустимы (422). Description может отсутствовать (тогда ""), но явный null недопустим.

БД обеспечивает `UNIQUE(owner_id, normalized_title)`. Одинаковые названия у разных
пользователей разрешены. Локальная проверка или предварительный SELECT не заменяют
это ограничение. При редактировании сам предмет не считается дубликатом.

| Поле ответа Subject | Семантика |
| --- | --- |
| id | UUID, созданный сервером |
| title, description, icon, tone | Нормализованные данные формы |
| lectureCount | Целое >= 0: материалы с сохранённым оригиналом, исключая удаляемые |
| progressPercent | Всегда null до определения настоящей метрики |
| createdAt | Серверное время создания в UTC |
| version | Положительное целое: 1 при создании, +1 после каждого успешного PATCH |

Клиент не передаёт id, userId/ownerId, lectureCount, progressPercent, createdAt,
старые lectures/progress или другие служебные поля: они отклоняются как лишние.
Новый предмет имеет lectureCount=0; null-прогресс не означает 0%.
На этапе 8 lectureCount вычисляется из материалов в состоянии stored в том же SQL-снимке,
что предметы; uploading/deleting не считаются. Счётчик не хранится в subjects.
В POST поле version не принимается. В PATCH оно обязательно как ожидаемая версия,
а новую версию назначает сервер. GET и список возвращают текущую версию.
Сохранённые ответы POST этапа 5 могут не содержать version: до редактирования нужен GET по UUID.
Демонстрационные предметы и статистика localStorage не импортируются в аккаунт.

## Первоочередные endpoints — статус указан у каждого

### GET /auth/csrf — РЕАЛИЗОВАН НА ЭТАПЕ 4

Вход не требуется, тела и query-параметров нет. При необходимости создаётся анонимная
сессия, cookie сохраняется браузером. Session id не возвращается в JSON.
Ответ 200:

```json
{
  "data": {
    "headerName": "X-CSRF-TOKEN",
    "token": "example-csrf-token"
  }
}
```

Токен в примере не предназначен для использования.
Повтор безопасен: клиент сохраняет последнее полученное значение.
Недоступность БД — 503; 429 пока целевой контракт до реализации лимитов.
Пользовательские данные не создаются, пагинации нет.

### POST /auth/register — РЕАЛИЗОВАН НА ЭТАПЕ 3

Вход не требуется; обязательны CSRF, JSON и разрешённая регистрация.
Регистрация закрыта по умолчанию, включая разработку. Явное включение:
`STUDYMATE_REGISTRATION_ENABLED=true`; это не отключает CSRF и не включает вход.
При валидном CSRF и корректном теле закрытый режим возвращает `403 REGISTRATION_CLOSED`.
Без CSRF возвращается `403 CSRF_INVALID` раньше обработки тела/флага регистрации.
Браузер получает токен через `/auth/csrf` и сохраняет cookie. Регистрация не меняет
сессию и не заменяет CSRF; после отдельного успешного входа токен нужно обновить.
Вымышленный пример запроса, пароль нельзя использовать для настоящего аккаунта:

```json
{
  "email": "student@example.com",
  "password": "Example-only-password-2026!",
  "displayName": "Айдана"
}
```

Ответ 201:

```json
{
  "data": {
    "id": "0b7393dd-d32b-4314-b43e-4637821ccdb9",
    "email": "student@example.com",
    "displayName": "Айдана"
  }
}
```

Автоматического входа нет: затем нужен POST /auth/login.
Основные ошибки: 422 VALIDATION_FAILED, 409 EMAIL_ALREADY_EXISTS
с fieldErrors.email, 403 CSRF_INVALID/REGISTRATION_CLOSED.
`429 RATE_LIMITED` остаётся частью целевого контракта; частотные лимиты ещё не реализованы
и должны появиться до открытия пилота. Этот этап не разрешает публичную регистрацию.
Idempotency-Key здесь не используется: повтор с занятым email даёт 409,
второй аккаунт не создаётся. Если ответ потерян, сначала пробуют вход.
Пароль/тело регистрации не логируются и не сохраняются в журнале идемпотентности.

### POST /auth/login — РЕАЛИЗОВАН НА ЭТАПЕ 4

Вход заранее не требуется; JSON и CSRF обязательны.

```json
{
  "email": "student@example.com",
  "password": "Example-only-password-2026!"
}
```

Ответ 200 — User в data, как в ответе регистрации, плюс session cookie через Set-Cookie.
Используются штатные механизмы Spring Security с заменой идентификатора сессии.
После успеха frontend получает новый CSRF и загружает данные вошедшего пользователя.
Ошибки: 401 INVALID_CREDENTIALS, 422 VALIDATION_FAILED, 403 CSRF_INVALID, 503 SERVICE_UNAVAILABLE.
429 остаётся целевым контрактом; частотные лимиты должны быть готовы до открытия пилота.
Неверный email и неверный пароль не различаются в сообщении.
Повтор может обновить сессию, но не создаёт аккаунт; сохранённого идемпотентного
ответа нет. При потере ответа сначала проверяют GET /auth/me.

### POST /auth/logout — РЕАЛИЗОВАН НА ЭТАПЕ 4

Тело отсутствует. Нужен CSRF; аутентифицированная сессия — если ещё существует.
Ответ 204 без тела: сессия инвалидируется, session cookie удаляется.
Frontend очищает приватные данные, отменяет запросы прежнего аккаунта
и получает CSRF для анонимной сессии.

Повтор уже выполненного выхода со свежим действующим CSRF возвращает 204.
Старый токен может дать 403 CSRF_INVALID; это не означает, что первый выход не состоялся.
Недоступность — 503. GET /auth/logout не выполняет выход.

### GET /auth/me — РЕАЛИЗОВАН НА ЭТАПЕ 4

Нужна аутентифицированная сессия. Тело и query-параметры отсутствуют; CSRF не нужен.
Ответ 200:

```json
{
  "data": {
    "id": "0b7393dd-d32b-4314-b43e-4637821ccdb9",
    "email": "student@example.com",
    "displayName": "Айдана"
  }
}
```

Без аутентификации — 401 AUTHENTICATION_REQUIRED.
DemoUser не подставляется. Повтор безопасен, пагинация не нужна.

### GET /subjects — РЕАЛИЗОВАН НА ЭТАПЕ 5

Нужна сессия; тело и CSRF не нужны.
Пример: `GET /api/v1/subjects?q=SQL&page=1&pageSize=20`.

| Параметр | Правило |
| --- | --- |
| q | Необязательная строка, trim, максимум 160 единиц UTF-16; пустая — без фильтра |
| page | Целое 1–9007199254740991 (безопасное целое JS), по умолчанию 1 |
| pageSize | Целое 1–100, по умолчанию 20 |

Поиск — регистронезависимая подстрока в title или description своих предметов.
Сравнение выполняется по Java lowercase(Locale.ROOT). Символы %, _ и обратный слеш
считаются текстом, не клиентскими SQL-шаблонами. q обрезается по JS trim, внутренние
пробелы q не схлопываются. Непарные UTF-16-суррогаты и NUL в q недопустимы.
Неизвестные и повторённые параметры дают 400 INVALID_QUERY. Числа задаются десятичными
цифрами, без знака, дроби, экспоненты и пробелов; пустое значение недопустимо.
Владелец ограничивается до поиска и пагинации. Порядок: createdAt DESC, id DESC.
total — число своих предметов после фильтра; pageSize — запрошенный размер страницы.
В одном ответе список и total читаются одним SQL-снимком. Между запросами
не обещается неизменяемый снимок списка.

200, data=[], total сохраняет размер отфильтрованного набора.
Ошибки: 400 INVALID_QUERY, 401 AUTHENTICATION_REQUIRED.
Повтор безопасен, но может показать изменившиеся данные.

### PATCH /subjects/{id} — РЕАЛИЗОВАН НА ЭТАПЕ 6

Нужны сессия владельца, CSRF и `Content-Type: application/json`. Query-параметров нет.
Idempotency-Key не применяется: защиту от повторной записи обеспечивает version.
Тело — обычный JSON-объект, не JSON Patch. Обязательны version и хотя бы одно из полей
title, description, icon, tone. Пропущенное поле сохраняет прежнее значение.

```json
{
  "version": 1,
  "title": "Базы данных: практика",
  "description": ""
}
```

Version — целое JSON-число 1–9007199254740991, полученное из актуального GET/list/PATCH.
Строка `"1"`, дробь `1.0`, null, отсутствие версии и тело только с version дают 422.
Правила title/description/icon/tone совпадают с созданием; любой явный null недопустим.
Пустая строка description очищает описание. Неизвестные/служебные поля дают 422.
Version из первоначального ответа POST может быть устаревшей: перед открытием формы
нужно выполнить GET /subjects/{id} и сохранить полученную версию вместе с исходными полями.

Успех — **200 `{ "data": Subject }`**, полный актуальный объект с новой версией.
Каждый принятый PATCH увеличивает version на 1, даже если нормализованные значения
совпадают с прежними. id, createdAt, владелец и вычисляемые поля не изменяются.
PATCH блокирует строку на время короткой транзакции: проверка владельца/версии,
изменение полей и увеличение версии выполняются вместе. Из двух конкурентных
запросов одной версии успешен только один. Уникальность названия гарантирует PostgreSQL.

Основные ошибки:

| HTTP | error.code | Что делает frontend |
| --- | --- | --- |
| 400 | INVALID_ID / INVALID_QUERY / MALFORMED_JSON | Исправляет формат запроса |
| 401 / 403 | AUTHENTICATION_REQUIRED / CSRF_INVALID | Сохраняет ввод, восстанавливает сессию/CSRF |
| 404 | SUBJECT_NOT_FOUND | Сообщает, что предмет недоступен; чужой UUID не раскрывается |
| 422 | VALIDATION_FAILED | Показывает fieldErrors или общую ошибку, оставляет форму открытой |
| 409 | SUBJECT_TITLE_EXISTS | Показывает fieldErrors.title; данные и версия не изменены |
| 409 | SUBJECT_VERSION_CONFLICT | Сохраняет черновик и предлагает загрузить актуальные данные |

Конфликт версии возвращает общую ошибку с пустым fieldErrors, без чужих данных.
Для доступного предмета версия проверяется раньше конфликта названия. Frontend не должен
автоматически подставлять новую версию и повторять PATCH: это может затереть чужие правки.
При потере ответа результат неизвестен: выполнить GET, сверить значения и предложить
пользователю решение. Повтор прежнего PATCH после успеха получит конфликт версии;
изменения второй раз не применятся. Отдельного кэша ответов PATCH нет.

### DELETE /subjects/{id} — РЕАЛИЗОВАН НА ЭТАПЕ 6

Нужны сессия владельца и CSRF. Тела, query-параметров, version и Idempotency-Key нет.
**204 без тела** — предмет удалён. **404 SUBJECT_NOT_FOUND** — UUID чужой, отсутствует
или уже удалён; повтор не имеет новых эффектов. **409 SUBJECT_NOT_EMPTY** — удаление
блокируется связанными материалами, включая обработку и незавершённую очистку.
Также применяются 400 INVALID_ID/INVALID_QUERY, 401 и 403 CSRF_INVALID.
DELETE удаляет текущий пустой предмет независимо от версии его названия/оформления.
При сетевом сбое можно проверить GET и повторить DELETE; 404 означает отсутствие доступного предмета.

На этапе 8 непустой предмет защищает реальная FK-связь materials с subjects.
Защита удаления использует отказ PostgreSQL при нарушении внешнего ключа (без CASCADE)
и проверена на явно тестовой таблице ссылок, включая состояния processing/deleting и гонки.
V7 добавляет non-deferrable FK (subject_id, owner_id) с ON DELETE RESTRICT и индекс:
он защищает и от чужого subject_id, и от удаления до завершения очистки.
UI не определяет возможность удаления по lectureCount.

Frontend убирает карточку после успеха, при 409 сохраняет её и объясняет причину;
при 404 обновляет список. Удаление не меняет сохранённый ответ первоначального POST.

## Idempotency-Key создания предмета

Реализовано на этапе 5. Клиент генерирует UUID для одной логической отправки формы.
Принимается один заголовок в формате 8-4-4-4-12 hex-символов, регистр не важен;
пустой/неверный/повторённый заголовок даёт INVALID_IDEMPOTENCY_KEY.
Это идентификатор запроса, а не клиентский id предмета.
Область: пользователь + HTTP-операция + ключ. Отпечаток вычисляется по нормализованным
полям; порядок JSON-полей незначим. Cookie/CSRF не входят в сохраняемый отпечаток.

| Ситуация | Ответ |
| --- | --- |
| Новый ключ, допустимое свободное название | Один предмет, 201 |
| Тот же ключ и запрос в течение 24 часов после успешной фиксации | Прежние 201, тело и Location; без нового предмета |
| Тот же завершённый ключ, другие нормализованные данные | 409 IDEMPOTENCY_KEY_REUSED |
| Первый запрос ещё выполняется | 409 REQUEST_IN_PROGRESS с Retry-After; повторить прежний ключ |
| Новый ключ, занятое название | 409 SUBJECT_TITLE_EXISTS |
| Такой же ключ у другого пользователя | Независимая операция его аккаунта |

Аутентификация, CSRF и формат проверяются до выдачи сохранённого результата.
Проверка существующего ключа предшествует повторной проверке занятости названия.
Предмет и успешный результат фиксируются одной транзакцией.
Результат хранится в PostgreSQL и переживает перезапуск приложения. Для текущего
REQUEST_IN_PROGRESS задаётся Retry-After: 1. Просроченные ответы очищаются раз в 15 минут
партиями до 1000 строк; срок 24 часа проверяется при запросе независимо от очистки.
422 и доменный конфликт названия не создают предмет и не закрепляют успешный результат.
После исправления формы клиент создаёт новый ключ.

При сетевой ошибке используется прежний ключ. После 24 часов гарантия повторения
ответа заканчивается: сначала сверяют список, затем явно решают о новом создании.
Повтор не восстанавливает уже удалённый предмет: сохранённый ответ описывает исходную
операцию, актуальность проверяется GET/списком. То же относится к уже изменённому предмету:
повтор возвращает исходные поля/версию и никогда не откатывает последующее редактирование.
При обновлении V4→V5 старые JSON-ответы остаются побайтово прежними, без добавления version.
Disabled-кнопка не заменяет эту защиту или ограничение уникальности.

Для будущих платных генераций ключ дополнительно сохраняется в задании на весь срок
хранения операции. Истечение краткосрочного кэша не разрешает повторный платный вызов;
полный контракт генераций уточняется на этапе 10.

| Поле | Семантика |
| --- | --- |
| id | Серверный UUID задания |
| type | Тип операции, назначенный внутренним модулем backend |
| status | queued / running / succeeded / failed / cancelled |
| attemptCount | Число начатых попыток; 0 до первого выполнения |
| maxAttempts | Зафиксированный лимит попыток; 1 для операций без автоматического повтора |
| createdAt, updatedAt | Время создания и последнего изменения записи UTC; обновляется также при продлении аренды |
| nextAttemptAt | Только queued: не раньше этого времени; это не обещанное время запуска |
| finishedAt | Время перехода в succeeded/failed/cancelled; иначе null |
| resultId | UUID результата при succeeded, если операция создаёт такой результат; иначе null |
| error | Только failed: объект code/message из разрешённого списка; иначе null |

Коды `data.error`: JOB_TEMPORARY_FAILURE, JOB_PROCESSING_FAILED, JOB_ATTEMPTS_EXHAUSTED,
JOB_LEASE_EXPIRED, JOB_OUTCOME_UNKNOWN, а также PDF-коды из раздела обработки ниже и
AI_UNAVAILABLE/AI_INVALID_RESPONSE/AI_OUTCOME_UNKNOWN для конспекта. Сообщения фиксированы сервером, без текста
исключений или ответа провайдера. В текущем механизме JOB_LEASE_EXPIRED хранится как
внутренняя причина повтора queued; наружу error выдаётся только для failed.
Это ошибка **самого задания**, а не HTTP-ошибка: чтение существующего failed всё равно даёт 200.
ResultId не даёт доступа к результату: отдельный endpoint повторно проверяет владельца.
Payload, ключ повтора, токен/срок аренды, ownerId и внутренние ошибки не выдаются.

Ошибки HTTP: 400 INVALID_ID/INVALID_QUERY; 401 AUTHENTICATION_REQUIRED;
404 JOB_NOT_FOUND (чужой и отсутствующий UUID не различаются); 503 SERVICE_UNAVAILABLE.
GET ничего не ставит в очередь, не возобновляет и не повторяет. POST/PATCH/DELETE jobs
не являются публичными endpoints; нет кнопки API «повторить неизвестную платную операцию».

Состояния и повторы:

- queued → running → succeeded/failed; известный временный сбой безопасной операции
  возвращает её в queued с задержкой. Просроченная аренда обрабатывается так же.
- По умолчанию не больше 3 начатых попыток, задержки 2, 4, 8… секунд с верхним пределом 60;
  при лимите 3 фактически доступны только задержки 2 и 4 секунды.
- При SAFE модуль гарантирует допустимость повтора. Для MANUAL после потери аренды,
  таймаута или неопределённого исключения состояние failed, код JOB_OUTCOME_UNKNOWN;
  автоматической новой попытки нет. Платные вызовы ещё не подключены.
- Внутренний модуль может отменить queued/running: cancelled — окончательное состояние.
  Клиентская отмена HTTP-запроса не отменяет задание.
- Прежняя попытка после утраты аренды не может сохранить результат. Внешний вызов
  мог уже выполниться: для внешних эффектов нужна отдельная идемпотентность адаптера.
- Повтор внутреннего enqueue с тем же владельцем/типом/ключом и payload возвращает тот же
  job id даже после завершения/отмены. Другой payload/политика — 409 IDEMPOTENCY_KEY_REUSED.
  Это запись на весь срок хранения задания, не 24-часовой кэш POST /subjects.

Frontend получает jobId при DELETE/process и processingJobId в Material. Опрос примерно раз в 2 секунды
без перекрытия запросов. Остановить опрос при succeeded/failed/cancelled, 404, выходе,
потере сессии или уходе со страницы. При сети/503 делать паузу, не создавать новую операцию.
После возврата на страницу читать прежний job id. Сон хостинга задерживает выполнение;
queued/running не означают непрерывную работу сервера. UI-проверка этапа 7 ещё не проводилась.

завершение старой генерации не восстанавливает удаляемые данные.

Задания различают queued/running/succeeded/failed/cancelled.
Полный контракт материалов этапа 8 приведён ниже; контракт конспекта этапа 10 — после страниц PDF.
Контракты генерации тестов и попыток завершены на этапах 11–12 ниже.
Локальная отправка файла отличается от подтверждённого сервером сохранения;
статус конспекта не подменяет статус PDF. Опрос ограничен по частоте и прекращается
при завершении, уходе со страницы, выходе или потере авторизации.
Сон хостинга может приостановить выполнение.

В первой версии у вопроса один правильный вариант. До завершения попытки
не выдаются correctOptionId, раскрывающие ответ объяснения или иной ключ.
Вариант должен принадлежать вопросу, вопрос — тесту; повтор questionId отклоняется.
Балл: 100 × правильные ответы / число вопросов, округление до двух знаков.
Пропуск даёт ноль. Сервер фиксирует начало и завершение; продолжительность —
прошедшее время, не доказательство непрерывной активности.
Повтор идентичных ответов возвращает сохранённый результат, другие валидные ответы после
завершения — 409 ATTEMPT_ALREADY_SUBMITTED; невалидный ввод остаётся 422.
Новая генерация не меняет прежние попытки.
Намеренное удаление материала следует отдельной принятой политике.
Пользователь повторно подтвердил удаление истории попыток вместе с материалом перед этапом 8.

После первого сценария: карточки и события повторения, чат с источниками и историей,
агрегаты кабинета, изменение/восстановление пароля и удаление аккаунта.
Маршруты и DTO пока не фиксируются. «Изученная лекция» и «план на день» требуют
определений; вымышленные проценты и события не подставляются.

## Материалы — реализованный контракт этапа 8

Все запросы требуют сессию. POST/PATCH/DELETE требуют `X-CSRF-TOKEN` в заголовке;
CSRF в multipart-поле или query не принимается. Ответы имеют `Cache-Control: no-store`.
ID — полный UUID; чужой и отсутствующий материал дают одинаковый 404 MATERIAL_NOT_FOUND.
Query допускается только у списка; неизвестные и повторные параметры отклоняются.

### Загрузка: POST /materials

`multipart/form-data` с одной частью `file`, одной текстовой `subjectId` и необязательной
текстовой `title`. Только эти части, без дублей. Browser FormData сам задаёт Content-Type
и boundary: apiClient не должен подставлять application/json или сериализовать FormData.
Заголовок `Idempotency-Key` — UUID одной логической загрузки; сохранить его для сетевого повтора.

Файл: `.pdf` без учёта регистра, MIME application/pdf, application/octet-stream или отсутствует.
Фактический размер 1–26 214 400 байт (25 МиБ), граница включена. Лимит всего multipart:
26 279 936 байт (файл + 64 КиБ служебных данных), заголовки одной части до 2048 байт,
текстовая часть title до 640 байт UTF-8. Проверяются сигнатура `%PDF-1.x` (0–7)
или `%PDF-2.0` и `%%EOF` в конце. Это базовая проверка контейнера, **не** подтверждение
извлекаемого текста/безопасности документа: повреждённые внутри, зашифрованные PDF и сканы
проверяются отдельной JVM обработчика этапа 9. JavaScript и действия PDF не исполняются.

Из имени файла убирается путь, края обрезаются; имя — не более 180 UTF-16, без управляющих
символов и непарных суррогатов. title после JS trim и схлопывания пробелов — 1–160 UTF-16.
Пропуск либо пустая/пробельная title: имя файла без последнего `.pdf`, нормализация и обрезка
до 160 без разрыва суррогатной пары; если имени нет, «Материал». Одинаковые названия допустимы.
Передавать строку `null` не нужно: это буквальное название, а не отсутствие поля.

Успех: **201 Created**, `Location: /api/v1/materials/{id}`, `{ "data": Material }`.
Ответ приходит после подтверждения PUT в R2 и фиксации PostgreSQL. В той же транзакции
создаётся задание извлечения текста; ждать его завершения для ответа загрузки не нужно.

```json
{
  "data": {
    "id": "3dfa4d7d-619d-4a97-9f09-a34d236e879b",
    "subjectId": "6f07410e-98f7-41a3-bfab-cbc387683fc1",
    "title": "Лекция 1",
    "fileName": "Лекция 1.pdf",
    "contentType": "application/pdf",
    "sizeBytes": 124800,
    "status": "stored",
    "processingStatus": "queued",
    "version": 1,
    "createdAt": "2026-09-29T10:00:00Z",
    "updatedAt": "2026-09-29T10:00:01Z",
    "deletionJobId": null,
    "processingJobId": "7e93afc3-28ee-44bc-b213-8e23d048a289",
    "pageCount": null,
    "textCharacters": null,
    "processingError": null
  }
}
```

Это все 16 полей DTO. `status`: uploading (оригинал не подтверждён), stored (сохранён),
deleting (очистка не завершена). После удаления GET возвращает 404; deleted не выдаётся
как объект. `processingStatus`: not_started / queued / running / ready / failed / cancelled.
Версия относится к переименованию и не увеличивается при обработке. `updatedAt` учитывает
метаданные, хранение и последнее изменение задания, включая heartbeat. deletionJobId задан у deleting;
ошибка очистки читается через GET jobs и не подменяется вымышленной ошибкой PDF.
`processingJobId` — текущее задание либо null. `pageCount` и `textCharacters` — число физических
страниц и UTF-16 символов после успешной обработки, до этого null (не ноль).
`processingError` только при failed: `{ "code": "PDF_NO_TEXT", "message": "..." }`; иначе null.
`ready` означает сохранённый текст, а не готовый конспект, тест или прогресс обучения.

Повтор того же ключа и тех же нормализованных subjectId/title/fileName/байтов возвращает
исходные 201/JSON/Location, без повторного PUT или списания квоты. После переименования
или обработки это старый ответ: свежие данные получать GET. Старый кэш загрузки этапа 8
может содержать 12 полей и not_started; миграция не переписывает его. Другие данные с тем же ключом — 409
IDEMPOTENCY_KEY_REUSED; незавершённый запрос — 409 REQUEST_IN_PROGRESS + Retry-After: 2.
После начала удаления/компенсации — 410 UPLOAD_ABORTED; ключ больше не создаёт материал.
Ключи загрузок сохраняются вместе с техническим журналом, автоматического истечения пока нет.

| Ошибка | Действие frontend |
| --- | --- |
| 400 IDEMPOTENCY_KEY_REQUIRED / INVALID_IDEMPOTENCY_KEY / INVALID_ID / INVALID_MULTIPART | Исправить запрос |
| 422 VALIDATION_FAILED | Показать fieldErrors.file/title/subjectId |
| 422 INVALID_PDF | Показать ошибку файла |
| 413 PAYLOAD_TOO_LARGE | Показать предел 25 МиБ, сохранить форму |
| 404 SUBJECT_NOT_FOUND | Обновить предметы; не переносить файл в другой предмет автоматически |
| 409 STORAGE_QUOTA_EXCEEDED | Обновить storage/usage и предложить освободить место |
| 429 UPLOAD_BUSY | На процесс допускается 2 загрузки; повторить позже с тем же ключом, Retry-After: 2 |
| 503 STORAGE_UNAVAILABLE | R2 выключен/недоступен; не показывать успешную загрузку |
| 503 UPLOAD_FAILED | Результат PUT/фиксации не подтверждён: обновить список/квоту, дождаться очистки резерва |
| 410 UPLOAD_ABORTED | Не повторять автоматически; новая попытка после сверки — отдельное действие с новым ключом |

### Чтение, список и переименование

GET /materials/{id}: 200 `{ "data": Material }`.
GET /materials: 200 `{ "data": [Material], "meta": { "page": 1, "pageSize": 20, "total": 3 } }`.
Необязательный subjectId ограничивает список собственным предметом; чужой/отсутствующий —
404 SUBJECT_NOT_FOUND. q — буквальная подстрока нормализованного title, trim/lowercase,
не более 160 UTF-16. page 1–9007199254740991, pageSize 1–100 (по умолчанию 1 и 20).
Порядок createdAt DESC, id DESC. Включены uploading/deleting для восстановления интерфейса
после потери ответа; удалённые отсутствуют. Пустая/выходящая за конец страница возвращает
пустой data и настоящий total, всё из одного SQL-снимка.

PATCH /materials/{id}: JSON `{ "title": "Новое название", "version": 1 }`, оба поля обязательны,
явный null и неизвестные поля недопустимы. Версия — целое 1–9007199254740991; правила title
те же 1–160, но пустая строка при PATCH недопустима. Только stored. Успех 200 с полным Material,
версия увеличивается даже при no-op. 409 MATERIAL_VERSION_CONFLICT сохраняет введённый черновик
и предлагает загрузить актуальные данные; автоматической перезаписи нет.

### Квота, скачивание и удаление

GET /storage/usage: 200 `data` с usedBytes, reservedBytes, limitBytes=524288000,
maxUploadBytes=26214400. Доступно `limitBytes - usedBytes - reservedBytes`.
usedBytes включает сохранённые оригиналы до завершения удаления; reservedBytes включает
неподтверждённые загрузки и их компенсацию. Квоту проверяет сервер, а не счётчик клиента.

GET /materials/{id}/download: только stored, 200 `{ "data": { "url": "…", "expiresAt": "…" } }`.
Подписанная ссылка действует **60 секунд**, скачать может её обладатель; не сохранять и
не журналировать её. Оригинал отдаётся как attachment application/pdf с безопасным именем
material.pdf; для имени в UI использовать fileName. Локальный preview остаётся отдельным
сценарием: fetch PDF из R2 для встроенного preview потребует отдельно настроенного bucket CORS.
После истечения получить новую ссылку. Ранее выданная ссылка может действовать до удаления
объекта/истечения TTL. Для uploading/deleting: 409 MATERIAL_NOT_AVAILABLE.

DELETE /materials/{id}: cookie/CSRF, без тела, version и Idempotency-Key.
Frontend заранее предупреждает: **«Материал и связанные конспекты, тесты и история попыток
будут удалены»**. Пользователь эту политику подтвердил. Успех 202:
`{ "data": { "materialId": "UUID", "jobId": "UUID" } }`.
Повтор queued/running даёт тот же jobId. При failed/cancelled явный повтор DELETE создаёт
один новый job для прежнего материала. Пока deleting, новые переименования/скачивания
и обработка/чтение страниц запрещены, квота занята, предмет удалить нельзя.
Активное извлечение отменяется; его поздний результат не может записать страницы.
Редкая гонка с запуском новой обработки даёт 409 REQUEST_IN_PROGRESS и Retry-After: 1;
повторить тот же DELETE. Опрос GET /jobs/{jobId} примерно раз в 2 секунды
без перекрытия; остановить при terminal/404/logout/уходе со страницы. При succeeded обновить
материалы, предмет и квоту. Повтор после завершённого удаления — 404 MATERIAL_NOT_FOUND.
После неудачной или оборванной загрузки очистка может ждать до 5 минут от резервирования;
worker и сервер должны работать. Retry исчерпан — сохранить deleting и дать явную кнопку повтора.

Страницы и версии конспекта удаляются через ON DELETE CASCADE. Таблиц тестов/попыток ещё нет;
на следующих этапах они также обязаны ссылаться на material с ON DELETE CASCADE.

## Извлечение текста PDF — этап 9

Новый успешно загруженный PDF автоматически получает `material.extract_text` (SAFE).
Оригинал остаётся сохранённым, учитывается в квоте и lectureCount при любой ошибке парсера.
Материалы, созданные до V8, остаются `not_started`: миграция не запускает внешнюю работу.
GET материала, страниц или задания никогда не создаёт обработку.

Утверждённые включительные пределы: **200 страниц**, **100 000 UTF-16 символов на страницу**,
**1 000 000 на документ**, включая пробелы и переводы строк; **60 секунд** на дочернюю JVM
с **heap 256 МиБ**. Документ целиком отклоняется при превышении, частичный текст не публикуется.
OCR отсутствует. Документ без букв/цифр в текстовом слое даёт PDF_NO_TEXT; пустые и сканированные
страницы внутри текстового документа сохраняются с пустым текстом и исходными номерами.
Номера начинаются с 1, отражают физические страницы, не печатные подписи или PDF page labels.
NUL и некорректные суррогаты заменяются U+FFFD. Разметка/таблицы/порядок колонок могут теряться.

### POST /materials/{id}/process

Для старого материала либо явного повтора после failed/cancelled. Сессия, CSRF, UUID
`Idempotency-Key`; без query и тела, Content-Type не требуется. Чужой/отсутствующий материал:
404 MATERIAL_NOT_FOUND; uploading/deleting: 409 MATERIAL_NOT_AVAILABLE; выключенный R2: 503 STORAGE_UNAVAILABLE.

Успех **202**: `{ "data": { "materialId": "UUID", "jobId": "UUID" } }`.
Повтор того же ключа для того же материала возвращает прежний jobId на весь срок хранения
задания, включая failed/succeeded/cancelled; это не повторное выполнение. Для новой попытки
после ошибки frontend создаёт новый ключ. Другой материал с тем же ключом: 409 IDEMPOTENCY_KEY_REUSED.
Новый ключ при queued/running: 409 PROCESSING_IN_PROGRESS, Retry-After: 2; прочитать свежий Material
и продолжить опрос его processingJobId. Новый ключ при ready: 409 TEXT_ALREADY_EXTRACTED.
Отсутствующий/неверный ключ: 400 IDEMPOTENCY_KEY_REQUIRED/INVALID_IDEMPOTENCY_KEY;
тело: 400 INVALID_REQUEST; неизвестный query: 400 INVALID_QUERY.

Структурная ошибка, шифрование, отсутствие текста и превышение лимитов завершают job без
автоповтора. Временный сбой скачивания и потеря аренды допускают ограниченный SAFE-повтор
по правилам очереди. Фиксированная ошибка документа не исправляется повтором: нужен другой PDF.

| Код processingError / job.error | Значение |
| --- | --- |
| PDF_INVALID | Повреждённая/нечитаемая структура PDF |
| PDF_ENCRYPTED | Шифрование, в том числе с пустым паролем; нужна незашифрованная копия |
| PDF_NO_TEXT | Нет текстового слоя с буквами/цифрами; OCR не подключён |
| PDF_TOO_MANY_PAGES | Больше 200 физических страниц |
| PDF_TEXT_LIMIT | Превышен объём текста страницы или документа |
| PDF_TIMEOUT | Дочерняя JVM превысила 60 секунд |
| PDF_RESOURCE_LIMIT | Исчерпана разрешённая память JVM |
| PDF_WORKER_FAILED | Обработчик не вернул допустимый результат |
| PDF_ORIGINAL_MISMATCH | Размер или SHA-256 оригинала не совпал с записью загрузки |

Возможны также общие JOB_* ошибки очереди. Все сообщения фиксированы сервером; содержимое
PDF, пути, object key, ответ R2 и исключения не попадают в ошибки. `failed` читается с HTTP 200.

### GET /materials/{id}/pages

Сессия и владелец; только query `page` (1–9007199254740991, default 1) и `pageSize`
(1–100, default 20), каждое значение один раз. Это номер страницы **API-списка**, не номер PDF.
Текст отсортирован по `pageNumber`. Успех 200:

```json
{
  "data": [{ "pageNumber": 1, "text": "Текст первой страницы\n" }],
  "meta": { "page": 1, "pageSize": 20, "total": 1 }
}
```

`total` равен числу физических страниц, включая пустые. За концом списка — data=[] с прежним total.
Только stored+ready: остальные состояния обработки дают 409 TEXT_NOT_READY, uploading/deleting —
409 MATERIAL_NOT_AVAILABLE; чужой/удалённый/несуществующий UUID — 404 MATERIAL_NOT_FOUND.
Плохая пагинация/неизвестные или повторяющиеся параметры — 400 INVALID_QUERY.
Данные читаются из PostgreSQL и доступны при выключенном R2; повторная генерация не выполняется.
Frontend выводит текст как текстовые узлы, без HTML/исполнения команд из документа.

## Конспект (этап 10)

Маршруты `/api/v1/materials/{id}/summary` требуют сессию и владельца; POST/PATCH также CSRF.
Все операции работают с PostgreSQL, R2 для чтения конспекта не нужен. ИИ получает только
извлечённый текст выбранного PDF с физическими номерами страниц. Перед POST интерфейс
сообщает, что этот текст будет передан внешнему провайдеру OpenAI, ответ может содержать
ошибки, а запрос расходует API-баланс. Автоматической генерации при upload/GET нет.
`STUDYMATE_AI_PROVIDER=disabled` по умолчанию; `fake` допустим только в профиле `local`
и помечается `model=fake-local`. Реальный `openai` использует `gpt-6-luna` и `store=false`.

### POST /materials/{id}/summary

Без query и тела; заголовок `Idempotency-Key: <UUID>`. Материал должен быть `stored`,
PDF-текст — `ready`. Ответ **202**:

```json
{ "data": { "materialId": "11111111-1111-4111-8111-111111111111", "jobId": "22222222-2222-4222-8222-222222222222" } }
```

Задание `material.summary` имеет политику MANUAL: неопределённый результат платного вызова
не повторяется автоматически. Тот же ключ возвращает прежний jobId даже после завершения.
Новый ключ после завершения запускает новую генерацию; предыдущая версия остаётся доступной
до успешной записи новой. Одновременно для материала выполняется не более одного задания.
Ошибки: 400 INVALID_ID/IDEMPOTENCY_KEY_REQUIRED/INVALID_IDEMPOTENCY_KEY/INVALID_REQUEST,
401/403 для сессии/CSRF, 404 MATERIAL_NOT_FOUND, 409 MATERIAL_NOT_AVAILABLE/TEXT_NOT_READY/
SUMMARY_IN_PROGRESS/IDEMPOTENCY_KEY_REUSED, 503 AI_UNAVAILABLE. В POST без готового
провайдера задание не создаётся.

Для PDF до 200 страниц/1 000 000 символов текст обрабатывается последовательно фрагментами
до 100 000 символов (не более 15 вызовов модели); страницы не отбрасываются и не обрезаются.
Ответ каждого фрагмента проверяется по схеме, размеру и физическим номерам страниц.
Итоговые тезисы соединяются по порядку и содержат ссылки вида `(стр. 2)`.
Это ссылки на исходные страницы, а не доказательство фактической точности тезиса.

### GET /materials/{id}/summary

Без query; **200** после первого POST. Пример после завершения:

```json
{
  "data": {
    "materialId": "11111111-1111-4111-8111-111111111111",
    "status": "ready",
    "jobId": "22222222-2222-4222-8222-222222222222",
    "version": 1,
    "content": "- Основной тезис лекции (стр. 1)",
    "sourcePages": [1],
    "origin": "ai",
    "model": "gpt-6-luna",
    "inputTokens": 1200,
    "outputTokens": 100,
    "createdAt": "2026-10-01T00:00:00Z",
    "updatedAt": "2026-10-01T00:00:00Z",
    "error": null
  }
}
```

`status`: queued/running/ready/failed/cancelled. Пока первой версии нет,
`version/content/sourcePages/origin/model/inputTokens/outputTokens/createdAt` равны null.
При повторной генерации GET продолжает отдавать предыдущую сохранённую версию и показывает
состояние нового задания. При failed `error={code,message}`, а старый content сохраняется.
Дополнительно `GET /jobs/{jobId}` даёт стандартные состояние/ошибку задания. Ошибки jobs:
AI_UNAVAILABLE, AI_INVALID_RESPONSE, AI_OUTCOME_UNKNOWN; MANUAL также может дать
JOB_OUTCOME_UNKNOWN при утрате аренды. Для первого POST до запуска — 404 SUMMARY_NOT_FOUND;
чужой/удалённый материал — 404 MATERIAL_NOT_FOUND; удаляемый — 409 MATERIAL_NOT_AVAILABLE.

### PATCH /materials/{id}/summary

JSON `{"version":1,"content":"Исправленный конспект"}`. `version` — целое 1–9007199254740991,
`content` — непустой корректный Unicode до 100 000 UTF-16 символов, допускает переносы строк.
Успех **200** с тем же объектом, что GET, и увеличенной версией. Предыдущая версия остаётся
в БД; после ручной правки `origin=user`, `model=null`, `sourcePages=[]`, счётчики токенов null,
поскольку прежние машинные ссылки нельзя выдавать за подтверждение отредактированного текста.
Во время queued/running редактирование даёт 409 SUMMARY_IN_PROGRESS. Устаревшая версия —
409 SUMMARY_VERSION_CONFLICT; форма сохраняет введённый текст и предлагает загрузить
актуальную версию. Отсутствующий конспект — 404 SUMMARY_NOT_FOUND; неверное тело —
422 VALIDATION_FAILED. Неизвестные поля и null отклоняются по общему контракту JSON.

Удаление материала отменяет активное задание и каскадно удаляет все версии конспекта.
Завершение отменённого задания не может восстановить удалённый материал или конспект.

## Тесты — генерация и версии (этап 11)

Этап 11 создаёт ровно **10 вопросов, по 4 варианта, один правильный**. Настройка количества
и редактирование вопросов пока не реализованы. Прохождение, баллы и история добавлены этапом 12.
Тест строится по извлечённому тексту PDF, независимо от наличия и ручных правок конспекта.
Каждая успешная генерация создаёт новый `quizId` и возрастающую `version` внутри материала.
Существующие версии не перезаписываются. API тестов всегда скрывает правильный вариант,
его индекс, объяснение и страницы-источники ответа. Разбор доступен только у завершённой попытки.

Все маршруты проверяют сессию и владельца, имеют `Cache-Control: no-store`. Для POST нужен
CSRF. Текст выбранного PDF передаётся OpenAI, расходуется API-баланс; до явного POST интерфейс
сообщает об этом и о возможных ошибках в вопросах. GET ничего не генерирует и работает при
выключенном ИИ/R2. Провайдер и ключ те же, что у конспектов; `fake-local` — демонстрация.

### POST /materials/{id}/quizzes

Без query и тела. `Idempotency-Key` — один UUID на логическое действие. Нужны `stored` и
`processingStatus=ready`. Успех **202**:

```json
{ "data": { "materialId": "11111111-1111-4111-8111-111111111111", "jobId": "22222222-2222-4222-8222-222222222222" } }
```

Тип задания — `material.quiz`, политика MANUAL, одна попытка, предел 1200 секунд.
**При succeeded `resultId` содержит UUID конкретной версии теста (`quizId`), а не materialId.**
Опрос GET `/jobs/{jobId}` примерно раз в 2 секунды, без перекрытия, с остановкой при terminal,
404, потере сессии и уходе. После succeeded — GET `/quizzes/{resultId}` и обновление списка версий.

Повтор того же ключа возвращает прежний jobId, включая завершённое/ошибочное/отменённое задание;
запрос повторно не оплачивается. После завершения новый ключ явно запускает новую генерацию.
Одновременно у материала только одно queued/running задание теста; конспект и тест имеют разные
типы заданий. Сетевой повтор сохраняет ключ, автоматического повтора платного вызова нет.

Ошибки POST: 400 INVALID_ID, IDEMPOTENCY_KEY_REQUIRED, INVALID_IDEMPOTENCY_KEY, INVALID_QUERY,
INVALID_REQUEST; 401 AUTHENTICATION_REQUIRED; 403 CSRF_INVALID; 404 MATERIAL_NOT_FOUND;
409 MATERIAL_NOT_AVAILABLE, TEXT_NOT_READY, IDEMPOTENCY_KEY_REUSED;
409 QUIZ_IN_PROGRESS с Retry-After: 2; 503 AI_UNAVAILABLE (задание не создано).

Короткий PDF передаётся одним ограниченным запросом. Длинный текст до 1 млн UTF-16 символов
обрабатывается целиком фрагментами до 100 000 символов: до 15 запросов для внутренних тезисов
и один для теста, итого **не более 16**. Внутренние тезисы не заменяют сохранённый конспект.
Вопросы выбираются по полученным тезисам, поэтому охват каждого факта не гарантируется.
Проверяются количество/типы, уникальность формулировок и вариантов, длины, единственный индекс
ответа 0–3, непустое объяснение и существующие номера страниц. Проверка структуры не доказывает
фактическую точность. При нехватке материала провайдер может вернуть QUIZ_INSUFFICIENT_CONTENT;
частичный тест не сохраняется. Другие ошибки задания: AI_UNAVAILABLE, AI_INVALID_RESPONSE,
AI_OUTCOME_UNKNOWN, JOB_OUTCOME_UNKNOWN и общие JOB_* ошибки.

### GET /materials/{id}/quizzes

Query: `page` от 1 до 9007199254740991 (default 1), `pageSize` от 1 до 100 (default 20).
Параметры по одному; неизвестные/повторные/невалидные — 400 INVALID_QUERY. Порядок version DESC.
Чужой/отсутствующий материал — 404 MATERIAL_NOT_FOUND; uploading/deleting — 409 MATERIAL_NOT_AVAILABLE.
**200**, пример с одной сохранённой версией:

```json
{
  "data": [{
    "id": "33333333-3333-4333-8333-333333333333",
    "materialId": "11111111-1111-4111-8111-111111111111",
    "version": 1,
    "questionCount": 10,
    "model": "gpt-6-luna",
    "createdAt": "2026-10-02T00:00:00Z"
  }],
  "meta": {
    "page": 1,
    "pageSize": 20,
    "total": 1,
    "generation": {
      "status": "ready",
      "jobId": "22222222-2222-4222-8222-222222222222",
      "error": null
    }
  }
}
```

`meta.generation` относится к последнему заданию материала, независимо от страницы списка.
До первого POST: `data=[]`, total=0, `generation={status:"not_started",jobId:null,error:null}`.
Статусы: not_started / queued / running / ready / failed / cancelled. `ready` соответствует
job.status=succeeded. При failed: `error={code,message}`, HTTP остаётся 200. Список прежних версий
доступен во время новой генерации и после ошибки; не удалять его из UI. За концом списка — data=[].

### GET /quizzes/{id}

Без query; **200** `{ "data": Quiz }`. Полный набор полей Quiz:

| Поле | Тип / значение |
| --- | --- |
| id, materialId | UUID версии теста и исходного материала |
| version | Положительное целое, версия внутри материала |
| questionCount | 10 |
| model | gpt-6-luna или явный fake-local для разработки |
| createdAt | ISO 8601 UTC |
| questions | Ровно 10 объектов `{id,position,text,options}` |
| questions[].position | 1–10, порядок вопросов |
| questions[].options | Ровно 4 объекта `{id,position,text}`, position 1–4 |

ID вопросов и вариантов создаёт сервер. Порядок вариантов перемешивается один раз при сохранении
и остаётся стабильным при повторных GET. Ответы/объяснения/источники хранятся отдельно от публичного
DTO; не угадывать ключ по position/id и не считать балл на frontend. Для текста и вариантов нужны
обычные текстовые узлы, без исполнения HTML. Чужой/отсутствующий/удалённый тест — 404 QUIZ_NOT_FOUND;
при удалении материала — 409 MATERIAL_NOT_AVAILABLE. Неверный UUID — 400 INVALID_ID,
query — 400 INVALID_QUERY. PATCH/DELETE теста не реализованы. Попытки описаны ниже.

Удаление материала отменяет активное задание теста, затем каскадно удаляет все версии, вопросы
и варианты, попытки и выбранные ответы. Поздний результат не может их восстановить.
Попытка ссылается на конкретный quizId; новая генерация не меняет прошлую попытку.

## Попытки, результат и история (этап 12)

Все маршруты имеют префикс `/api/v1`, требуют cookie-сессию и проверяют владельца.
Оба POST требуют `X-CSRF-TOKEN`; все ответы — `Cache-Control: no-store`.
Это синхронные операции с PostgreSQL: **jobId и опрос задания не нужны**, ИИ не вызывается,
баланс OpenAI не расходуется. Сохранённые тесты можно проходить при выключенных ИИ/R2/workers.

Попытка относится к одному неизменяемому `quizId`, а не к «последней версии» материала.
Статусы только `in_progress` и `completed`, переход однонаправленный. Таймера, автоматического
завершения и сохранения промежуточного выбора на сервере нет. Новая попытка с новым ключом
разрешена, даже если прежняя ещё in_progress. Это тренировка: разбор ранее завершённой попытки
того же теста остаётся доступен; новый запуск не скрывает уже изученные ответы.

### DTO Attempt

POST начала, POST submit и GET отдельной попытки возвращают `{ "data": Attempt }`.
Все поля присутствуют; нулевые баллы отличаются от `null` незавершённой попытки.

| Поле | Тип / правило |
| --- | --- |
| id | UUID попытки |
| quizId, materialId | UUID версии теста и исходного материала |
| quizVersion | Положительное целое, версия теста внутри материала |
| status | in_progress / completed |
| questionCount | 10 |
| startedAt | ISO 8601 UTC, время создания на сервере |
| completedAt | ISO 8601 UTC или null до завершения |
| correctCount | Целое 0–10 или null до завершения |
| scorePercent | JSON number 0–100, округлённый до 2 знаков, или null до завершения |
| questions | 10 объектов `{id,position,text,options}` в сохранённом порядке, как в GET quiz |
| questions[].options | 4 объекта `{id,position,text}`; никаких полей правильности |
| review | null до завершения; после — 10 объектов Review, в порядке вопросов |

Объект Review:

```json
{
  "questionId": "44444444-4444-4444-8444-444444444444",
  "selectedOptionId": null,
  "correctOptionId": "55555555-5555-4555-8555-555555555555",
  "isCorrect": false,
  "explanation": "Объяснение из сохранённой версии теста.",
  "sourcePages": [1, 3]
}
```

`selectedOptionId=null` означает пропуск. `sourcePages` — физические страницы PDF, как при
генерации теста. Объяснение подготовлено ИИ при генерации и может содержать фактическую ошибку;
проверка попытки лишь сравнивает выбранный вариант с сохранённым ключом.
Тексты вопросов, вариантов и объяснений выводить текстовыми узлами без исполнения HTML.
В незавершённой попытке даже после других завершённых попыток этого теста `review=null`;
`correctOptionId`, `isCorrect`, объяснения и страницы ответа в ней не появляются.

### POST /quizzes/{id}/attempts

Без query и тела. Передать один `Idempotency-Key` в формате UUID. **201** с полным Attempt;
новая попытка имеет in_progress, completedAt/correctCount/scorePercent/review=null.
Время начала, владелец и число вопросов приходят от сервера.

Один ключ на логический запуск: сетевой повтор с тем же quizId/ключом не создаёт вторую
попытку и не меняет startedAt. Возвращается **текущее** состояние прежней попытки, также 201;
если она уже completed, ответ содержит сохранённый результат и разбор. Тот же ключ с другим
своим quizId даёт 409 IDEMPOTENCY_KEY_REUSED. Уникальность ключа действует внутри аккаунта
и этого endpoint на всё время хранения попытки. Новый ключ — отдельная попытка.
После удаления материала попытка и её ключ удаляются; старый quizId даёт 404 и не воссоздаётся.

### POST /attempts/{id}/submit

Без query. `Content-Type: application/json`. Idempotency-Key не требуется: повтор определяется
UUID попытки и нормализованным набором ответов. Единственное поле тела — `answers`:

```json
{
  "answers": [
    { "questionId": "44444444-4444-4444-8444-444444444444", "optionId": "55555555-5555-4555-8555-555555555555" },
    { "questionId": "66666666-6666-4666-8666-666666666666", "optionId": null }
  ]
}
```

- answers обязателен, массив от 0 до 10 объектов. `[]` завершает попытку с нулём баллов.
- questionId обязателен и должен принадлежать именно этой версии теста; повтор UUID,
  включая разный регистр, запрещён. optionId — UUID варианта этого вопроса либо null.
- Пропущенный вопрос, отсутствующий optionId и optionId=null равнозначны: пропуск, 0 баллов.
  Пустая строка, неверный UUID, null-элемент, лишние поля и неверные типы дают 422 VALIDATION_FAILED.
- Клиент не передаёт баллы, ключи, правильность, владельца или время. Всё сохраняется
  атомарно: по строке на каждый вопрос, результат и completed. Частичной сдачи нет.
- Балл = `round(100 × correctCount / questionCount, 2)`, половина округляется вверх.
  При 10 вопросах возможны 0, 10, …, 100. Неверный ответ и пропуск дают одинаковые 0 баллов.

Успех **200** с полным completed Attempt. При повторе порядок массива неважен; одинаковые
UUID независимо от регистра и разные формы пропуска дают тот же сохранённый результат,
включая первоначальное completedAt. Другой валидный набор после completed —
**409 ATTEMPT_ALREADY_SUBMITTED**, предыдущие данные остаются неизменны. Проверка формата
и принадлежности сохраняется и после completed: невалидный набор возвращает 422.
При потере ответа повторить те же выбранные ответы или выполнить GET попытки. После 409
получить сохранённый результат через GET; для другого прохождения начать новую попытку.

### GET /attempts/{id}

Без query, **200** с полным Attempt. Позволяет восстановить состояние после перезагрузки
страницы и открыть разбор completed. Для in_progress сервер хранит только начало и версию
теста; промежуточные выбранные варианты не восстанавливаются из этого API. GET не начинает
и не завершает попытку. Прошедшее время можно вычислить по startedAt/completedAt; это не
показатель непрерывной активности пользователя и не лимит сдачи.

### GET /attempts

**200** `{ "data": [AttemptInfo], "meta": { "page": 1, "pageSize": 20, "total": 0 } }`.
При отсутствии результатов data=[]; пример метаданных выше показывает пустую историю.
AttemptInfo содержит все первые 10 полей DTO Attempt: от id до scorePercent;
**questions и review отсутствуют**. Для разбора сделать отдельный GET по id.

| Query | Допустимое значение |
| --- | --- |
| page | Целое 1–9007199254740991, default 1 |
| pageSize | Целое 1–100, default 20 |
| materialId | Необязательный UUID, все версии тестов одного материала |
| quizId | Необязательный UUID конкретной версии |
| status | Необязательное in_progress / completed; без фильтра оба |

Фильтры объединяются через AND и применяются **до** count/пагинации вместе с owner.
Порядок startedAt DESC, id DESC. total относится ко всем совпавшим строкам, а не странице.
Чужие/отсутствующие UUID фильтров дают пустой список, не раскрывают существование ресурса.
Пустые/повторные/неизвестные/невалидные параметры — 400 INVALID_QUERY.
История не содержит попытки удаляемых материалов начиная с перехода материала в deleting.
Агрегаты progressPercent и показатели кабинета этим этапом не рассчитываются.

### Ошибки и удаление

| HTTP / code | Когда / действие |
| --- | --- |
| 400 INVALID_ID, INVALID_QUERY | Неверный UUID в пути или параметры запроса |
| 400 IDEMPOTENCY_KEY_REQUIRED, INVALID_IDEMPOTENCY_KEY | Нет ключа начала либо неверный/повторный заголовок |
| 400 INVALID_REQUEST | Тело в запросе начала попытки |
| 400 MALFORMED_JSON | Нечитаемый JSON submit или отсутствующее тело |
| 401 AUTHENTICATION_REQUIRED | Сессия отсутствует/истекла; восстановить вход |
| 403 CSRF_INVALID | Обновить CSRF и повторить с прежним ключом/ответами |
| 404 QUIZ_NOT_FOUND | Чужой/отсутствующий тест при начале |
| 404 ATTEMPT_NOT_FOUND | Чужая/отсутствующая попытка при чтении/submit |
| 409 MATERIAL_NOT_AVAILABLE | Материал удаляется; повтор start/submit тоже не возвращает данные |
| 409 IDEMPOTENCY_KEY_REUSED | Ключ начала уже использован для другого теста |
| 409 ATTEMPT_ALREADY_SUBMITTED | Другая валидная сдача после завершения; открыть сохранённый результат |
| 422 VALIDATION_FAILED | Неверная структура/ответы; fieldErrors может быть пустым, либо содержать answers/путь поля; попытка не меняется |

Подтверждённое удаление материала каскадно удаляет все версии тестов, **все завершённые и
незавершённые попытки и ответы**. Во время очистки прямые запросы дают 409, после — 404.
Frontend предупреждает об этом до DELETE материала. Новая генерация теста, в отличие от
удаления материала, сохраняет все прежние версии и результаты.
