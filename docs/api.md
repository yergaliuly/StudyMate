# Черновик контракта API — для совместного согласования

> Все запросы ниже ПЛАНИРУЮТСЯ. Ни один endpoint пока не реализован.
> Участник 2 уточняет контракт, участник 1 использует такие же поля в демонстрационных данных.
> Не менять названия полей молча. Сначала обновить этот документ в PR и согласовать обе стороны.

## Общие договорённости

Предлагаемый префикс: `/api/v1`. JSON-поля — `snake_case`, идентификаторы — строки,
время — ISO 8601 в UTC. Названия и пояснения интерфейс отображает по-русски.
Способ авторизации согласовать до реализации входа; предложена серверная cookie-сессия.
Клиентский `user_id` не является доказательством личности: владельца сервер берёт из сессии.

Успешный одиночный ответ: `{ "data": { ... } }`.
Список: `{ "data": [...], "meta": { "page": 1, "page_size": 20, "total": 3 } }`.
Ошибка: `{ "error": { "code": "FILE_TOO_LARGE", "message": "Файл превышает допустимый размер" } }`.
Не возвращать в ошибке SQL, секреты, системный путь или трассировку сервера.

## Минимальные запросы

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/auth/register` | Создать аккаунт |
| POST | `/auth/login` | Войти |
| POST | `/auth/logout` | Завершить сессию |
| GET | `/auth/me` | Текущий пользователь без пароля и секретов |
| GET | `/subjects` | Свои предметы |
| POST | `/subjects` | Создать предмет |
| GET | `/subjects/{id}` | Открыть свой предмет |
| PATCH | `/subjects/{id}` | Изменить название/описание |
| DELETE | `/subjects/{id}` | Удалить; поведение для непустого предмета согласовать |
| GET | `/materials?subject_id={id}` | Свои материалы предмета |
| POST | `/materials` | Multipart: `file` и `subject_id`; сервер проверяет владельца |
| GET | `/materials/{id}` | Метаданные и статус обработки |
| GET | `/materials/{id}/download` | Получить краткоживущий доступ после проверки владельца |
| DELETE | `/materials/{id}` | Удалить материал и учесть файл в R2 |
| GET | `/storage/usage` | `used_bytes`, `limit_bytes`, `max_upload_bytes` |
| POST | `/materials/{id}/summary` | Запустить генерацию; предлагается HTTP 202 и задание |
| GET | `/materials/{id}/summary` | Сохранённый конспект |
| POST | `/materials/{id}/quizzes` | Запустить создание теста; предлагается HTTP 202 и задание |
| GET | `/jobs/{id}` | Состояние своей генерации |
| POST | `/quizzes/{id}/attempts` | Создать попытку и получить вопросы без правильных ответов |
| POST | `/attempts/{id}/submit` | Проверить выбранные ответы на сервере |
| GET | `/attempts/{id}` | Свой результат после проверки |

Сначала реализовать вход и предметы, затем материалы, затем ИИ и тесты.
Историю, карточки и чат специфицировать на втором этапе, не выдавать черновые пути за готовые.

## Пример материала

Идентификаторы и значения ниже вымышлены.

```json
{
  "data": {
    "id": "material_17",
    "subject_id": "subject_3",
    "title": "Лекция 4. SQL-запросы",
    "original_name": "lecture_sql.pdf",
    "size_bytes": 245760,
    "status": "processing",
    "created_at": "2026-09-26T10:00:00Z"
  }
}
```

Предлагаемые состояния материала: `processing`, `ready`, `failed`.
`uploading` до появления записи — состояние frontend, а не подтверждённое серверное сохранение.
Временный download URL не является постоянным адресом материала и не заменяет его `id`.
Не возвращать секреты хранилища.

## Пример задания генерации

```json
{
  "data": {
    "id": "job_5",
    "material_id": "material_17",
    "kind": "summary",
    "status": "queued"
  }
}
```

Состояния: `queued`, `running`, `succeeded`, `failed`.
При успехе уточнить тип/идентификатор результата; при ошибке — безопасный код и сообщение.
Frontend прекращает опрос после завершения, выхода со страницы или ошибки авторизации;
ограничивает частоту опроса и не делает бесконечный цикл без задержки.

## Отправка попытки

```json
{
  "answers": [
    { "question_id": "question_1", "option_id": "option_b" },
    { "question_id": "question_2", "option_id": "option_a" }
  ]
}
```

До отправки попытки не отдавать клиенту `correct_option_id`, объяснение, раскрывающее ответ,
или вычисленный правильный вариант. Балл считает backend. Повторную отправку той же попытки
обрабатывать однозначно, не создавать дубли результатов из-за повторного клика.

## Перед первым интеграционным PR согласовать

Способ входа и выхода; поля форм; HTTP-коды; пагинацию; cookie/CSRF и локальный proxy;
допустимые размеры/типы файлов; удаление непустого предмета; формат теста и результата;
ограничения повторной генерации. Настоящие серверные проверки нельзя заменить клиентскими.
