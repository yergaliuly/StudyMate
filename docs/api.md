## Общие правила

- Базовый путь `/api/v1`; все пути ниже приводятся относительно него.
- JSON, query и multipart-поля — camelCase; SQL-поля — snake_case.
- Идентификаторы объектов — UUID сервера, передаваемые строками. Demo-id не задают формат.
- Время — ISO 8601 UTC, например `2026-09-27T10:00:00Z`.
- JSON-запросы: `Content-Type: application/json`; будущая загрузка файла — multipart.
- Успех: `{ "data": ... }`; список дополнительно содержит `meta`.
  Ответ `204` не имеет тела: HTTP-клиент не вызывает для него JSON-парсер.
- Ошибка: `error.code`, `error.message`, `error.fieldErrors`.
  Код стабилен для обработки программой; fieldErrors — объект строк по именам полей,
  для общей ошибки он пуст. Message предназначен пользователю.
- Неизвестные поля тела, неверные типы и недопустимый null дают `422 VALIDATION_FAILED`.
- Владельца backend определяет из сессии, включая повторы с Idempotency-Key.
  Чужой и отсутствующий приватный объект возвращают одинаковый `404`.
- Приватные ответы, CSRF и подписанные ссылки используют `Cache-Control: no-store`.
- SQL, стек исключения, системные пути, пароли, cookie и секреты сервисов не выдаются.

## Cookie, CSRF и CORS

Сессии PostgreSQL обслуживает Spring Session JDBC. Cookie `STUDYMATE_SESSION`: HttpOnly, Secure по умолчанию,
SameSite=Lax, Path=/, без общего Domain. После входа идентификатор сессии меняется,
после выхода сессия инвалидируется и cookie удаляется. Срок бездействия — 30 минут,
абсолютный срок — 12 часов после успешного входа (для анонимной сессии — от создания).
Повторный успешный вход начинает новый абсолютный срок; обычные запросы его не продлевают.
HTTP без Secure допускается только в явно выбранном профиле `local`.
JWT и session id в localStorage не используются.

Целевой production — единый origin frontend/API; локально нужен Vite proxy для `/api`.
Backend CORS не включает; пример proxy и запуска — [backend/README.md](../backend/README.md).
В текущем frontend proxy ещё нужно добавить; исходники frontend backend-этапы не меняют.
`VITE_API_BASE_URL=/api/v1` — публичная настройка.
Для разных origins, если они понадобятся, разрешаются конкретный origin frontend,
credentials и необходимые методы/заголовки, включая Content-Type, X-CSRF-TOKEN,
Idempotency-Key. OPTIONS обрабатывается до проверки сессии. Произвольный origin
не допускается; клиент использует `credentials: "include"`.
Если выбранное размещение окажется cross-site, одной настройки CORS недостаточно:
политику cookie и ограничения браузера нужно отдельно проверить до интеграции.
Совместимость такого размещения с выбранным SameSite=Lax сейчас не обещается.

Протокол браузера:

1. Получить `GET /auth/csrf` с cookie; token и headerName хранить в памяти страницы.
2. Получить `GET /auth/me`; при 401 показать вход.
3. В POST/PATCH/DELETE передавать CSRF-заголовок, включая register/login/logout
   и будущий multipart. Не помещать токен в URL.
4. После успешного входа и выхода получить свежий CSRF. После обновления страницы
   заново выполнить инициализацию.
5. При потере сессии POST может получить `403 CSRF_INVALID` раньше 401.
   Проверить /auth/me, сохранить ввод и предложить вход при необходимости.
   Если сессия действует, обновить CSRF. Создание не повторять вслепую с новым ключом.

## Общие ошибки

| HTTP | error.code | Условие |
| --- | --- | --- |
| 400 | INVALID_REQUEST | Общая ошибка HTTP-запроса без более точного кода |
| 400 | MALFORMED_JSON | Невозможно разобрать JSON |
| 400 | INVALID_QUERY | Неверные page/pageSize/q или неизвестный query-параметр |
| 400 | INVALID_ID | Идентификатор пути не является UUID |
| 400 | IDEMPOTENCY_KEY_REQUIRED / INVALID_IDEMPOTENCY_KEY | Нет обязательного ключа либо неверный формат |
| 401 | AUTHENTICATION_REQUIRED | Нет аутентифицированной сессии |
| 401 | INVALID_CREDENTIALS | Неверный email или пароль, без уточнения причины |
| 403 | CSRF_INVALID | Отсутствует действующий CSRF-токен |
| 403 | ACCESS_DENIED | Общий отказ в доступе |
| 403 | REGISTRATION_CLOSED | Регистрация отключена для текущего режима запуска |
| 404 | SUBJECT_NOT_FOUND | Предмет отсутствует либо принадлежит другому пользователю |
| 404 | NOT_FOUND | Отсутствующий маршрут или технический ресурс |
| 405 | METHOD_NOT_ALLOWED | Метод не поддерживается; сохраняется заголовок Allow |
| 406 | NOT_ACCEPTABLE | Запрошенный формат ответа не поддерживается |
| 409 | EMAIL_ALREADY_EXISTS | Нормализованный email занят |
| 409 | SUBJECT_TITLE_EXISTS | Название занято внутри текущего аккаунта |
| 409 | IDEMPOTENCY_KEY_REUSED | Завершённый ключ связан с другим запросом |
| 409 | REQUEST_IN_PROGRESS | Операция с этим ключом выполняется; есть Retry-After |
| 409 | SUBJECT_NOT_EMPTY | Предмет содержит материалы; будущий DELETE |
| 415 | UNSUPPORTED_MEDIA_TYPE | Неверный Content-Type |
| 413 | PAYLOAD_TOO_LARGE | Превышен лимит запроса; лимит загрузки PDF ещё не согласован |
| 422 | VALIDATION_FAILED | Неверные значения/типы, отсутствующие или лишние поля |
| 429 | RATE_LIMITED | Ограничение частоты; есть Retry-After |
| 503 | SERVICE_UNAVAILABLE | Временная недоступность сервиса |
| 500 | INTERNAL_ERROR | Неожиданная ошибка без раскрытия подробностей |

Retry-After задаётся числом секунд. Отсутствие HTTP-ответа не доказывает,
что операция не выполнена. Ниже перечислены основные исходы endpoints;
общие ошибки формата, CSRF, частоты и доступности также применяются, где нужно.

Пример ошибки формы, HTTP 422:

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Проверь поля формы.",
    "fieldErrors": {
      "title": "Название должно содержать от 2 до 60 символов.",
      "tone": "Выбери цвет из допустимых значений."
    }
  }
}
```

Общая ошибка без поля, HTTP 401:

```json
{
  "error": {
    "code": "AUTHENTICATION_REQUIRED",
    "message": "Войди в аккаунт.",
    "fieldErrors": {}
  }
}
```

## Модели и валидация

### User и формы аккаунта

User содержит только `id`, `email`, `displayName`.
Хеш пароля, служебные флаги и данные сессии не передаются.
Инициалы Header вычисляются frontend.

| Поле | Регистрация | Вход |
| --- | --- | --- |
| email | Обязательная строка; trim; синтаксически валидный адрес, максимум 254 символа | Те же правила формата |
| password | Обязательная строка, 12–128 единиц UTF-16; без trim/нормализации | Непустая строка, максимум 128 единиц UTF-16; без нормализации |
| displayName | Обязательная строка; trim; 1–60 единиц UTF-16 | Не принимается |

Нормализация email: trim по правилам JavaScript, затем lowercase(Locale.ROOT) в Java.
Она не зависит от locale машины и не удаляет точки и части после плюса.
В User возвращается этот нормализованный email. Конкурентную уникальность обеспечивает БД.
Имя также использует JS trim; внутренние пробелы сохраняются. Некорректные пары
UTF-16 отклоняются с 422 вместо молчаливой замены символов; NUL в имени недопустим.
Синтаксическая проверка не подтверждает владение ящиком. Подтверждение email и механизм
доступа к закрытому пилоту ещё не определены; документ не открывает публичную регистрацию.

### Subject и форма предмета

Допустимые коды проверены по актуальным
[SubjectFormModal.jsx](../frontend/src/components/subjects/SubjectFormModal.jsx)
и [subjectStorage.js](../frontend/src/services/subjectStorage.js)
в исходной версии этапа 5 `50f535a8fb4ea8906339a2c7bb231b8b0c32cca6`.

| Поле создания | Правило |
| --- | --- |
| title | Обязательная строка; trim и схлопывание пробелов; длина после нормализации 2–60 |
| description | Необязательная строка; при отсутствии ""; trim; максимум 160 |
| icon | Обязательная строка: book, database, languages, code |
| tone | Обязательная строка: blue, purple, indigo, green |

Длины title/description измеряются в единицах UTF-16, как текущие JS length/maxLength.
Сохраняется семантика `trim().replace(/\s+/g, ' ')`; совместимость Java/JS проверена
на обычных и Unicode-пробелах. Ключ сравнения — Java lowercase(Locale.ROOT),
без зависимости от locale машины/БД. NUL и непарные UTF-16-суррогаты в title/description
недопустимы (422). Description может отсутствовать (тогда ""), но явный null недопустим.

БД обеспечивает `UNIQUE(owner_id, normalized_title)`. Одинаковые названия у разных
пользователей разрешены. Локальная проверка или предварительный SELECT не заменяют
это ограничение. При будущем редактировании сам предмет не считается дубликатом.

| Поле ответа Subject | Семантика |
| --- | --- |
| id | UUID, созданный сервером |
| title, description, icon, tone | Нормализованные данные формы |
| lectureCount | Целое >= 0: материалы с сохранённым оригиналом, исключая удаляемые |
| progressPercent | Всегда null до определения настоящей метрики |
| createdAt | Серверное время создания в UTC |

Клиент не передаёт id, userId/ownerId, lectureCount, progressPercent, createdAt,
старые lectures/progress или другие служебные поля: они отклоняются как лишние.
Новый предмет имеет lectureCount=0; null-прогресс не означает 0%.
На этапе 5 материалов ещё нет, поэтому lectureCount всех предметов равен 0;
счётчик не хранится в subjects, его запрос будет дополнен при появлении материалов.
Демонстрационные предметы и статистика localStorage не импортируются в аккаунт.

## Первоочередные endpoints — статус указан у каждого

### GET /auth/csrf — РЕАЛИЗОВАН НА ЭТАПЕ 4

Вход не требуется, тела и query-параметров нет. При необходимости создаётся анонимная
сессия, cookie сохраняется браузером. Session id не возвращается в JSON.
Ответ 200:

```json
{
  "data": {
    "headerName": "X-CSRF-TOKEN",
    "token": "example-csrf-token"
  }
}
```

Токен в примере не предназначен для использования.
Повтор безопасен: клиент сохраняет последнее полученное значение.
Недоступность БД — 503; 429 пока целевой контракт до реализации лимитов.
Пользовательские данные не создаются, пагинации нет.

### POST /auth/register — РЕАЛИЗОВАН НА ЭТАПЕ 3

Вход не требуется; обязательны CSRF, JSON и разрешённая регистрация.
Регистрация закрыта по умолчанию, включая разработку. Явное включение:
`STUDYMATE_REGISTRATION_ENABLED=true`; это не отключает CSRF и не включает вход.
При валидном CSRF и корректном теле закрытый режим возвращает `403 REGISTRATION_CLOSED`.
Без CSRF возвращается `403 CSRF_INVALID` раньше обработки тела/флага регистрации.
Браузер получает токен через `/auth/csrf` и сохраняет cookie. Регистрация не меняет
сессию и не заменяет CSRF; после отдельного успешного входа токен нужно обновить.
Вымышленный пример запроса, пароль нельзя использовать для настоящего аккаунта:

```json
{
  "email": "student@example.com",
  "password": "Example-only-password-2026!",
  "displayName": "Айдана"
}
```

Ответ 201:

```json
{
  "data": {
    "id": "0b7393dd-d32b-4314-b43e-4637821ccdb9",
    "email": "student@example.com",
    "displayName": "Айдана"
  }
}
```

Автоматического входа нет: затем нужен POST /auth/login.
Основные ошибки: 422 VALIDATION_FAILED, 409 EMAIL_ALREADY_EXISTS
с fieldErrors.email, 403 CSRF_INVALID/REGISTRATION_CLOSED.
`429 RATE_LIMITED` остаётся частью целевого контракта; частотные лимиты ещё не реализованы
и должны появиться до открытия пилота. Этот этап не разрешает публичную регистрацию.
Idempotency-Key здесь не используется: повтор с занятым email даёт 409,
второй аккаунт не создаётся. Если ответ потерян, сначала пробуют вход.
Пароль/тело регистрации не логируются и не сохраняются в журнале идемпотентности.

### POST /auth/login — РЕАЛИЗОВАН НА ЭТАПЕ 4

Вход заранее не требуется; JSON и CSRF обязательны.

```json
{
  "email": "student@example.com",
  "password": "Example-only-password-2026!"
}
```

Ответ 200 — User в data, как в ответе регистрации, плюс session cookie через Set-Cookie.
Используются штатные механизмы Spring Security с заменой идентификатора сессии.
После успеха frontend получает новый CSRF и загружает данные вошедшего пользователя.
Ошибки: 401 INVALID_CREDENTIALS, 422 VALIDATION_FAILED, 403 CSRF_INVALID, 503 SERVICE_UNAVAILABLE.
429 остаётся целевым контрактом; частотные лимиты должны быть готовы до открытия пилота.
Неверный email и неверный пароль не различаются в сообщении.
Повтор может обновить сессию, но не создаёт аккаунт; сохранённого идемпотентного
ответа нет. При потере ответа сначала проверяют GET /auth/me.

### POST /auth/logout — РЕАЛИЗОВАН НА ЭТАПЕ 4

Тело отсутствует. Нужен CSRF; аутентифицированная сессия — если ещё существует.
Ответ 204 без тела: сессия инвалидируется, session cookie удаляется.
Frontend очищает приватные данные, отменяет запросы прежнего аккаунта
и получает CSRF для анонимной сессии.

Повтор уже выполненного выхода со свежим действующим CSRF возвращает 204.
Старый токен может дать 403 CSRF_INVALID; это не означает, что первый выход не состоялся.
Недоступность — 503. GET /auth/logout не выполняет выход.

### GET /auth/me — РЕАЛИЗОВАН НА ЭТАПЕ 4

Нужна аутентифицированная сессия. Тело и query-параметры отсутствуют; CSRF не нужен.
Ответ 200:

```json
{
  "data": {
    "id": "0b7393dd-d32b-4314-b43e-4637821ccdb9",
    "email": "student@example.com",
    "displayName": "Айдана"
  }
}
```

Без аутентификации — 401 AUTHENTICATION_REQUIRED.
DemoUser не подставляется. Повтор безопасен, пагинация не нужна.

### GET /subjects — РЕАЛИЗОВАН НА ЭТАПЕ 5

Нужна сессия; тело и CSRF не нужны.
Пример: `GET /api/v1/subjects?q=SQL&page=1&pageSize=20`.

| Параметр | Правило |
| --- | --- |
| q | Необязательная строка, trim, максимум 160 единиц UTF-16; пустая — без фильтра |
| page | Целое 1–9007199254740991 (безопасное целое JS), по умолчанию 1 |
| pageSize | Целое 1–100, по умолчанию 20 |

Поиск — регистронезависимая подстрока в title или description своих предметов.
Сравнение выполняется по Java lowercase(Locale.ROOT). Символы %, _ и обратный слеш
считаются текстом, не клиентскими SQL-шаблонами. q обрезается по JS trim, внутренние
пробелы q не схлопываются. Непарные UTF-16-суррогаты и NUL в q недопустимы.
Неизвестные и повторённые параметры дают 400 INVALID_QUERY. Числа задаются десятичными
цифрами, без знака, дроби, экспоненты и пробелов; пустое значение недопустимо.
Владелец ограничивается до поиска и пагинации. Порядок: createdAt DESC, id DESC.
total — число своих предметов после фильтра; pageSize — запрошенный размер страницы.
В одном ответе список и total читаются одним SQL-снимком. Между запросами
не обещается неизменяемый снимок списка.

Ответ 200:

```json
{
  "data": [
    {
      "id": "63e340c8-c145-4d0b-a648-464547a5fc01",
      "title": "Базы данных",
      "description": "SQL, таблицы и связи",
      "icon": "database",
      "tone": "blue",
      "lectureCount": 0,
      "progressPercent": null,
      "createdAt": "2026-09-27T10:00:00Z"
    }
  ],
  "meta": {
    "page": 1,
    "pageSize": 20,
    "total": 1
  }
}
```

Пустой аккаунт/поиск: 200, data=[], total=0. Страница за концом списка:
200, data=[], total сохраняет размер отфильтрованного набора.
Ошибки: 400 INVALID_QUERY, 401 AUTHENTICATION_REQUIRED.
Повтор безопасен, но может показать изменившиеся данные.

### POST /subjects — РЕАЛИЗОВАН НА ЭТАПЕ 5

Нужны сессия, CSRF, JSON и Idempotency-Key.
Пример заголовка: `Idempotency-Key: 773b6d14-d350-4c27-8db8-b3b1fdb5d159`.

```json
{
  "title": "Базы данных",
  "description": "SQL, таблицы и связи",
  "icon": "database",
  "tone": "blue"
}
```

Владелец берётся из сессии. Ответ 201 и
`Location: /api/v1/subjects/63e340c8-c145-4d0b-a648-464547a5fc01`:

```json
{
  "data": {
    "id": "63e340c8-c145-4d0b-a648-464547a5fc01",
    "title": "Базы данных",
    "description": "SQL, таблицы и связи",
    "icon": "database",
    "tone": "blue",
    "lectureCount": 0,
```

Ошибки: 400 для отсутствующего/неверного ключа, 401, 403 CSRF_INVALID,
422 VALIDATION_FAILED, 409 SUBJECT_TITLE_EXISTS/IDEMPOTENCY_KEY_REUSED/REQUEST_IN_PROGRESS.
Конкурентное нарушение уникальности в БД возвращает 409, а не 500:

```json
{
  "error": {
    "code": "SUBJECT_TITLE_EXISTS",
    "message": "Предмет с таким названием уже есть.",
    "fieldErrors": {
      "title": "Выбери другое название."
    }
  }
}
```

Возвращаемый Location задаёт адрес ресурса; получение по этому адресу появится
на этапе 6. Пока актуальный предмет можно найти в списке.

### GET /subjects/{id} — НЕ РЕАЛИЗОВАН (ЭТАП 6)

Нужны сессия и принадлежность предмета. Тело и query-параметры отсутствуют;
CSRF и Idempotency-Key не нужны. Ответ 200 — объект Subject в оболочке data,
точно той же структуры, что пример ответа POST /subjects выше.
Ошибки: 400 INVALID_ID, 401 AUTHENTICATION_REQUIRED,
404 SUBJECT_NOT_FOUND для чужого и отсутствующего UUID.
Повтор безопасен; пагинации нет. Материалы выдаются отдельным будущим запросом,
генерации при чтении не запускаются.

## Idempotency-Key создания предмета

Реализовано на этапе 5. Клиент генерирует UUID для одной логической отправки формы.
Принимается один заголовок в формате 8-4-4-4-12 hex-символов, регистр не важен;
пустой/неверный/повторённый заголовок даёт INVALID_IDEMPOTENCY_KEY.
Это идентификатор запроса, а не клиентский id предмета.
Область: пользователь + HTTP-операция + ключ. Отпечаток вычисляется по нормализованным
полям; порядок JSON-полей незначим. Cookie/CSRF не входят в сохраняемый отпечаток.

| Ситуация | Ответ |
| --- | --- |
| Новый ключ, допустимое свободное название | Один предмет, 201 |
| Тот же ключ и запрос в течение 24 часов после успешной фиксации | Прежние 201, тело и Location; без нового предмета |
| Тот же завершённый ключ, другие нормализованные данные | 409 IDEMPOTENCY_KEY_REUSED |
| Первый запрос ещё выполняется | 409 REQUEST_IN_PROGRESS с Retry-After; повторить прежний ключ |
| Новый ключ, занятое название | 409 SUBJECT_TITLE_EXISTS |
| Такой же ключ у другого пользователя | Независимая операция его аккаунта |

Аутентификация, CSRF и формат проверяются до выдачи сохранённого результата.
Проверка существующего ключа предшествует повторной проверке занятости названия.
Предмет и успешный результат фиксируются одной транзакцией.
Результат хранится в PostgreSQL и переживает перезапуск приложения. Для текущего
REQUEST_IN_PROGRESS задаётся Retry-After: 1. Просроченные ответы очищаются раз в 15 минут
партиями до 1000 строк; срок 24 часа проверяется при запросе независимо от очистки.
422 и доменный конфликт названия не создают предмет и не закрепляют успешный результат.
После исправления формы клиент создаёт новый ключ.

При сетевой ошибке используется прежний ключ. После 24 часов гарантия повторения
ответа заканчивается: сначала сверяют список, затем явно решают о новом создании.
Повтор не восстанавливает уже удалённый предмет: сохранённый ответ описывает исходную
операцию, актуальность проверяется GET/списком.
Disabled-кнопка не заменяет эту защиту или ограничение уникальности.

Для будущих платных генераций ключ дополнительно сохраняется в задании на весь срок
хранения операции. Истечение краткосрочного кэша не разрешает повторный платный вызов;
полный контракт генераций уточняется на этапе 10.

Сервер проверяет непустой предмет независимо от счётчика в браузере.
Удаление материала удаляет оригинал и связанные учебные данные, включая попытки;
frontend явно предупреждает до запроса. Сбои очистки сохраняются для повторения,
завершение старой генерации не восстанавливает удаляемые данные.

Задания различают queued/running/succeeded/failed/cancelled.
Публичные состояния материала для загрузки, обработки и удаления уточняются до этапа 8.
До подключения frontend нужен полный объект Material и точный ответ загрузки, включая
правила `title`, лимит в байтах и состояния обработки. Таблица выше — карта, не полный DTO.
Локальная отправка файла отличается от подтверждённого сервером сохранения;
статус конспекта не подменяет статус PDF. Опрос ограничен по частоте и прекращается
при завершении, уходе со страницы, выходе или потере авторизации.
Сон хостинга может приостановить выполнение.

В первой версии у вопроса один правильный вариант. До завершения попытки
не выдаются correctOptionId, раскрывающие ответ объяснения или иной ключ.
Вариант должен принадлежать вопросу, вопрос — тесту; повтор questionId отклоняется.
Балл: 100 × правильные ответы / число вопросов, округление до двух знаков.
Пропуск даёт ноль. Сервер фиксирует начало и завершение; продолжительность —
прошедшее время, не доказательство непрерывной активности.
Повтор идентичных ответов возвращает сохранённый результат, другие ответы после
завершения — 409 ATTEMPT_ALREADY_SUBMITTED. Новая генерация не меняет прежние попытки.
Намеренное удаление материала следует отдельной принятой политике.
Frontend попросил повторно подтвердить удаление истории попыток; вопрос открыт
до реализации удаления, исходное решение пользователя автоматически не меняется.

После первого сценария: карточки и события повторения, чат с источниками и историей,
агрегаты кабинета, изменение/восстановление пароля и удаление аккаунта.
Маршруты и DTO пока не фиксируются. «Изученная лекция» и «план на день» требуют
определений; вымышленные проценты и события не подставляются.

Не фильтровать только текущую страницу как весь набор предметов. После создания
и изменения обновлять список, после удаления последнего элемента страницы —
при необходимости выбирать предыдущую. Сохранять различие пустого аккаунта и пустого
поиска, уже появившееся в DashboardPage. Старый ключ localStorage не переносить на сервер.

Будущая совместная проверка после соответствующих этапов:

1. A входит и создаёт предмет с выбранным оформлением.
2. Обновление страницы и повторный вход сохраняют предмет.
3. B не видит его в списке/поиске/по UUID, но может создать такое же название.
4. Конкурентные создания не обходят уникальность; повтор ключа не создаёт дубль.
5. Ошибки сохраняют ввод; повтор после потери ответа использует прежний ключ.
6. Изменение не меняет id/счётчики; чужой предмет изменить/удалить нельзя.
7. Пустой предмет удаляется, непустой возвращает 409; ошибка не убирает карточку.
8. Выход A и вход B не оставляют на экране данные A.

Формы, authApi и subjectApi уже есть; этап 5 позволяет совместно проверить аккаунт,
пустой список, поиск, создание, ошибки, сетевой повтор и смену аккаунта.
Облачная загрузка PDF, конспекты, тесты и результаты ещё не подключены.
До появления экранов выполняются API-тесты. Визуальная и сквозная проверка
не объявляется успешной на основании чтения кода.
