# План frontend

Основной frontend MVP реализован на React + Vite + JavaScript. Восемь этапов его
завершения закончены; дополнительное исправление инициализации CSRF объединено
в `main` через PR #40. Следующая работа — совместная подготовка запуска,
описанная в [общем плане](launch-plan.md). Этот документ фиксирует объём frontend,
а инструкции запуска и проверки находятся в [frontend README](../frontend/README.md).

## Что уже реализовано

До восьми этапов были подключены регистрация, вход, сессия и CSRF, предметы
с поиском и пагинацией, создание и изменение с проверкой версии, удаление пустых
предметов, загрузка PDF, квота, обработка, извлечённый текст и скачивание оригинала.
Рабочий кабинет использует серверные данные; демонстрационный режим открывается
явно и хранит свои данные отдельно.

| Этап frontend | Выполненный объём |
| --- | --- |
| 1. Переименование материала | Свежая версия, проверка названия, сохранение черновика, явное разрешение конфликта и проверка неизвестного результата |
| 2. Удаление материала | Подтверждение, наблюдение за серверной очисткой, проверка отсутствия материала, обновление списка и квоты |
| 3. Создание и чтение конспекта | Явное подтверждение генерации, наблюдение за заданием, чтение сохранённого результата и безопасный повтор с прежним ключом |
| 4. Редактирование и повторная генерация | Версии и черновики текста, отдельное подтверждение новой генерации, сохранность прежнего текста и защита от повторной отправки |
| 5. Генерация и версии тестов | Список версий, просмотр конкретного теста, явное создание новой версии и проверка результата задания |
| 6. Прохождение теста | Начало попытки, выбор ответов, отправка, серверный результат и разбор, восстановление после неизвестного результата |
| 7. История попыток | Пагинация и фильтры, просмотр результатов, продолжение попытки и общие черновики при переходах между разделами |
| 8. Сквозной интерфейс и подготовка интеграции | Проверка навигации с клавиатуры и узких экранов, сквозные браузерные сценарии, инструкция совместной интеграции |

После этих этапов PR #40 устранил гонку параллельного получения CSRF, в том числе
при повторном запуске эффектов React StrictMode. Отмена ожидания одним экраном
не прерывает общий запрос; новое поколение токена ждёт завершения прежнего запроса.
Изменяющие запросы автоматически не повторяются.

Завершение frontend-этапов не означает завершение подготовки общего запуска.
Автоматические тесты с подменённым API, реальная интеграция с `AI=fake` и проверка
реального OpenAI учитываются отдельно. Подтверждённые результаты и их ограничения
собраны в [плане запуска](launch-plan.md); команды — в
[разделе проверок frontend README](../frontend/README.md#автоматические-проверки).

## Ближайшая работа

1. Зафиксировать общую ревизию frontend и backend, учесть уже принятую проверку PR #40
   и закрыть оставшиеся пункты [плана запуска](launch-plan.md). Если появились новые
   результаты, записать их отдельно от прежнего отчёта.
2. Исправлять воспроизводимые проблемы общего сценария небольшими изменениями:
   frontend отвечает за интерфейс, доступность и клиентское состояние;
   backend — за API, доступ к данным, задания, PostgreSQL и R2.
3. Подготовить запуск по общему плану: адреса и маршрутизацию API, серверное окружение,
   лимиты и эксплуатационные проверки. Vite dev proxy не является production-настройкой.
4. Отдельно согласовать необходимость реального OpenAI, расход API-баланса
   и данные для этой проверки. Успешный локальный fake не подтверждает внешний провайдер.

Статусы этих задач ведутся в [общем плане запуска](launch-plan.md), чтобы frontend
и backend не поддерживали разные списки готовности.

## После MVP

Карточки с повторениями, чат по материалу с источниками, агрегаты и расширенный
кабинет, изменение профиля и операции с паролем/аккаунтом не входят в выполненные
восемь этапов. Их направление описано в [архитектуре](architecture.md), а новые
контракты ещё нужно согласовать в [документации API](api.md).

До реализации каждой функции нужны поля и ошибки API, правила доступа, пагинация
при необходимости, ограничения и поведение повторного запроса. Для показателей
кабинета дополнительно нужна серверная формула; демонстрационный процент не должен
выдаваться за реальный прогресс.

Материалы уже доступны внутри предмета. Отдельные пункты «Лекции», «Карточки»
и «Настройки» пока показывают заглушки; наличие пункта меню не означает готовую функцию.
Новые функции добавляются после подготовки общего запуска и согласования объёма.

## Порядок следующих изменений

Для каждого изменения: уточнить контракт и критерий готовности, внести код,
выполнить подходящие проверки и описать результат и ограничения. Создание PR
и push выполняет владелец ветки; перед этим готовятся команды и описание изменения.
Клиентское состояние помогает показать интерфейс, но доступ к данным всегда
проверяет backend.
