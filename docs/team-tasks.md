# Распределение задач

Команда работает в одном репозитории. Роли ниже обозначают зоны ответственности,
а не имена или аккаунты участников: frontend-разработчик ведёт интерфейс,
backend-разработчик — сервер. Изменения общего контракта и подготовку запуска
оба согласуют вместе.

## Ответственность

| Зона | Ответственный | Содержание |
| --- | --- | --- |
| `frontend/` | Frontend-разработчик | React/Vite, формы, состояния, адаптивность, доступность, интеграция API и проверки UI |
| `backend/` | Backend-разработчик | Аккаунты, безопасность, PostgreSQL, R2, PDF, ИИ, задания, тесты, результаты и проверки сервера |
| Контракт API | Backend-разработчик готовит, оба согласуют | Маршруты, DTO, ошибки, авторизация, повторы, состояния и пагинация |
| Запуск | Оба | Сквозные проверки, размещение, ограничения пилота, документация и решение о допуске пользователей |

## Текущее состояние

Backend-этапы 1–12 реализованы: аккаунты и сессии, предметы, материалы и квоты,
обработка PDF, конспекты, версии тестов, попытки, серверная проверка и история.
Основной frontend MVP подключён к этим API, включая скачивание, переименование,
удаление, редактирование конспекта, повторную генерацию и просмотр результатов.
Реальные агрегаты кабинета и карточки в этот объём не входят.

Реализация и проверки фиксируются раздельно:

| --- | --- |
| Frontend MVP и проверки этапа 8, PR #39 | Реализован основной интерфейс; автоматические проверки с подменой API не заменяют настоящий backend, R2 и OpenAI |

Следующий общий шаг — [подготовка MVP к запуску](launch-plan.md). Готовность пилота
пока не подтверждена. Исторические backend-этапы остаются в
[архитектуре](architecture.md#последовательные-этапы); отдельный порядок работ
интерфейса — в [плане frontend](frontend-plan.md).

## Ближайшая совместная работа

1. Свести отчёт о реальной интеграции: отметить выполненные и оставшиеся пункты,
   ревизии обеих частей и режимы внешних сервисов. Учесть принятую проверку PR #40
   и закрыть оставшиеся пункты плана запуска; поздние результаты дописать без повторения
   уже выполненной работы.
2. Отдельно согласовать проверку настоящего ИИ: учебный PDF без персональных данных,
   предел расходов, конспект, тест и качество результата. Подключением провайдера
   занимается backend-разработчик, поведением интерфейса — frontend-разработчик.
3. Подготовить размещение и пилот: один origin для UI/API, ограничения ресурсов и
   запросов, резервное копирование с восстановлением, порядок допуска небольшой группы.
   Конкретные решения и результаты записывать в план запуска, не считать их готовыми заранее.

Пошаговые сценарии: [авторизация](../frontend/docs/auth-integration-check.md) и
[полный MVP](../frontend/docs/mvp-integration-check.md). Это инструкции для проверки,
а не отчёты об уже выполненных действиях.

## Точки передачи изменений

| Что меняется | Backend-разработчик | Frontend-разработчик | Совместная проверка |
| --- | --- | --- | --- |
| API | Обновляет [api.md](api.md), примеры, ошибки и серверные проверки | Обновляет адаптеры, состояния и проверки UI | DTO, владелец, null-поля, конфликты, повторы и пагинация |
| Авторизация | Сессии, cookie, CSRF, лимиты | Формы, bootstrap, восстановление сессии | Первый вход/регистрация, logout, истечение сессии и два аккаунта |
| Материалы и задания | R2, квота, PDF, сохраняемые задания и очистка | Загрузка, текст, скачивание, подтверждение удаления и наблюдение | Потеря ответа, ошибки обработки, завершение удаления и обновление квоты |
| Конспекты, тесты и попытки | Провайдер, проверка генерации, версии, серверный балл и история | Явные действия, сохранённые данные, черновики, конфликты и разбор | Повтор не создаёт лишнюю операцию, новая генерация сохраняет прежние результаты |
| Размещение | JVM/PDF, PostgreSQL, R2, секреты, резервные копии и ограничения | Сборка UI, адрес API, адаптивность и доступность | Полный сценарий на выбранном окружении и восстановление после сбоя |

Перед передачей изменений указываются PR/ревизия, изменённый контракт, выполненные
проверки и оставшиеся ограничения. Изменения API не вводятся молча; согласование
общей архитектуры не заменяет согласования конкретного нового контракта.

Постоянные правила интеграции описаны в API: для операций с Idempotency-Key — отдельный
ключ на логическую операцию и сохранение ключа при её сетевом повторе; версия при редактировании и явное решение
при конфликте. Submit попытки не создаёт job и не требует Idempotency-Key; балл
приходит с сервера. Черновики выбора не являются серверным сохранением.
Удаление материала затрагивает конспекты, версии тестов и всю историю попыток.
Демо-данные не импортируются в аккаунт; неопределённый прогресс не показывается как ноль.

## Общие файлы и границы работы

`docs/design.md` ведёт frontend-разработчик; `docs/api.md` — backend-разработчик
с согласованием обеих сторон. Архитектура, общий README, CI и план запуска меняются
в согласованном объёме. Работа одного направления не переписывает другое.

Правила PR — в [git-workflow.md](git-workflow.md). Агент готовит изменения, проверяет
их и сообщает результат; commit, push, PR и слияние не выполняются автоматически.
Облачные ресурсы, передача текста настоящему ИИ и платные запросы требуют отдельного
разрешения. Секреты не передаются в чат/PR и не попадают во frontend.

Для изменений только документации проверяются согласованность, ссылки и diff.
Тесты приложения и реальные интеграционные проверки нельзя объявлять выполненными
на основании изменения документов или успеха подменённых тестов.

## После первой версии

Карточки с учётом повторений, чат с источниками, расширенный кабинет и дополнительные
функции аккаунта остаются отдельными согласуемыми этапами. OCR, аудио, платежи,
социальные функции, совместное редактирование и сложный RAG не добавляются автоматически.
