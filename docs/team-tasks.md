# Распределение задач

Пользователь отвечает за backend, его друг — за frontend.
Имена и аккаунты участников не заданы; не подставлять вымышленные данные в review.
Оба работают в одном репозитории, в своих зонах ответственности.

## Ответственность

| Зона | Ответственный | Содержание |
| --- | --- | --- |
| frontend/ | Друг пользователя | React/Vite, интерфейс, адаптивность, формы, состояния, интеграция API, проверки UI |
| backend/ | Пользователь | Аккаунты, безопасность, PostgreSQL, R2, PDF, ИИ, задания, тесты и результаты, проверки сервера |
| Контракт API | Backend готовит, оба согласуют | Поля, маршруты, ошибки, авторизация, повторы, загрузка, состояния и пагинация |
| Общий проект | Оба согласуют | Общая документация, Git-процесс, CI и подготовка выпуска |

Backend разрабатывается последовательно в одном потоке: обсуждение → согласованный
небольшой этап → реализация → проверка → отчёт и остановка до следующего указания.
Параллельные агенты и worktree для нескольких задач не нужны.
Старые задачи T00–T15 не являются автоматически действующим планом.

## Последовательная работа и точки интеграции

Единый план из 13 backend-этапов ведётся в architecture.md; номера не дублируются
отдельным конкурирующим планом. Таблица ниже показывает взаимодействие двух частей.

| Область | Друг: frontend | Пользователь: backend | Совместный результат |
| --- | --- | --- | --- |
| Подготовка | Проверить контракт и необходимый адаптер | Зафиксировать решения, затем настроить сервер отдельным этапом | Общий контракт без предположения, что он уже реализован |
| Аккаунт | Формы, CSRF, cookie, состояния 401/403 | Регистрация, сессии, вход, выход, текущий пользователь | Студент входит в свой аккаунт |
| Предметы | Подключить текущие создание/изменение/удаление и поиск асинхронно | CRUD, владелец, ограничения БД, идемпотентность | Два аккаунта изолированы, повтор не создаёт дубль |
| Материалы | Загрузка, состояние, квота и подтверждение удаления | R2, PostgreSQL, PDF, задания, восстановление и очистка | Оригинал и текст доступны владельцу, сбой не теряет состояние |
| Конспект | Чтение, редактирование, ожидание и ошибки | Адаптер ИИ, проверка и сохранение | Повторное открытие показывает сохранённый конспект |
| Тесты | Прохождение и разбор завершённой попытки | Версии, закрытый ключ, серверная проверка и история | Результат сохранён и не меняется новой генерацией |
| Выпуск | Адаптивность, доступность, сквозные сценарии | Тесты, конфигурация, лимиты, восстановление | Проверенный первый сценарий для небольшой группы |

## Правила готовности и общих файлов

Проверки выполняются вместе с функциями. Для этапа документации проверяются
согласованность, ссылки, примеры и diff; запуск сервера и тесты приложения
не объявляются успешными, когда сервер ещё не создан.

Frontend не переписывается backend-работами. Изменения API не вводятся молча.
`docs/design.md` ведёт frontend-разработчик; `docs/api.md` готовит backend-разработчик
с последующим согласованием обеих сторон. Общий README, .gitignore, CI и Git-процесс
меняются отдельно в согласованном объёме.

Правила PR описаны в [git-workflow.md](git-workflow.md). Они не разрешают агенту
самостоятельные commit, push, PR, переключение веток, merge, rebase или reset.
Такие операции выполняются только по явному указанию пользователя в его границах.
Облачные ресурсы и реальные платные запросы также требуют отдельного разрешения.
О невыполненных проверках и отсутствующих зависимостях сообщается прямо.

## После первой версии

Карточки с учётом повторений, чат по лекции с источниками, расширенный кабинет
и дополнительные функции аккаунта — следующие согласованные этапы.
OCR, аудио, платежи, социальные функции, совместное редактирование и сложный RAG
не добавляются автоматически. Хостинг и ИИ-провайдер ещё не выбраны.
