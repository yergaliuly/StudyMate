# Распределение задач

Пользователь отвечает за backend, его друг — за frontend.
Имена и аккаунты участников не заданы; не подставлять вымышленные данные в review.
Оба работают в одном репозитории, в своих зонах ответственности.

## Ответственность

| Зона | Ответственный | Содержание |
| --- | --- | --- |
| frontend/ | Друг пользователя | React/Vite, интерфейс, адаптивность, формы, состояния, интеграция API, проверки UI |
| backend/ | Пользователь | Аккаунты, безопасность, PostgreSQL, R2, PDF, ИИ, задания, тесты и результаты, проверки сервера |
| Контракт API | Backend готовит, оба согласуют | Поля, маршруты, ошибки, авторизация, повторы, загрузка, состояния и пагинация |
| Общий проект | Оба согласуют | Общая документация, Git-процесс, CI и подготовка выпуска |

Backend разрабатывается последовательно в одном потоке: обсуждение → согласованный
небольшой этап → реализация → проверка → отчёт и остановка до следующего указания.
Параллельные агенты и worktree для нескольких задач не нужны.
Старые задачи T00–T15 не являются автоматически действующим планом.

## Текущее состояние и передача контракта

Этапы 1–6 слиты через PR #6, #10, #12, #15, #17 и #19. Этап 7 реализован в `feat/backend-jobs` от
`e12a63e0b27586675340e789a0dc6a33d3c8c737` (также включает auth integration, PR #18).
Frontend содержит кабинет, локальные предметы,
страницу предмета, выбор/перетаскивание и локальный просмотр PDF, формы авторизации
и общий apiClient с тестами (PR #7–9), authApi и subjectApi (PR #11, #13).
В main также подключены авторизация/восстановление сессии и Vite proxy (PR #18).
Облачной загрузки нет; общий UI-сценарий требует отдельной проверки.

Пользователь утвердил backend-направление из [architecture.md](architecture.md).
[api.md](api.md) подтверждён другом в части общей архитектуры, cookie/CSRF,
формата ответов и подробно описанных запросов аккаунта и предметов.
После основы этапа 2 реализованы аккаунты и POST регистрации: PostgreSQL, Argon2id,
валидация и конкурентная уникальность email. Регистрация закрыта по умолчанию;
явный флаг разработки не отключает CSRF. На этапе 4 готовы GET csrf/me и POST login/logout,
сессии JDBC и Flyway V3. Проверены настоящие HTTP-запросы с cookie/CSRF, смена и истечение
сессии, изоляция аккаунтов и перезапуск JAR. Полный UI-сценарий проверяется отдельно.
На этапе 5 готовы список/поиск/пагинация и создание предметов, Flyway V4, проверка
уникальности внутри аккаунта и Idempotency-Key с хранением результата 24 часа.
Проверены два аккаунта, конкуренция, откат транзакции, очистка и повтор после перезапуска.
На этапе 6 готовы GET/PATCH/DELETE по UUID, версия предмета (Flyway V5), конфликт 409
и удаление пустого предмета. Защита непустого проверена на тестовых FK-ссылках PostgreSQL;
реальные материалы, их FK ON DELETE RESTRICT и подсчёт остаются этапом 8.
На этапе 7 готова очередь PostgreSQL (V6): аренда/heartbeat, ограниченные повторы,
атомарная запись результата, отмена внутри backend и восстановление после остановки JVM.
GET /jobs/{id} показывает состояние только владельцу. Реальных обработчиков и публичного
создания задания пока нет; проверка выполняется на операции только из src/test.

Ветка для текущей интеграции — `feat/backend-jobs`, backend
`http://127.0.0.1:8080`, API `/api/v1`, профиль `local` для HTTP, регистрация только с
`STUDYMATE_REGISTRATION_ENABLED=true`. После push пользователь передаёт SHA из `git rev-parse HEAD`.
Команды запуска и пример Vite proxy — [backend/README.md](../backend/README.md).
Proxy и auth integration уже в main; друг проверяет cookie, обновление CSRF, вход, выход и ошибки форм;
исходники frontend данным этапом не менялись. Существующий subjectApi проверен через HTTP
с Node и cookie jar: создание, повтор, конфликты, поиск, страницы и изоляция совместимы.
Для редактирования/удаления нужны новые методы subjectApi.update/remove. Нынешний адаптер
отбрасывает version: её нужно сохранять из DTO. Перед формой редактирования загрузить GET,
передавать его version в PATCH и обновлять её после успеха. 409 SUBJECT_VERSION_CONFLICT
сохраняет черновик и предлагает загрузить актуальные данные; автоматической перезаписи нет.
DELETE возвращает 204 без тела; повтор/чужой/отсутствующий UUID — 404. Карточку убирать
после успеха; при SUBJECT_NOT_EMPTY оставлять и показывать сообщение.
Для создания держать прежний Idempotency-Key при сетевом повторе, обрабатывать 409 и
Retry-After, после успеха обновлять список. Null-прогресс скрывать, demo/localStorage не импортировать.

Для этапа 7 друг может подготовить jobApi.getById и состояния queued/running/succeeded/failed/cancelled.
Полный ответ/ошибки описаны в api.md; error задания внутри data не означает HTTP-ошибку.
После появления endpoint загрузки/генерации опрашивать полученный job id без перекрытия
запросов, прекращать на терминальном состоянии/404/выходе. Сетевой сбой не повод создавать
новое задание. Сейчас пользовательских операций, возвращающих job id, ещё нет.

Друг подтвердил, что перед интеграцией адаптирует существующие обработчики:
SubjectFormModal/onSave, DeleteSubjectModal/onConfirm, загрузку и поиск предметов.
Конкретное задание, ошибки, CSRF, Idempotency-Key и проверки двух аккаунтов — в api.md.
Изменение localStorage на HTTP не означает автоматический импорт демонстрационных данных.

Перед интеграцией материалов backend должен дополнить `title` загрузки, лимит в байтах,
полный объект материала, состояния и ответ загрузки. Контракт PATCH дополнен в api.md;
пользователь подтвердил версию в JSON и конфликт 409. Перед интеграцией frontend-разработчик
должен ознакомиться с дополнением; его согласие на новый формат не предполагается.
Непустой предмет удалять нельзя — обе стороны согласны.
Удаление истории попыток вместе с материалом друг предложил повторно подтвердить;
до реализации нужно обсудить это с пользователем, сохраняя исходное решение в документации.

## Последовательная работа и точки интеграции

Единый план из 13 backend-этапов ведётся в architecture.md; номера не дублируются
отдельным конкурирующим планом. Таблица ниже показывает взаимодействие двух частей.

| Область | Друг: frontend | Пользователь: backend | Совместный результат |
| --- | --- | --- | --- |
| Подготовка | Проверить контракт и необходимый адаптер | Зафиксировать решения, затем настроить сервер отдельным этапом | Общий контракт без предположения, что он уже реализован |
| Аккаунт | Формы, CSRF, cookie, состояния 401/403 | Регистрация, сессии, вход, выход, текущий пользователь | Студент входит в свой аккаунт |
| Предметы | Подключить текущие создание/изменение/удаление и поиск асинхронно | CRUD, владелец, ограничения БД, идемпотентность | Два аккаунта изолированы, повтор не создаёт дубль |
| Материалы | Загрузка, состояние, квота и подтверждение удаления | R2, PostgreSQL, PDF, задания, восстановление и очистка | Оригинал и текст доступны владельцу, сбой не теряет состояние |
| Конспект | Чтение, редактирование, ожидание и ошибки | Адаптер ИИ, проверка и сохранение | Повторное открытие показывает сохранённый конспект |
| Тесты | Прохождение и разбор завершённой попытки | Версии, закрытый ключ, серверная проверка и история | Результат сохранён и не меняется новой генерацией |
| Выпуск | Адаптивность, доступность, сквозные сценарии | Тесты, конфигурация, лимиты, восстановление | Проверенный первый сценарий для небольшой группы |

## Правила готовности и общих файлов

Проверки выполняются вместе с функциями. Для этапа документации проверяются
согласованность, ссылки, примеры и diff; запуск сервера и тесты приложения
не объявляются успешными, когда сервер ещё не создан.

Frontend не переписывается backend-работами. Изменения API не вводятся молча.
`docs/design.md` ведёт frontend-разработчик; `docs/api.md` готовит backend-разработчик
с последующим согласованием обеих сторон. Общий README, .gitignore, CI и Git-процесс
меняются отдельно в согласованном объёме.

Правила PR описаны в [git-workflow.md](git-workflow.md). Они не разрешают агенту
самостоятельные commit, push, PR, переключение веток, merge, rebase или reset.
Такие операции выполняются только по явному указанию пользователя в его границах.
Облачные ресурсы и реальные платные запросы также требуют отдельного разрешения.
О невыполненных проверках и отсутствующих зависимостях сообщается прямо.

## После первой версии

Карточки с учётом повторений, чат по лекции с источниками, расширенный кабинет
и дополнительные функции аккаунта — следующие согласованные этапы.
OCR, аудио, платежи, социальные функции, совместное редактирование и сложный RAG
не добавляются автоматически. Хостинг и ИИ-провайдер ещё не выбраны.
