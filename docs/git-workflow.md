# Работа вдвоём через ветки и pull request

## Один репозиторий, отдельная ветка на задачу

Не создавать отдельные репозитории для frontend/backend и не работать постоянно в двух
долгоживущих ветках «участник 1» и «участник 2». В этом проекте короткие ветки на задачи.

Перед новой задачей убедиться, что текущая работа сохранена и нет незафиксированных изменений.

```powershell
git switch main
git pull --ff-only origin main
git switch -c frontend/example-task
```

Название задачи — пример; для frontend используем префикс `frontend/` и короткое
английское описание. Подготовка файлов и проверки могут выполняться с помощником.
Коммит, push и создание PR выполняет сам владелец изменений.

## Изменения и review

Добавить код → локально проверить → посмотреть `git diff` и `git status` → commit → push.

```powershell
git add frontend/
git diff --cached
git commit -m "feat(ui): add dashboard layout"
git push -u origin frontend/example-task
```

На GitHub открыть PR: base `main`, compare своя ветка. Название — на английском,
описание — на русском: результат изменения, список важных деталей и отдельный блок
«Проверки». Указать фактически выполненные проверки и оставшиеся ограничения;
при визуальных изменениях добавить скриншот UI. Попросить второго участника проверить.
Шаблон PR уже в `.github/`.
Исправления добавляются в ту же ветку и тот же PR, а не в новый PR на каждый комментарий.

После review и доступных автоматических проверок слить PR, затем оба обновляют локальный `main`.
Для PR только с документацией проверить ссылки, команды по текущей конфигурации и
`git diff --check`. Тесты приложения повторять при изменении кода или обнаружении
риска для его работы; исторический результат прогона помечать отдельно.
Не добавлять пустую CI-проверку, чтобы создать видимость тестирования.

## Правила команды

Один PR — одна понятная задача. Не пушить напрямую в `main` после начальной структуры.
Не подменять авторство: каждый настраивает свой Git, не копирует чужое имя и почту.
Не коммитить секреты; не менять общие API-поля без обсуждения.
Защиту `main` и обязательное review настроить в GitHub при доступности на выбранном тарифе.
Файл в репозитории сам по себе не включает защиту ветки и не назначает reviewers.

При конфликтах не выбирать бездумно «оставить всё моё» или «всё чужое».
Разобраться в затронутом коде, обсудить с автором другой части и перепроверить результат.
Не выполнять force push в общую ветку.

Официальный процесс: `https://docs.github.com/en/get-started/using-github/github-flow`.
