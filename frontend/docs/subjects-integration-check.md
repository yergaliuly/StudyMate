# Предметы с настоящим backend

Это инструкция проверки предметов, не отчёт о выполнении. Нужен текущий backend с
применёнными миграциями на `127.0.0.1:8080`; frontend запускается через `npm run dev`
на `127.0.0.1:5173`. Запуск БД и миграций описан в [backend README](../../backend/README.md).
Войдите в тестовый аккаунт. Стандартные Playwright-тесты используют подменённые API-ответы.
Проверка материалов и всего MVP — в [общем сценарии](mvp-integration-check.md),
известные результаты — в [плане запуска](../../docs/launch-plan.md).

## Список и создание

1. В новом аккаунте список пуст; демонстрационных предметов и процентов прогресса нет.
2. Нажмите «Добавить предмет». Заполните название, описание, выберите иконку и цвет.
   При отправке форма блокируется. После ответа POST 201 список запрашивается заново.
3. Перезагрузите страницу: предмет остаётся в списке. Выйдите и войдите в тот же
   аккаунт: данные сохраняются на сервере, не в localStorage/sessionStorage.
4. Создайте предмет с тем же названием в другом регистре и с лишними пробелами:
   ожидаются 409 SUBJECT_TITLE_EXISTS, сохранённый ввод и ошибка в форме.
5. Поиск выполняется по названию/описанию на сервере; новый запрос возвращает на
   первую страницу. Несуществующий запрос показывает «Ничего не найдено».
6. При наличии более 20 предметов доступны страницы. Общий счётчик берётся из meta.total.
7. Остановите backend и нажмите «Обновить список»: показана ошибка, не пустой список.
   После запуска сервера обновление снова работает. При истёкшей сессии предложен вход.
8. Выйдите из аккаунта A и войдите в B: в B нет карточек и черновика A.
   B может создать собственный предмет с таким же названием.
9. Демо остаётся отдельным: его предметы не импортируются в аккаунт и не удаляются
   при выходе из аккаунта.

При неизвестном результате создания форма сохраняет исходный ключ и данные:
«Повторить создание» отправляет тот же запрос, без автоматического повтора.
«Изменить данные» — явное решение начать другое создание после проверки списка.
При возврате в тот же аккаунт черновик сохраняется в памяти; после явного выхода,
смены аккаунта или перезагрузки страницы он очищается.

## Просмотр и редактирование

1. Откройте предмет кнопкой на карточке. Данные загружаются отдельным
   `GET /api/v1/subjects/{id}`, а не берутся из исторического ответа создания.
   Проверьте название, описание, иконку и цвет. Переход к материалам и загрузка PDF
   проверяются отдельно по общему сценарию MVP.
2. Откройте редактирование из карточки или окна предмета. Перед появлением формы
   выполняется свежий GET; его версия используется для последующего PATCH.
3. Измените название, описание, иконку и цвет, затем сохраните. Во время отправки
   повторное сохранение заблокировано. После ответа PATCH 200 карточка и список
   обновляются. Перезагрузите страницу и проверьте, что правки сохранились.
4. Очистите описание и сохраните: серверное описание становится пустой строкой.
   Отмена редактирования не изменяет данные сервера.
5. Попробуйте переименовать предмет в уже существующий: ожидается
   `409 SUBJECT_TITLE_EXISTS`, ошибка названия и сохранённый ввод. Исправьте название
   и сохраните ещё раз. Другие поля черновика не должны сброситься.

## Конфликт в двух вкладках

1. В одном тестовом аккаунте откройте один предмет для редактирования в двух вкладках.
   Оба редактора должны успеть загрузить исходные данные до первого сохранения.
2. В первой вкладке измените описание и сохраните. Во второй введите другое описание
   и сохраните: ожидается `409 SUBJECT_VERSION_CONFLICT`; её черновик остаётся в форме.
3. Во второй вкладке нажмите «Загрузить актуальную версию». Эта операция выполняет
   GET, но сама по себе не заменяет ввод и не отправляет PATCH.
4. Проверьте оба решения в отдельных повторах сценария: «Использовать версию сервера»
   либо «Продолжить с моим черновиком». Сохранение своего черновика с новой версией
   требует отдельного нажатия «Сохранить изменения»; автоматического перезаписывания нет.
5. Если первая вкладка снова сохранит правки после загрузки актуальных данных во
   второй, повторное сохранение во второй вновь должно показать конфликт.

## Удаление

1. Создайте отдельный пустой тестовый предмет. Откройте удаление и отмените его:
   карточка остаётся. Повторите и подтвердите; после DELETE 204 окно закрывается,
   список запрашивается заново. После перезагрузки предмета нет.
2. Откройте подтверждение удаления одного предмета в двух вкладках до первого
   удаления. Подтвердите в первой, затем во второй: DELETE 404 означает, что предмет
   больше недоступен. Интерфейс обновляет список и не сообщает, будто именно второй
   запрос успешно удалил его. Если открыть предмет уже после удаления, его GET
   вернёт 404 ещё до подтверждения.
3. При `409 SUBJECT_NOT_EMPTY` окно объясняет причину, предмет остаётся в списке.
   Решение принимает сервер; `lectureCount` не используется как разрешение удаления.
   На настоящем стенде используйте отдельный тестовый предмет с загруженным PDF.
   После проверки удалите материал, дождитесь подтверждённой очистки, затем удалите
   пустой предмет. Отдельная тестовая FK-таблица для этого не нужна.

## Неизвестный результат и восстановление сессии

Потеря ответа PATCH или DELETE не доказывает, что изменение не выполнено. Нажатие
«Проверить результат» выполняет GET без повторной мутации. После проверки доступны
актуальные данные для осознанного решения; повторное изменение требует отдельного
действия пользователя. Если GET возвращает 404, интерфейс сообщает о недоступности
предмета и обновляет список. Новая сетевая ошибка не подменяется успешным результатом.

При `422 VALIDATION_FAILED` сохраняются ввод и ошибки полей. При истёкшей сессии
или неверном CSRF выполняется проверка авторизации; PATCH/DELETE автоматически не
повторяются. Возврат в тот же аккаунт сохраняет черновик в памяти. Явный выход,
смена аккаунта или перезагрузка страницы очищают его. Для проверки смены аккаунта
оставьте редактор A открытым в первой вкладке, выйдите из A во второй и попробуйте
сохранить в первой. После перехода к входу войдите в B: данные и черновик A не
показываются. Кнопки за модальным окном недоступны; для обычного выхода в той же
вкладке сначала закройте редактор.

Управляемые тесты `e2e/subject-details.spec.js` проверяют ошибки, конфликты и потерю
ответа без настоящего backend. Сценарии списка и создания остаются в своих тестах.
Это не отчёт об успешном запуске: перед PR запустите проверки ниже и отдельно отметьте
пройденные ручные сценарии. Новые проверки не заменяют прежние тесты авторизации и демо.

## Команды проверки

Из каталога `frontend`:

```powershell
node --test tests/apiClient.test.js tests/authApi.test.js tests/subjectApi.test.js tests/sessionFlow.test.js tests/subjectDraft.test.js
npm run build
npx playwright test
```

В отчёт записывайте статусы и результат сценариев без паролей, cookie, CSRF и HAR.
