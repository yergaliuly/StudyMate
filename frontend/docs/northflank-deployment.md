# Публикация frontend в Northflank

Обновление 06.10.2026: frontend опубликован, совместная проверка аккаунта и предметов
завершена. Следующий этап и границы подтверждённого результата описаны в
[проверке перед пилотом](pilot-error-handling.md). Ниже сохранены инструкция размещения
и результаты проверки **до публикации**.

Первый опубликованный этап проверяет интерфейс, сессию и предметы через настоящий backend.
R2, jobs, генерация ИИ и включение регистрации в этот этап не входят.
Публикация frontend и вход через него пока не подтверждены. Проверки от 06.10.2026
перечислены ниже: запросы к облачному backend шли через локальный nginx.
На машине разработки Docker отсутствует; проверка самого контейнера ожидает CI.

## 1. Подготовить версию

Frontend-разработчик самостоятельно выполняет push и создаёт PR из
`frontend/northflank-deployment`. После review и merge убедитесь, что в `main`
есть `frontend/Dockerfile` и конфигурация nginx. Только затем создавайте сервис из `main`.
Используйте существующий проект `studymate-dev` и согласованные ресурсы;
этот сценарий не требует смены тарифа, добавления платных опций или новых хранилищ.

Локальная сборка образа из корня репозитория на Linux/macOS с доступным Docker:

```sh
docker build -t studymate-frontend:test ./frontend
```

Проверка образа в Linux/CI (нужны Node.js 24, OpenSSL и свободный порт 8080):

```sh
node frontend/deploy/tests/proxy-smoke.mjs --docker studymate-frontend:test
```

Режим `--docker` использует Linux host networking и не запускается на macOS/Windows.
На Windows доступна проверка с установленным nginx: после `npm ci` и `npm run build`
в `frontend` задайте `NGINX_BIN`, `OPENSSL_BIN`, `SH_BIN` путями к nginx, OpenSSL и sh
через `$env:ИМЯ = 'путь'`, затем из корня запустите
`node frontend/deploy/tests/proxy-smoke.mjs`. Обе проверки используют временный HTTPS-сервер
с тестовыми ответами и не обращаются к настоящему backend; native-проверка не проверяет образ Docker.

## 2. Заполнить создание сервиса

Выберите **Combined service** — сборка из Git и запуск в одном сервисе.

| Поле | Значение |
| --- | --- |
| Project | `studymate-dev` |
| Service name | `studymate-frontend` |
| Repository | `yergaliuly/StudyMate` |
| Branch | `main` после merge PR |
| Build type | `Dockerfile` |
| Build context | `/frontend` |
| Dockerfile path | `/frontend/Dockerfile` |

Путь Dockerfile отсчитывается от корня репозитория, даже при контексте `/frontend`.
Значения `/` и `/Dockerfile` из формы по умолчанию для этой сборки не подходят.
Это соответствует [правилам Northflank для Dockerfile](https://northflank.com/docs/v1/application/build/build-with-a-dockerfile).

Dockerfile собирает Vite через Node.js 24 и запускает результат в nginx 1.30.5.
Команды сборки и запуска уже заданы в образе: переопределять их в форме не нужно.
`VITE_API_BASE_URL=/api/v1` закреплён при сборке. Не задавайте здесь URL backend,
пароли, cookie, CSRF или ключи R2/OpenAI; frontend-сборка не должна получать секреты.

## 3. Указать runtime-переменные и порт

В **Runtime variables** задайте следующие значения; они также служат значениями по умолчанию образа.

| Переменная | Значение |
| --- | --- |
| `BACKEND_HOST` | `site--studymate-backend--wpkj64cc5mq6.code.run` |
| `BACKEND_PORT` | `443` |

`BACKEND_HOST` содержит только hostname, без `https://`, порта и пути.
nginx передаёт `/api/` в backend по HTTPS с проверкой сертификата, сохраняет
Cookie/Set-Cookie и CSRF-заголовок. Ответы API не кэшируются; изменяющие запросы
автоматически не повторяются. В браузере все API-запросы остаются на домене frontend.

DNS backend разрешается при старте nginx; после изменения его IP перезапустите frontend.
nginx не доверяет входящим IP/forwarding-метаданным и пересоздаёт используемые заголовки.
Реальный IP клиента пока не гарантируется: цепочку доверенных прокси Northflank/backend
нужно согласовать отдельно. Авторизация от IP не зависит; код backend этим этапом
не меняется, безусловное доверие forwarded-заголовкам не включается.

В **Networking** добавьте порт `8080`, протокол **HTTP**, доступ **Public**.
Если форма автоматически добавила порт `80` из базового образа, удалите его; nginx слушает `8080`.
Публичный HTTPS и сертификат предоставляет Northflank; в контейнере остаётся HTTP
на 8080. Используйте выданный платформой URL, не добавляя к нему `:8080`.
См. [настройку портов Northflank](https://northflank.com/docs/v1/application/network/configure-ports).

В **Health checks** настройте HTTP readiness probe: порт `8080`, путь `/healthz`.
Ожидается `200`. Это проверка nginx frontend, а не Java, БД, сессии, R2 или ИИ.
Путь `/api/v1/auth/me` не подходит для такой проверки: гость получает ожидаемый `401`.
См. [настройку health checks](https://northflank.com/docs/v1/application/observe/configure-health-checks).

Создайте сервис, дождитесь успешных build/deployment и сохраните SHA сборки и публичный URL.
Если сборка не видит Dockerfile, сначала проверьте выбранную ветку и оба пути из таблицы.
Локальная разработка остаётся прежней: Vite `127.0.0.1:5173` проксирует API на `127.0.0.1:8080`.

## 4. Проверить опубликованный интерфейс

До входа backend-разработчик подтверждает наличие согласованного тестового аккаунта.
Пароль вводится владельцем аккаунта непосредственно в форме; в чат, Git и отчёт он не попадает.
Если аккаунта ещё нет, проверка входа и предметов остаётся невыполненной; регистрацию не включайте.

В новом приватном окне откройте HTTPS-адрес frontend и DevTools → Network:

- `/healthz` возвращает `200`; главная страница и статические файлы загружаются.
- Начальная цепочка: `/api/v1/auth/csrf` → `200`, затем `/auth/me` → `401 AUTHENTICATION_REQUIRED`.
  Ответы API содержат JSON, а не HTML главной страницы; запросы идут на домен frontend.
- При проверке закрытой регистрации с корректным телом и CSRF ожидается
  `403 REGISTRATION_CLOSED`. `403 CSRF_INVALID` — другая ошибка, её нужно исследовать.
- Вход тестового аккаунта: login → `200`, новый CSRF → `200`, me → `200`.
  Проверьте имя аккаунта, reload без повторного login и отсутствие циклических запросов.
- Создайте пустой тестовый предмет, найдите его поиском, откройте и измените название.
  После reload сервер показывает сохранённые данные; повторный клик не создаёт дубликат.
- Отдельно проверьте `422 VALIDATION_FAILED`: отправьте PATCH своего тестового предмета
  с корректным CSRF и JSON `{"version":"1","title":"Проверка"}`. Строковый тип version
  отклоняется до изменения; свежий GET подтверждает прежние данные. Клиентская форма
  может отсеять неверный ввод раньше HTTP, поэтому это отдельная ручная API-проверка.
- Откройте редактирование одного предмета в двух вкладках до сохранения. Сохраните в первой,
  затем во второй: ожидается `409 SUBJECT_VERSION_CONFLICT`, черновик остаётся,
  актуальная версия загружается вручную, автоматического повторного PATCH нет.
- Удалите только созданный для проверки пустой предмет: DELETE → `204`, карточка исчезает.
- Выполните logout → `204`, новый CSRF → `200`, me → `401`; reload оставляет гостевой экран.
  Cookie сессии на HTTPS имеет `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, без `Domain`;
  секреты не попадают в Web Storage.

Проверено 06.10.2026 перед публикацией:

| Проверка | Результат |
| --- | --- |
| Node-тесты / production Playwright / dev StrictMode | 593 / 217 / 3 прошли; API-ответы подменены |
| Vite production build | Прошла; прежнее предупреждение о размере JS chunk больше 500 kB |
| Native nginx 1.30.5 + HTTPS fixture | 14 проверок переменных и 5 групп proxy/TLS прошли |
| Настоящий backend `/actuator/health` | `200`, `UP` |
| Настоящий backend через локальный nginx | CSRF `200`, гостевой me `401 AUTHENTICATION_REQUIRED`; проверка TLS включена |
| Cookie настоящего backend | Host-only, `Path=/`, `Secure`, `HttpOnly`, `SameSite=Lax`; значения не сохранялись |
| Docker image / Northflank deployment | Docker ожидает CI; frontend ещё не опубликован |
| Вход, reload, logout и предметы на опубликованном сайте | Не проверены: нужны публикация и согласованный тестовый аккаунт |

Запишите дату, SHA frontend/backend, URL frontend, результат build/deployment и каждого пункта выше.
Разделите «прошло», «ошибка» и «не проверено». Для ошибки достаточно действия, HTTP-статуса,
кода ошибки и безопасного описания; не прикладывайте HAR, пароли, cookie или значения токенов.
Успех этого этапа подтверждает auth и предметы, но не полный PDF/AI-сценарий.
Следующие проверки согласуются по [общему плану запуска](../../docs/launch-plan.md)
и [сценарию интеграции MVP](mvp-integration-check.md).
