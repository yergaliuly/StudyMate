# Ручная проверка авторизации с настоящим backend

Это инструкция, а не отчёт об уже выполненных проверках. В PR отдельно указывайте
результат автоматических тестов с подменёнными ответами и результат ручного
сценария с Java/PostgreSQL.

## Запуск

- Java 21, PostgreSQL 17 и существующая база `studymate` доступны.
- Backend запущен с профилем `local`, переменными подключения к БД и
  `STUDYMATE_REGISTRATION_ENABLED=true`. Переменные задаются в терминале;
  пароль БД не добавляется в Git или frontend-переменные `VITE_*`.
- `http://127.0.0.1:8080/actuator/health` возвращает `{"status":"UP"}`.

В отдельном PowerShell:

```powershell
cd C:\Daniyar\MyProjects\studymate\frontend
npm ci
npm run dev -- --host 127.0.0.1 --port 5173 --strictPort
```

Откройте `http://127.0.0.1:5173` в новом приватном окне браузера. Все запросы
интерфейса должны идти на `/api/v1` этого же origin; Vite проксирует `/api`
на `http://127.0.0.1:8080`. Не заменяйте адрес на `localhost` посреди сценария.

Откройте DevTools → Network. Проверяйте пути, порядок, статусы и коды ошибок.
Не прикладывайте к PR HAR, тела с паролями, cookie или значения CSRF-токенов.

## Полный сценарий

1. При открытии страницы выполняются `GET /api/v1/auth/csrf` →
   `GET /api/v1/auth/me`. Первый ответ — `200`, второй —
   `401 AUTHENTICATION_REQUIRED`; видна форма входа. В dev-режиме React StrictMode
   может отменить первоначальную попытку и начать новую; завершённая проверка
   должна сохранять этот порядок.
2. Перейдите к регистрации. Используйте вымышленное имя, уникальный email вида
   `auth-<дата-время>@example.com` и отдельный тестовый пароль длиной 12–128 символов.
   Для проверки сохранения пробелов можно добавить по пробелу в начало и конец
   пароля и затем вводить его точно так же. Не используйте настоящий пароль.
3. Отправьте форму один раз. Во время запроса повторная отправка заблокирована.
   `POST /api/v1/auth/register` содержит CSRF-заголовок и получает `201`.
   Появляются форма входа и сообщение «Аккаунт создан. Теперь войдите.»;
   пароль очищен. Автоматического `POST /auth/login` нет.
4. В другой вкладке **того же приватного окна** откройте
   `http://127.0.0.1:5173/api/v1/auth/me`: по-прежнему
   `401 AUTHENTICATION_REQUIRED`. Регистрация сама по себе не выполняет вход.
5. В интерфейсе повторите регистрацию с тем же email и корректными остальными
   полями. Ожидаются `409 EMAIL_ALREADY_EXISTS` и понятное сообщение в форме.
   Затем переключитесь на вход.
6. Введите существующий email и неверный пароль. Ожидаются
   `401 INVALID_CREDENTIALS`, общее сообщение о неверном email или пароле и
   сохранение гостевого состояния. Для неизвестного email сообщение такое же.
7. Введите правильные данные. Ожидаемый порядок:
   `POST /auth/login` (`200`) → `GET /auth/csrf` (`200`) →
   `GET /auth/me` (`200`). Экран аккаунта показывает имя и email из `/me`,
   инициалы и сообщение о подключении к серверу. Демо-предметы и демонстрационный
   прогресс не выдаются за данные аккаунта; подключение предметов — отдельный шаг.
8. Перезагрузите страницу. После проверки сессии снова открыт тот же аккаунт;
   повторного `POST /auth/login` нет.
9. Откройте демо явной кнопкой, создайте там вымышленный предмет, вернитесь в
   аккаунт. Предмет остаётся только в демо; имя и email аккаунта не заменяются
   демонстрационным пользователем. Выход из аккаунта не должен удалять демо-данные.
10. Нажмите выход. Ожидается один `POST /api/v1/auth/logout` с CSRF-заголовком,
    **без тела**, ответ `204`; затем новый `GET /auth/csrf` (`200`) и
    `GET /auth/me` (`401 AUTHENTICATION_REQUIRED`). Приватный экран закрыт,
    показана форма входа. Перезагрузка оставляет пользователя гостем.
11. В DevTools → Application убедитесь, что пароль, CSRF-токен, session id и
    данные вошедшего пользователя не записаны в localStorage/sessionStorage.
    Cookie сессии имеет `HttpOnly` и `SameSite=Lax`; в локальном HTTP-профиле
    отсутствие `Secure` ожидаемо. Не копируйте значения cookie в отчёт.

## Ошибки настоящего сервера

### Регистрация закрыта

В терминале backend остановите процесс через `Ctrl+C`. В том же терминале
с сохранёнными настройками Java и БД выполните из каталога `backend`:

```powershell
$env:STUDYMATE_REGISTRATION_ENABLED = 'false'
.\mvnw.cmd spring-boot:run
```

После запуска перезагрузите страницу frontend, чтобы получить действующий CSRF.
Гостем отправьте корректную регистрацию с новым тестовым email. Ожидаются
`403 REGISTRATION_CLOSED` и сообщение «Регистрация сейчас закрыта.».

Затем остановите backend и обязательно восстановите локальный режим:

```powershell
$env:STUDYMATE_REGISTRATION_ENABLED = 'true'
.\mvnw.cmd spring-boot:run
```

### Серверная валидация 422

Обычная форма не отправляет заведомо неверные поля из-за клиентской валидации.
Для отдельной проверки реального API, когда регистрация включена, выполните
в DevTools → Console страницы `http://127.0.0.1:5173`:

```javascript
await (async () => {
  const options = { credentials: 'include', mode: 'same-origin', cache: 'no-store' };
  const csrfResponse = await fetch('/api/v1/auth/csrf', options);
  if (!csrfResponse.ok) throw new Error('Не удалось получить CSRF');
  const { data: csrf } = await csrfResponse.json();
  const response = await fetch('/api/v1/auth/register', {
    ...options,
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      [csrf.headerName]: csrf.token,
    },
    body: JSON.stringify({ email: 'invalid', password: 'short', displayName: '' }),
  });
  const payload = await response.json();
  console.log({
    status: response.status,
    code: payload.error?.code,
    fields: Object.keys(payload.error?.fieldErrors ?? {}),
  });
})();
```

Ожидаются `422`, `VALIDATION_FAILED` и ошибки соответствующих полей. После проверки
перезагрузите страницу. Этот запрос проверяет серверную валидацию; отображение
серверных `fieldErrors` в форме отдельно проверяется Playwright с подменой ответа.
Не записывайте ручную проверку API как проверку полного UI-сценария 422.

### Backend недоступен и неизвестный результат запроса

Остановите backend, оставив Vite запущенным, и перезагрузите страницу. Ожидается
экран ошибки подключения с явной кнопкой повторной проверки; ошибка не превращается
в гостевую сессию или автоматический вход в демо. Запустите backend снова и
нажмите повторную проверку: состояние определяется по настоящему `/auth/me`.

При потере ответа на вход или выход интерфейс должен перепроверить сессию через
CSRF и `/me`, без автоматического повторения POST. При невозможности проверки
нельзя утверждать, что вход или выход состоялся. После восстановления соединения
сначала выполните проверку сессии. Если неизвестен результат регистрации,
попробуйте вход с тестовыми данными, а не повторную регистрацию вслепую.
Потеря ответа **после** обработки POST и блокировка повторной отправки воспроизводятся
в тестах с подменой ответов; простая остановка backend этого не доказывает.

## Автоматические проверки без backend

В отдельном PowerShell из каталога `frontend`:

```powershell
node --test tests/apiClient.test.js tests/authApi.test.js tests/subjectApi.test.js tests/sessionFlow.test.js
npm run build
npx playwright test
```

Если Chromium ещё не установлен: `npx playwright install chromium`.
Стандартные Playwright-тесты используют preview на порту `4173` и подменяют API;
они не требуют Java, PostgreSQL или работающего backend. Успех этих тестов
не заменяет ручную проверку через dev-сервер на `5173`.

В PR запишите выполненные пункты, ожидаемые/полученные статусы и найденные ошибки,
без секретов. Невыполненные пункты отметьте явно. Тестовые аккаунты остаются в
локальной БД; пересоздавать базу или удалять пользователей для этой проверки не нужно.
