# Совместная проверка MVP с настоящим backend

Это инструкция, а не отчёт о выполнении каждого пункта. Сценарий проверяет настоящий
интерфейс, Java backend, PostgreSQL и приватное хранилище файлов. Основной проход с
настоящими R2/jobs и AI=`fake` подтверждён отчётом backend-разработчика от 04.10.2026
на ревизии `405217b`; расширенный список выполнен частично. Сводка результатов,
исправление CSRF в PR #40 и оставшиеся проверки — в [плане запуска](../../docs/launch-plan.md).
Автоматические проверки Node/Playwright с подменёнными HTTP-ответами учитываются отдельно.

Источники: [контракт API](../../docs/api.md), [запуск backend](../../backend/README.md),
[проверка авторизации](auth-integration-check.md),
[проверка предметов](subjects-integration-check.md). Последняя описывает ранний этап
предметов; для уже подключённых материалов, тестов и истории применяется сценарий ниже.

## 1. Подготовка окружения и данных

- Frontend и backend содержат согласованные изменения до истории попыток включительно.
  Запишите их ревизии и наличие локальных изменений в отчёте. Старые описания состояния
  отдельных этапов в документации не заменяют проверку фактически запущенной версии.
- Доступны JDK 21 и отдельная локальная PostgreSQL 17 с настройками из backend README.
  Backend запускается с `SPRING_PROFILES_ACTIVE=local`; Flyway должен применить миграции
  до V11 включительно. Чужую или рабочую базу для этого сценария не используйте.
- Для загрузки, скачивания, извлечения текста и удаления нужен уже настроенный приватный
  R2-бакет. `STUDYMATE_R2_ENABLED`, `STUDYMATE_JOBS_ENABLED` и
  `STUDYMATE_MATERIAL_MAINTENANCE_ENABLED` включены. Endpoint, бакет и секреты настраивает
  владелец backend по его README; этот документ не создаёт облачные ресурсы.
- Создайте два тренировочных аккаунта A и B. Если они уже есть, регистрация не нужна.
  Для создания новых аккаунтов регистрация включается только в локальном стенде через
  `STUDYMATE_REGISTRATION_ENABLED=true`. Не открывайте публичную регистрацию этим шагом.
- Подготовьте небольшой искусственный PDF с извлекаемым текстом и несколькими десятками
  учебных фактов. Добавьте, если удобно, одну пустую физическую страницу. Не используйте
  реальные лекции студентов или персональные данные. Запишите имя, размер в байтах и
  ожидаемое число страниц. Для негативной проверки нужен отдельный PDF без текстового слоя.
- Для A и B используйте разные профили браузера или независимые браузеры. Две обычные
  вкладки одного профиля разделяют cookie; они нужны отдельно для проверки конфликтов.

Пароли, cookie, CSRF, ключи OpenAI/R2, подписанные download URL и полные HAR не прикладывайте
к отчёту. Секреты остаются в настройках запуска backend и не попадают в `VITE_*`.
Spring Boot не читает `.env` автоматически; нужные переменные задаются в IDE/терминале.

### Основной проход: настоящий backend и R2, локальная генерация без OpenAI

В уже настроенном терминале backend задайте до запуска:

```powershell
$env:SPRING_PROFILES_ACTIVE = 'local'
$env:STUDYMATE_AI_PROVIDER = 'fake'
$env:STUDYMATE_R2_ENABLED = 'true'
$env:STUDYMATE_JOBS_ENABLED = 'true'
$env:STUDYMATE_MATERIAL_MAINTENANCE_ENABLED = 'true'
.\mvnw.cmd spring-boot:run
```

Команда выполняется из `backend/`; Java, PostgreSQL и R2 должны быть настроены заранее
по backend README. `fake` допустим только с профилем `local` и возвращает `fake-local`.
Он не обращается к OpenAI и не расходует его API-баланс. Работа с R2 остаётся настоящей:
это не проверка без облачного хранилища и не утверждение о бесплатности тарифа R2.
Если R2 недоступен, полный цикл PDF отметьте как заблокированный; нельзя выдавать
подмену HTTP или локальный preview за сохранение файла в R2.

Из `frontend/` в отдельном терминале:

```powershell
npm ci
npm run dev -- --host 127.0.0.1 --port 5173 --strictPort
```

Откройте `http://127.0.0.1:5173`. Backend слушает `127.0.0.1:8080`, health возвращает
`{"status":"UP"}`. Запросы UI идут на `/api/v1` того же origin через Vite proxy.
Не смешивайте `localhost` и `127.0.0.1`. Preview на `4173` из Playwright не заменяет
этот запуск. В Network фиксируйте пути, статусы и безопасные коды ошибок, не секреты.

## 2. Аккаунт, предмет и PDF

1. Войдите в A. Проверьте профиль из `/auth/me`, серверный список предметов и отсутствие
   демонстрационного прогресса среди реальных данных. Подробный вход/выход проверяется
   по [сценарию авторизации](auth-integration-check.md).
2. Создайте отдельный предмет с узнаваемым тестовым названием. После `POST /subjects`
   с ответом `201` он остаётся после обновления страницы. Демо-предметы не импортируются.
3. Перед загрузкой запишите `usedBytes`, `reservedBytes` и `lectureCount` этого предмета.
   Не предполагайте нулевую исходную квоту: в аккаунте могут быть другие тестовые файлы.
4. Выберите PDF и загрузите один раз. `POST /materials` отправляет FormData с файлом,
   subjectId и, при заполнении, title; используется один Idempotency-Key на эту загрузку.
   Повторное нажатие во время запроса не создаёт второй материал.
5. `201` означает сохранённый оригинал. После свежего чтения материал имеет `stored`;
   извлечение текста проходит отдельным заданием через `processingJobId`. Быстрый job
   может завершиться до следующего чтения — UI не обязан успеть показать каждый статус.
   `ready` означает текст PDF, а не конспект или процент изучения.
6. После завершения перечитайте материал и страницы. Проверьте физические номера,
   пустую страницу при её наличии, количество страниц и текст без исполнения HTML.
   До готовности `pageCount`/`textCharacters=null` не должны показываться как ноль.
7. Проверьте обновлённые предмет и квоту: `lectureCount` увеличился на один, `usedBytes`
   увеличился на размер файла, завершённая успешная загрузка не оставила новый резерв.
8. Скачайте оригинал. Каждый клик получает свежий `GET /materials/{id}/download`;
   скачанный PDF совпадает с загруженным, имя сохранения по контракту — `material.pdf`.
   Ссылка действует 60 секунд и не сохраняется в приложении. Удалённый встроенный
   PDF-viewer и CORS бакета не являются частью этого сценария скачивания.
9. Переименуйте материал, обновите страницу и проверьте название. Исходное `fileName`
   сохраняется. Для проверки конфликта откройте редактирование в двух вкладках A,
   сохраните первую, затем вторую: `409 MATERIAL_VERSION_CONFLICT` сохраняет черновик.
   Чтение и выбор версии не отправляют PATCH; повторное сохранение требует действия.

Дополнительно загрузите PDF без текста: ожидается `PDF_NO_TEXT`, понятное объяснение
отсутствия OCR, доступный оригинал и занятая квота. Такой файл не превращается в готовый
конспект. Проверки 25 МиБ на файл и 500 МиБ на аккаунт проводите на подготовленных
тестовых данных; если граничный объём не воспроизведён, отметьте это в отчёте.
Клиентская блокировка слишком большого файла не доказывает серверный `413`, а отображение
лимита не доказывает `409 STORAGE_QUOTA_EXCEEDED`.

## 3. Конспект и версии теста в режиме fake

1. Откройте «Конспект» у PDF с готовым текстом. Открытие делает GET, но не запускает
   генерацию. Перед первым созданием должен быть показан явный диалог о внешнем ИИ,
   расходах и возможных ошибках. В этом проходе backend настроен на `fake`.
2. Подтвердите создание: `POST /materials/{id}/summary` → `202`, затем наблюдение за job
   и отдельный GET сохранённого конспекта. Результат помечен `fake-local`/демонстрацией;
   его нельзя записывать как проверку качества настоящего ИИ.
3. Закройте и откройте панель, затем обновите страницу. Конспект читается с сервера;
   нового POST генерации нет. Измените текст редактором: PATCH с version → `200`,
   `origin=user`, машинные страницы-источники больше не выдаются за ссылки ручного текста.
4. Проверьте конфликт редактирования в двух вкладках: второй PATCH со старой версией
   даёт `409 SUMMARY_VERSION_CONFLICT`, ввод сохраняется. После свежего GET нужно
   явно выбрать версию и отдельно сохранить; автоматического перезаписывания нет.
5. Запустите «Создать заново» после отдельного подтверждения. Прежний конспект остаётся
   доступен во время ожидания, затем обновляется; новый логический запуск имеет новый ключ.
   Открытый редактор не должен позволять параллельный запуск генерации.
6. Откройте «Тесты» и явно создайте тест. `POST /materials/{id}/quizzes` → `202`;
   при `material.quiz` succeeded поле `resultId` — quizId. UI читает именно эту версию
   через `GET /quizzes/{resultId}`, затем обновляет список.
7. Проверьте 10 вопросов по 4 варианта, порядок сохранённой версии и метку `fake-local`.
   В GET quiz нет правильных вариантов, объяснений и результатов. Повторное открытие
   или обновление списка не вызывает генерацию. Тест строится по PDF, а не по ручному
   тексту конспекта; fake-проход проверяет интеграцию, не смысл вопросов.

## 4. Прохождение и история

1. Нажмите «Начать тест» у сохранённой версии. `POST /quizzes/{quizId}/attempts` без
   тела и с отдельным Idempotency-Key получает `201`. Запишите attemptId для проверки
   последующих GET. До сдачи `review`, `correctCount` и `scorePercent` равны null.
2. Выберите ответы на несколько вопросов, один сбросьте. Перейдите в «Результаты»,
   найдите эту незавершённую попытку и нажмите «Продолжить». В той же вкладке и аккаунте
   выбор сохраняется в памяти; новая попытка и новый POST начала не появляются.
3. Перед сдачей проверьте число ответов и пропусков. Подтвердите: один
   `POST /attempts/{id}/submit`, без Idempotency-Key и без баллов от клиента, → `200`.
   Балл, выбранные и правильные варианты, объяснения и физические страницы приходят
   из сохранённого результата. Пропуск не отображается как правильный ответ.
4. История обновляется, разбор остаётся открытым. Повторите завершение из истории
   с фильтром «Не завершены»: завершённая строка исчезает из фильтра, но открытый
   результат остаётся. В истории null-балл отличается от результата 0%.
5. Вернитесь к версии теста и нажмите «Пройти ещё раз». Создаётся другой attemptId с
   новым ключом. Сдайте все вопросы пропущенными: результат должен быть ровно 0%.
   Открытие старого результата в истории не подменяет текущий проход этой версии.
6. Создайте вторую версию теста в fake-режиме. Первая версия и обе завершённые попытки
   остаются доступны; новая генерация не меняет старые вопросы, баллы и разбор.
7. Проверьте статусный фильтр, «Попытки материала», «Попытки этой версии», сброс фильтров
   и переходы «История материала»/«История этой версии» из панели тестов. Фильтры
   объединяются, смена фильтра возвращает первую страницу и закрывает выбранный detail.
8. При наличии более 20 попыток проверьте вторую страницу, возврат, сохранение страницы
   при уходе из раздела и корректировку исчезнувшей последней страницы. Дополнительные
   попытки существующего теста не вызывают ИИ. Если 21 попытку не подготовили, пагинацию
   реального API отметьте как невыполненную, даже когда она покрыта подменёнными тестами.

## 5. Перезагрузка, повторный вход и два аккаунта

1. Создайте ещё одну незавершённую попытку A и выберите вариант без сдачи. При обновлении
   страницы браузер должен предупреждать о незавершённом выборе. После подтверждённой
   перезагрузки откройте её из истории: attemptId прежний, вопросы есть, локальный
   неотправленный выбор потерян. Сервер промежуточные ответы не хранит.
2. Выйдите и снова войдите в A. Загрузите историю заново, откройте завершённую и
   незавершённую попытки. Серверные материалы, версии, результаты и попытки сохранены;
   прежние локальные черновики после явного выхода не восстанавливаются.
3. В независимом профиле войдите в B. Его предметы, материалы и история не содержат A.
   B может создать собственный предмет с таким же названием. В том же профиле браузера
   отдельно проверьте A → явный выход → B: старые строки, вопросы и черновики не видны.
4. Сравните доступ прямыми **GET** из сессии B к известным тестовым UUID A: subject,
   material, quiz, attempt и job должны возвращать соответствующий `404`, без содержимого.
   Для `GET /attempts?materialId=<материал A>` или `quizId=<тест A>` ожидается `200`
   с пустым списком. Это отдельная проверка владения API; отсутствие карточки в UI её
   не заменяет. Используйте Network/локальный API-клиент, не переносите cookie A в B.

После основного прохода можно отдельно остановить backend и перезапустить с
`STUDYMATE_AI_PROVIDER=disabled`, `STUDYMATE_R2_ENABLED=false`,
`STUDYMATE_JOBS_ENABLED=false`. На уже сохранённом quizId проверьте чтение, начало,
сдачу и историю: им нужны PostgreSQL и сессия, а не ИИ/R2/worker. Загрузка, скачивание
и очистка файлов этим режимом не проверяются. Перед удалением в разделе 7 восстановите
R2, jobs и maintenance; не меняйте бакет существующих материалов.

## 6. Сессия, ошибки и неизвестный результат

Проверки выполняются на тренировочном аккаунте и искусственных данных. Для каждого
случая запишите, проверен ли полный UI-путь или только HTTP API.

| Ситуация | Как проверить и что ожидать |
| --- | --- |
| Backend недоступен | Остановить только backend, обновить историю. Ошибка отличается от пустого списка; старые строки помечены устаревшими, прежний разбор при неуспешном чтении скрыт. После запуска — явное обновление, без автоматического POST. |
| Истёкшая/потерянная сессия | Оставить черновик в первой вкладке A, выйти во второй вкладке того же профиля. Действие/чтение в первой вызывает проверку сессии и вход. При восстановлении того же A без перезагрузки первой вкладки сохранённый локальный выбор можно продолжить после GET; записи B не смешиваются. |
| Устаревший CSRF | Оставить первую вкладку с черновиком, во второй выйти и снова войти в A. Первая вкладка может отправить старый CSRF и получить `403 CSRF_INVALID`. Восстановление читает сессию/CSRF, но не повторяет изменение автоматически; следующий POST требует действия пользователя. |
| Два клика | Быстро дважды нажать начало/сдачу при медленном соединении. Во время запроса кнопка блокируется, создаётся одна логическая операция. Замедление само по себе не проверяет потерю ответа после commit. |
| `429`/`Retry-After` | Воспроизвести на согласованном локальном стенде, если маршрут реально вернул ограничение. До срока повтор недоступен, после срока запрос сам не отправляется; закрытие и открытие панели не сбрасывает срок. Не считать подменённый `429` проверкой серверного лимитера. |
| Неизвестный start попытки | После контролируемой потери ответа повторить начало явно: тот же ключ и один attemptId. Закрытие панели/уход в историю не создают новую попытку. |
| Неизвестный submit | Набор фиксируется. GET с `in_progress` не разрешает его изменить; явный retry отправляет тот же набор. GET с `completed` показывает сохранённый результат. `409 ATTEMPT_ALREADY_SUBMITTED` ведёт к GET, не к повторному submit. |
| `422` при submit | Первичный подтверждённый отказ сохраняет выбор и разрешает исправление. Если до него уже был неизвестный результат отправки, последующий `422` не снимает фиксацию прежнего набора. |
| Потерянный ответ upload/генерации | Проверить список, квоту или состояние задания. Явный сетевой повтор сохраняет прежний ключ; новый ключ не используется для обхода неопределённости. При `410 UPLOAD_ABORTED` сначала сверить очистку, затем отдельно начать другую загрузку. |
| Ошибка R2/PDF/ИИ | UI не сообщает об успешном сохранении/генерации, не скрывает существующие версии. `AI_UNAVAILABLE` можно проверить с provider=disabled; ошибку R2 — только управляемым отказом локального стенда. Верните настройки перед продолжением. |

Остановка backend или режим Offline **не доказывают**, что запрос был обработан,
а ответ потерялся. Для такой проверки нужна контролируемая задержка/потеря ответа
после подтверждённой серверной обработки на отдельном стенде. Если такого инструмента
нет, отметьте этот пункт «не выполнен в реальной интеграции» и отдельно приведите
автоматические проверки с подменой. Не выдавайте искусственный ответ `409`/`422`
за воспроизведение соответствующей серверной гонки.

При проверке идемпотентности сравнивайте равенство/различие ключей локально в Network.
Достаточно записать в отчёт «ключ прежний/новый» и число созданных объектов. Не публикуйте
полный дамп запросов. Восстановление сессии, чтение истории и наблюдение за job не должны
сами отправлять платные генерации, начало попытки, submit или повторное удаление.

## 7. Удаление и возврат квоты

1. Верните R2, worker и maintenance в рабочее состояние. Используйте только материалы,
   созданные для этой проверки. До удаления запишите размер, текущую квоту и число попыток.
2. Откройте удаление PDF и отмените его: данные остаются. Затем подтвердите предупреждение
   об удалении материала, конспектов, тестов и всей истории попыток.
3. `DELETE /materials/{id}` → `202` запускает очистку. Этот ответ ещё не означает, что
   объект удалён или место освободилось. При `deleting` чтение связанных данных недоступно,
   материал занимает квоту, а непустой предмет удалить нельзя (`SUBJECT_NOT_EMPTY`, если
   соответствующий запрос дошёл до сервера).
4. После job succeeded клиент отдельно проверяет `404 MATERIAL_NOT_FOUND`, обновляет
   материалы, предмет и квоту. `usedBytes` уменьшается на размер очищенного оригинала;
   связанный резерв не остаётся после подтверждённой очистки. Сравнивайте с исходным
   состоянием аккаунта, а не с обязательным нулём.
5. История этого материала пуста, прежние quizId/attemptId недоступны, открытый разбор
   не остаётся на экране. Владелец R2 отдельно проверяет отсутствие созданного тестового
   объекта; одной исчезнувшей карточки недостаточно. Не копируйте object key или URL в PR.
6. Закрытие окна очистки не отменяет серверную работу. При ещё существующем deleting
   откройте «Проверить удаление». При failed/cancelled явный повтор допустим; повтор
   активной очистки использует тот же job. Если отказ/повтор не воспроизведён, отметьте это.
7. Удалите остальные созданные для проверки файлы, включая PDF без текста, и дождитесь
   очистки. Теперь отдельный тестовый предмет удаляется с `204`. Пересоздавать базу,
   удалять пользователей вручную или очищать весь бакет для завершения сценария не нужно.

## 8. Отдельный проход с настоящим OpenAI

Выполняется только после явного разрешения владельца на реальную передачу текста и
расходы. Основной fake-проход не является таким разрешением. До запуска согласуйте
искусственный PDF, ожидаемые действия (конспект и/или тест) и допустимые расходы;
настройте существующий проектный API-ключ по backend README, не передавая его в отчёте.

1. На локальном backend смените provider с `fake` на `openai` и перезапустите его.
   Прочитайте существующий материал; открытие UI не должно само вызвать OpenAI.
2. Отдельно подтвердите создание конспекта, затем теста, если оба действия согласованы.
   Проверьте реальные job, сохранённый результат после GET и отсутствие метки `fake-local`.
   Длинный PDF может потребовать нескольких обращений к модели; один POST не равен
   одному вызову OpenAI. Не запускайте повторную генерацию только ради браузерного теста.
3. Сопоставьте несколько тезисов, вопросов, правильных ответов и физических страниц с PDF.
   Валидный JSON и успешная сдача проверяют структуру и сохранённый ключ, а не истинность
   содержания. Неподходящие вопросы фиксируйте как отдельный результат качества.
4. Проверьте сохранность версии/результата после обновления. Запишите факт расхода в
   проекте провайдера без ключей и приватного текста. При неизвестном исходе сначала
   проверьте job, сохранённый результат и расходы; новый платный запуск не делайте вслепую.
5. Верните `fake` или `disabled` для дальнейших обычных проверок. Реальный OpenAI smoke
   отметьте отдельно от fake, от проверки R2 и от автоматических тестов.

## 9. Как записать результат

Скопируйте шаблон в отчёт проверки, заполнив только фактически выполненное:

```text
Дата и участники:
Ревизии frontend/backend; локальные изменения:
ОС, браузер, JDK/PostgreSQL; origin frontend/backend:
Режим: local; AI=fake/disabled/openai; R2/jobs/maintenance=включены/выключены
Данные: искусственный PDF, размер/страницы; тренировочные аккаунты A/B

Пункт | Пройден / ошибка / заблокирован / не выполнялся | Наблюдение
2. Аккаунт/предмет/PDF/скачивание/название |
3. Конспект/редактирование/версии теста |
4. Прохождение/пропуски/история/фильтры/пагинация |
5. Перезагрузка/повторный вход/два аккаунта/владение GET |
6. Сессия/CSRF/конфликты/Retry-After/неизвестный исход |
7. Очистка R2/связанных данных/квоты/предмета |
8. Настоящий OpenAI — отдельное разрешение и результат |

Для ошибки: шаги, ожидаемое и фактическое, endpoint/status/безопасный code,
повторяемость, влияние на сохранённые данные, ссылка на исправление при наличии.
Отдельно: какие проверки были только API, какие — полный UI-путь,
какие — автоматические с подменой; что осталось непроверенным и почему.
Тестовые материалы очищены / какие оставлены намеренно:
Секреты, HAR и приватный текст в отчёт не включены.
```

Полный проход не подтверждает готовность публичного пилота: настройка хостинга,
допуск пользователей, серверные частотные ограничения и восстановление резервной
копии остаются отдельными пунктами общего [этапа 13](../../docs/architecture.md).
